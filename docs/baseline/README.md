# Textus 改造基线 · 文档地图

> 给人，也给 AI 代理：**做界面 / 产品 / 任务相关工作前，先读这份，再读别的。**
> 成因：2026-11-16 一次界面评审里，代理把上游文档当成本仓规划、又拿方向稿当已批准画板，连续读错两次。本文件就是防这件事的。

本仓库是 `CatVinci-Studio/Textus` 的**下游工作仓**：上游文档描述上游产品，`docs/baseline/` 描述**我们的改造**。两套真相并存，读错就会拿上游的路线图当我们的、或拿我们的裁决当上游的。

## 三条规矩

1. **进度与裁决只写下游文档**。上游文档是语境，B 组 rebase 时它们会变，写进去的结论会丢。
2. 冲突时的优先级：**工程门禁按上游；产品与界面决策按 baseline**（裁决以《界面改造方案》§4 为准）。
3. 改任务先改出处文档，再改清单（清单自己的规矩，在此重申）。

## 给 AI 代理的读法（最小集）

接手界面 / 产品任务时，按序读：本文件 → 《改造任务清单》（进度）→ 与任务相关的基线文档（界面任务必读《界面改造方案》全文 + 相关画板源文件）→ 只有涉及工程落地时才进上游 `docs/dev/*`。**方向稿（`boards/directions/`）是历史选项，不是批准稿**；批准稿只有 `boards/screens/`。

**界面任务的目标永远是 `boards/screens/` 里的画板（新 IA 工作台）**，不是现有实现的样子。现有实现是宿主，写代码要查它的机制时才进引擎代码；不要把它当作设计或审美的参照物。
