# 笔记资产理论

> 版本：v0.2
> 日期：2026-11-15
> 状态：待验证，不是结论
> 范围：以真实交付为核心的个人工作，不绑定任何软件

## 0. 一句话版本

> **资产不是写出来的，是被下一次真实交付验证出来的；笔记只保留证据、边界和触发条件。**

这句话不是产品文案，而是一个可以被证伪的假设：如果一个"资产"在 30 天内没有被下一次交付调用，或者调用后没有改善结果，它就不该继续被称为资产。

## 1. 这套理论要解决什么

传统笔记优化的是"记录得全不全"。

到了 AI 时代，记录成本接近零，瓶颈不再是记录，而是：

1. 哪些内容值得留下；
2. 留下之后怎么验证；
3. 验证之后怎么在正确的时刻被调用。

所以这套理论不关心"如何记得更多"，只关心**如何让一次交付改变下一次交付**。

## 2. 五个基本主张

1. **资产的最小单位不是知识，是"条件—动作—结果"。**单独一句结论无法复用，因为没有说明它在什么条件下成立。
2. **判断只能由结果验证，不能由表达力验证。**写得再顺，也不等于对。
3. **资产必须带触发条件。**不知道什么时候该用它，等于没有它。
4. **复用形态决定复用成本。**清单、模板、prompt、脚本的成本完全不同。
5. **没有淘汰机制的系统必然失真。**只增不减的库，最后一定没人看。

## 3. 旧模型为什么不够

旧模型是一条开环流水线：

```text
任务 → 判断 → 资产
```

它的问题是终点错了：写完资产卡就结束，没有任何一步要求回到真实结果。执行一段时间后，它必然退化成任务台账。

具体缺四件事：

| 缺失 | 后果 |
| --- | --- |
| 结果 | 判断无法被验证，只能靠感觉 |
| 边界 | 资产在错误场景被套用 |
| 触发 | 资产躺在库里，不会被想起 |
| 形态 | 复用成本过高，宁愿重做 |

第五件事是淘汰：没有失效机制，旧结论会一直假装有效。

## 4. 结果闭环

修正后的循环是：

```text
真实交付 → 先做后记 → 结果判定 → 边界提炼 → 可调用形态
     ↑                                              │
     └────────────── 下一次交付复用 ─────────────────┘
```

| 步骤 | 要产出什么 | 门槛 |
| --- | --- | --- |
| 真实交付 | 一次有验收标准的交付 | 不是"学习某主题" |
| 先做后记 | 只记决策点和意外 | 不写过程流水账 |
| 结果判定 | 预期 vs 实际 vs 偏差 | 事前先写验收标准 |
| 边界提炼 | 适用 / 不适用 / 反例 | 至少一条反例 |
| 可调用形态 | 清单、模板、prompt、脚本、决策表 | 下一次能直接拿来用 |

硬规则：

> **7 天内没有被下一次真实交付调用，标记为"未验证"。30 天内仍未被调用，降级或归档。**

这条规则比任何分类都重要。它把"记录"变成"实验"。

预防性判断的例外：边界防住的错误不会发生，没有"实际结果"可验。这类判断靠**反例验证**——边界一旦失效，立即升格为已验证反例；平时保持 confirmed，可标注"未经结果验证"。

## 5. 记录的最小充分集

这套记录有**两层**，不要混：

- **执行期**：防弹笔记法式的核心任务笔记——自由写、堆资料、做连结，是任务的工作台。这一层不受任何字段约束。
- **交付后**：从工作台切出下面的最小集，成为卡片；原笔记以 `sourceIds` 挂为证据。

卡片是切片，不是工作台：执行期的东西不进卡片，卡片的字段也不反过来管执行期。

### 5.1 任务卡

只加三行，不要写流水账：

```yaml
expected_outcome: "2 周内交付，客户一次通过"
actual_outcome: "18 天交付，返工 1 次"
variance: "低估了外部确认时间"
```

写法门槛：`expected_outcome` 写成**可判定、可数**的条件（时间、次数、通过与否），不写形容词——复用成功率要靠它判定 better / same / worse。

### 5.2 资产卡

必须有四项：

```yaml
boundary:
  applies_when:
    - "周期 ≥ 15 天"
    - "外部依赖 ≤ 2 方"
  fails_when:
    - "周期 < 15 天"
    - "需求方未定稿"
  counterexample: "上一次 10 天项目，因材料等待延期 6 天"

trigger:
  stage: before_delivery   # before_delivery / during_task / after_result / on_demand
  label: "报价前"

reuse_form: checklist      # checklist / template / prompt / script / decision_table / doc

last_used_at: null
```

### 5.3 不要记什么

- 不记完整的操作过程，只记决策点和意外。
- 不记没有来源的结论。
- 不记自己不会回头看的会议纪要。
- 不用形容词代替结果数字。
- 不在一条记录里塞多个判断。

**谁来记**：agent 采证据、可以起草客观字段（情境、预期、来源）；判断字段——边界、触发、实际结果的评价——由人定稿（《Textus-Agent工具契约》的 `create_draft` / `propose_patch` 已按此设计）。

### 5.4 一条完整示例

```text
情境：一次对外交付，周期要求 2 周，预算有限
动作：先做可行性检查，再报价
预期：2 周内交付，一次通过
实际：18 天交付，返工 1 次
偏差：低估了等待外部确认的时间
边界：周期 < 15 天不接；外部依赖超过 2 方要加缓冲
触发：每次报价前
```

**七行的定死口径**：情境、动作、预期、实际、偏差、边界、触发。形态（`reuse_form`）不占行——它是资产卡的字段，封装为资产时才定（上例即"报价前 5 项检查清单"）。七行，比一篇复盘有用。

## 6. 触发与形态

### 6.1 触发阶段

只保留四个阶段，避免无限扩张：

| 阶段 | 典型场景 |
| --- | --- |
| `before_delivery` | 报价、提案、开工前 |
| `during_task` | 执行中遇到偏差 |
| `after_result` | 复盘、偏差归因 |
| `on_demand` | 主动查询 |

一个资产只设一个主触发。多个触发会让它既不明显，也不准确。

### 6.2 复用形态

| 形态 | 适用 | 成本 |
| --- | --- | --- |
| 清单 | 检查项明确 | 低 |
| 模板 | 结构重复 | 低 |
| prompt | 交给 Agent 执行 | 中 |
| 决策表 | 多条件分支 | 中 |
| 脚本 | 可自动化 | 高 |
| 说明文档 | 需要解释背景 | 高 |

优先级：能用清单就不用文档，能自动化再考虑脚本。

## 7. 理论本身如何迭代

### 7.1 三层分离

| 层 | 放什么 | 变更频率 |
| --- | --- | --- |
| 理论层 | 假设、指标、边界 | 高 |
| 数据层 | 卡片与字段 | 中 |
| 实现层 | 软件、脚本、Agent | 低 |

原则：**理论在文档层迭代，不要每次改理论都改数据结构。**数据结构只保留不会轻易变的字段。

### 7.2 理论卡

把理论本身也写成一张卡，带版本和结论：

```yaml
type: theory
version: 0.2
hypothesis: "记录结果与边界后，下一次交付准备时间下降 20%"
metrics: [复用率, 复用成功率, 返工率]
started_at: 2026-11-15
review_at: 2026-12-13
verdict: pending
```

理论卡也遵守同一套规则：有假设、有指标、有期限、有结论。没有结论的理论不进入下一版。

### 7.3 四个指标

| 指标 | 定义 | 作用 |
| --- | --- | --- |
| 复用率 | 30 天内被调用过的 active 资产 / active 资产总数（分母排除激活未满 30 天的**观察期**资产，单列计数） | 判断资产是否真的被用 |
| 复用成功率 | 复用后达到验收标准的次数 / 有结果记录（`result`）的复用次数 | 判断资产是否有效 |
| 返工率 | 返工交付 / 总交付 | 判断是否减少了重复错误 |
| 台账率 | 30 天未复用且无结果记录的资产 / 资产总数（同样排除观察期资产） | 判断系统是否在退化 |

只看前三项容易自我感觉良好，台账率才是警报。

### 7.4 月度复盘只问三个问题

1. 哪条判断被结果证伪了？
2. 哪个资产一次都没被用过？
3. 哪个字段几乎没人填？

对应动作有四个：改判断、删资产、删字段、**修数**——绕过工具的真实使用（直接打开文件抄一段、在没有插件的设备上复用）在复盘时人工补记 `record_use`，否则 7 天规则会误伤真用过的资产。

### 7.5 删除机制

淘汰时间线：30 天未被调用标记"未验证"（§4）→ 连续 3 个复盘周期仍未复用 → `deprecated`。

- 连续 3 个复盘周期未被复用 → `deprecated`。
- 90% 的卡片都空着的字段 → 从 schema 删除。
- 指标连续两个周期不达标 → 升级理论版本，而不是加强执行。
- 反例必须保留，不能为了好看删掉。
- confirmed 但 90 天未被任何任务 `sourceIds` 引用 → 打"复查"标记（不降级，只提醒）。

### 7.6 版本规则

- 每张卡带 `theory_version`。
- 新版本只影响新卡和后续修改，不改写历史。
- 旧卡不迁移，除非它被再次使用。
- 版本号只增不减，避免"悄悄改定义"。

## 8. 最小实验

### 8.1 设计

- 周期：4 周。
- 样本：10 个真实交付物。
- 记录：每个交付只写七行。
- 封装：至少 3 条可调用资产。
- 复用：至少 1 条资产在后续交付中实际使用。

### 8.2 通过标准

- 复用率 ≥ 30%。
- 复用后结果有可观察改善，或返工率下降。
- 至少记录 3 条反例。
- 记录时间不超过交付时间的 10%。

### 8.3 失败标准

出现任意一条，就优先修改理论，而不是增加功能：

- 复用率 < 30%；
- 复用后没有改善；
- 记录本身拖慢交付；
- 大部分字段空着；
- 自己不愿意回看。

### 8.4 常见失败方式

| 失败方式 | 表现 | 修正 |
| --- | --- | --- |
| 记录癖 | 卡片越来越多，交付没变快 | 限制每单七行 |
| 结论先行 | 先写方法，再找证据 | 先做后记 |
| 无边界的资产 | 到处都适用 | 强制写反例 |
| 只存不触发 | 从不打开资产库 | 绑定触发阶段 |
| 理论教条化 | 为了填字段而填字段 | 每月删字段 |

## 9. 适用边界

适用：

- 有重复性的交付；
- 结果能在 2 周内观察到；
- 决策点相对清晰；
- 自己既是执行者也是复盘者。

不适用：

- 纯探索阶段，还没有交付物；
- 结果不可归因；
- 超长期研究；
- 一次性创意首发；
- 团队流程已经成熟，个人笔记改变不了结果。

反例：把每一篇读书笔记都做成资产卡，通常会在两周内放弃。读书笔记没有交付和结果，不满足这套理论的前提。

## 10. 与软件的关系

这套理论对软件只提出六条约束，不规定实现：

1. 能存下结果、边界、触发和复用形态；
2. 能按触发阶段取回资产，而不是只靠搜索；
3. 正式状态必须人工确认；
4. 修改保留历史，冲突不覆盖；
5. 理论版本与卡片版本可追溯；
6. 计数字段（`use_count` / `verified_count` / `last_used_at`）只能由工具写；外部编辑器不碰这些字段，写坏以审计日志修复。

Textus 的具体落地见《Textus-改造方案》与《Textus-Agent工具契约》，但软件不是理论成立的前提。

## 12. 来源与推导

> v0.2 新增。写清楚哪些是继承、哪些是自己的假设——三个月后的自己要能追溯。

### 12.1 智能体时代的前提（百度世界 2026）

- 2026-11-12 百度世界大会，李彦宏提出"AI 的下一幕是智能组织"；同年 5 月 Create 开发者大会上，"一次性软件 / 日抛型软件"变得合理（代码智能体秒哒）。
- 本理论的前提句"记录成本接近零，瓶颈转移到验证与调用"是这个叙事向**个人工作流**的移用：智能体把生产变便宜之后，稀缺的不再是写，而是"哪些值得留、怎么验证、何时被调用"。
- 理论动机的一对张力句：**软件可以日抛，判断必须持久。**

### 12.2 防弹笔记法（Esor 张惇翔）

- 继承：以任务为中心组织笔记；`sourceIds` 来源链 ≈ 原法的"连结"；反对按资料类型分类存档。
- 有意为之的偏离：原法的核心任务笔记是执行期工作台；本理论的任务卡是交付后切片。两层关系见 §5 开头——执行期用防弹式笔记随便写，交付完切七行，原笔记挂 `sourceIds`。

### 12.3 哪些是自己的假设

五条主张里，第 1 条（条件—动作—结果）、第 3 条（触发）、第 5 条（淘汰）是本理论的新增假设，没有前人背书，证伪口径就是 §8 的最小实验；第 2 条（结果验证）与复盘方法同源；第 4 条（复用形态决定成本）是工程常识。
