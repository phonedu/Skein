# 同步 supersede 裁决（S0a）

> 归档：S0a 完整裁决记录（2026-11-19），保留作历史；现行裁决见 [decisions/0051](../decisions/0051-同步-supersede-S0a.md)。

> **状态**：已落档，2026-11-19。本文是 fork 自建同步的**前置裁决**；没有本文，不写同步代码。
> **性质**：supersede 早先「不改同步 / 深度分叉不建议」的口径，不是推翻上游，也不是要求上游接受本 fork 的同步实现。
> **上游关系**：`CatVinci-Studio/Textus` 的同步仍以插件为准；本 fork 的内置同步只服务 Skein，不进入上游 PR（[publishing-gate](../discipline/publishing-gate.md)）。

## 1. 被 supersede 的是什么

早先的判断是：

- 上游同步由官方 `catvinci.cloud-sync` 插件承载，fork 不另做；
- 深度分叉会拉高跟随上游的成本，所以「不改同步」；
- 手机端只做只读/轻量，不承诺上传下载。

本文把这三条改为：

1. **fork 自建内置同步**，作为 Skein 的产品能力；
2. **插件先做多端参考实现，内置随后接管**；插件冻结为 `/1` 参考，不再双维护；
3. **手机端前台可读写**，后台同步不作为 v1 承诺，单独立项。

## 2. 为什么改

### 2.1 插件的硬边界

评审已确认（[02-Android 评审](../research/同步评审/02-Android移动端评审.md)、[00-汇总](../research/同步评审/00-汇总与建议.md)）：

- 插件只声明桌面与 iOS，**Android 不在 manifest 内**；手机无法使用。
- 即使补上 Android，`files.trash` 在移动端不可用；SAF `content://` 下插件文件 API 在宿主入口被拒；二进制写、mtime、原子写、后台同步都补不齐。
- 插件 base 只存 hash，没有 base 文本；三方合并、迁移 dry-run、冲突中心都做不完整。
- 手机没有插件入口、同步状态面、文件事件；这些是宿主能力，不是插件能补的。

### 2.2 产品需要

- 手机 ↔ 电脑同步是当前最大痛点；LAN（同一 Wi-Fi）是明确需求。
- 多库（工作/个人/资产）需要一库一仓库、独立密码、独立状态。
- 资产库作为主库子目录，必须随主库同步，不能做第二套仓库。
- 同步状态、冲突不静默覆盖、迁移可回滚，是笔记产品的信任底线。

### 2.3 为什么仍然「先插件、后内置」

- 插件只要 1–3 周就能拿到手机真实上传/下载/删除/冲突数据；内置是 12–22 人周。
- 插件已经把 `/1` 协议跑通；先把它冻结成参考实现，内置用同一套协议与 golden vectors，风险最低。
- 插件阶段修掉的 7 个小补丁（空扫描保护、锁、trash、默认库、状态、S3、打开文件）在内置里同样需要，不是白做。

## 3. 与「深度分叉不建议」的关系

- 仍然**不建议**把上游核心（编辑器、文档模型、插件 API）改成 fork 专属；内置同步放在独立 crate 与薄适配层，上游文件改动保持小。
- 仍然**只跟 release tag**，不追 main；同步的 patch 清单必须能在下一次 rebase 时重放。
- 上游若将来自己做同步：本 fork 的 `/1` 兼容层可以退成迁移工具，内置实现按 S5 的退出条件评估是否保留。

## 4. 不可越过的安全线

在任何阶段都必须成立：

1. **远端不误删**：空扫描、大批删除、锁失败、清单损坏时，宁可停下，不按删除处理。
2. **本地不半截**：写入先临时文件/临时对象，再原子替换；失败保留原文件。
3. **冲突一定两份**：不做静默覆盖；冲突副本命名稳定、可读。
4. **迁移可回滚**：导入 base/凭据前 dry-run；插件先停用后卸载；卸载前确认 base 已迁移。
5. **不泄露凭据**：日志、错误、诊断包不含 token/密码/密钥；E2EE 新连接默认开。
6. **旧客户端仍可读**：`/1` 不因 fork 新字段而拒绝；v2 硬切时旧客户端 fail closed 并提示升级。

## 5. 退出条件（什么时候可以停/回滚）

内置同步不是一次性承诺，满足以下任一条件就停下评估：

- **数据安全事件**：出现一次远端误删或本地丢文件，且无法从快照/冲突副本恢复 → 暂停内置，回滚到插件只读。
- **迁移失败率**：dry-run 通过但真迁移失败超过 10%，或出现不可恢复的 base/凭据丢失 → 停止推广。
- **上游接手**：上游发布官方多端同步且 `/1` 可互通 → 评估把内置降为迁移/兼容层。
- **维护成本**：连续两个上游 tag 的 rebase 需要改同步核心超过 2 人周 → 重新评估内置是否值得。

### 6.5 版本与回滚

- 内置发布后，插件冻结为 `/1` 参考实现，只修安全问题；不新增功能。
- 内置与插件不共享 base/secrets；迁移是复制/导入，不是原地接管。
- 回滚 = 停用内置 binding → 重新启用插件（使用迁移前的凭据/base 备份）；远端 `/1` 不变。

**内置同步是 fork 的产品能力，不是上游的分叉；先冻结 `/1`、先用插件拿真机数据、先把宿主文件层补齐，再谈 Rust 协议层。**
