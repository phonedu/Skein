# 裁决 66 — 一库多后端，各自保留同步基线

## 决定

| 事项 | 裁决 |
| --- | --- |
| 模型 | 一个库可以有多个后端（局域网 Hub、S3、WebDAV）；每个后端是独立仓库，各留自己的 base/last/repository_id。 |
| 活动后端 | 同一台设备同一时刻只有一个 active 后端；不做 Hub 与 S3 同时写。 |
| 切换 | 普通切换只改 active 后端，不清另一个后端的 base/last；不再把“切连接”当新仓库。 |
| 首次对账 | 目标后端没有状态时进入首次对账：目标空则上传；两边都有则只传本地独有、只下远端独有；同路径不同内容出冲突副本，不覆盖、不删除。 |
| 后续切换 | 使用该后端自己的 base 做增量；local 在其他后端改过的文件按本地变更上传。 |
| 设备间 | 两台设备只有选同一后端时才互相看见；一台 LAN、一台 S3 时各自同步，这是预期。 |
| 加密 | 同一库所有后端必须同一加密状态与密码；不一致拒绝切换。 |
| 不做 | 不做一库多入口的自动复制/迁移；不做两个后端并行写；不做首次对账自动删除。 |
| 旧状态 | 旧后端的 base/last 保留；只有用户明确清除该后端状态才删。 |

## 理由

用户参考的笔记软件是“一个本地库 + 多个独立后端”，不是“一个仓库多入口”。它的行为是：平时局域网，切 S3 时上传/检查，另一台设备切 S3 再对账；两台设备都切回局域网后才通过局域网互相同步。

当前 Textus 只有一个 binding、一份 base，切换连接会清 base 并生成新 repository_id，所以每次切换都全量重来，无法达到这个效果。把同步状态拆到“每库每后端”后，切换只换 active 指针，才能保留各后端的增量基线。

这也是质量最好的做法：LAN 和 S3 是两个独立仓库，不共享锁，不产生双写；首次对账只做上传/下载/冲突，不删除任何一边。真正“同一份数据多入口”的复制/迁移/共享锁是另一层能力，等确有需要再做。

## 影响

- `SyncConfig` / `Binding` 需要从“一个库一个 connection + base”改为“一个库多个 BackendState + 一个 activeBackendId”。
- `store_ops` 的 `remote_changed` 不再删除旧 base；只创建/更新目标 BackendState。
- 首次对账复用现有 planner（空 base）和冲突副本规则，但必须强制预览；不做删除推断。
- 同步页需要显示当前后端、各后端上次结果和“切换”动作；归 S15，排在 S13/S14 之后。
- S7 规格里“切换 = 换 binding，清 base”的旧规则由本裁决取代；`同步页面改版.md` 的 §4 增加指向本裁决的说明。
- 测试矩阵按 `单库多后端同步.md` 第 7 节执行；S12 的下载块复用继续有效。

## 来源

2026-11-25 用户口述参考笔记软件的行为：同一设备只能一种同步方式；默认局域网；切 S3 时上传，另一台设备切 S3 后检查；两台都切局域网才能通过局域网同步。用户确认这就是想要的效果。
