# 协议兼容性评审（子代理）

> 来源：子代理独立评审，2026-11-18；只读分析，未修改任何文件；未经逐条人工复核。
> 结论：**有条件成立**——v1 的“旧客户端只读兼容”在“清单/历史顶层可选字段”和“1–2MB 变长块”上基本成立，但按现方案直接实施，会在 **CDC 块数/8MB 上限**、**租约 + head CAS（history/head 双对象、WebDAV 无条件写）**、**三方合并缺少 base 文本**、**移动端 content:// 文件层** 四处硬失败；这四项必须先改协议或先补宿主能力。

## 1. 盲区清单（按严重程度）

### 2.0 A–K 逐项判定

| 项 | 判定 | 一句话依据 |
| --- | --- | --- |
| A 未知字段 | **有条件** | 旧客户端 `parseManifest` / `parseHistory` 只校验已知字段并原样返回；`publish` 用 `{...remote}` 保留 head 顶层新字段。但旧客户端上传文件时重建 `Entry`（只含 hash/size/blocks），entry 级新字段会被丢弃；`history.current` 在内容变化时重建为 `{at,device}`；`format`、`inScope` 路径、`KEEP_DAYS` 枚举、块大小/块数是全量严格校验，任一处不满足是整份清单/历史被拒，而不是跳过该文件。 |
| B CDC 变长块 | **不成立（按现描述不足）** | 除每块 ≤2MB 外，旧客户端还要求 `blocks.length <= ceil(128MB/2MB) = 64`。CDC 若允许 1MB 下限，>64MB 文件必然超过 64 块；这些 Entry 一旦进入 **head 或 history**，旧客户端会以 `invalidManifest`/`invalidHistory` 拒绝整份对象。 |
| C 锁租约 | **不成立（作为 v1 兼容改进）** | 旧客户端把锁当“存在即占用”，不认识 `expiresAt`，不会自动接管，只能人工 unlock；现有代码自己也明确回避了 DAV 条件 PUT；且 CAS 只保护 head，history 是先写的另一个对象。 |
| D head 增加 repositoryId | **有条件** | 顶层可选字段会被旧客户端 spread 保留；加密模式的 descriptor 本来就有 `repositoryId`；但本地 base 键含 `root`，vault 移动会丢 base；旧插件重建 Base 时只写 `format/files/parked`，会丢掉任何新 base 元数据。 |
| E 移动端可移植删除 | **不成立（移动端现状）** | content:// 下 `trash()` 直接抛错；Rust 在非桌面拒绝 trash；SAF 隐藏目录对插件不可达；二进制写不支持；无 mtime。 |
| F 文本三方合并 | **不成立（按现机制）** | 插件 `Base` 只存 hash，没有 base 文本；history 会被 `thin`/`fit`/上限/崩溃/重建清掉，不能作为稳定的 base 来源。 |
| G head ETag 快进 | **有条件** | 需要给 `ObjectStore` 加 ETag/条件 GET；head 不变不代表 history 不变（崩溃窗口）；DAV 可能无 ETag 或弱 ETag；加密 head 每次重封 IV 随机。 |
| H 上传校验优化 | **有条件** | WebCrypto 没有 MD5；S3 SigV4 已经签名 payload SHA-256；DAV 无通用服务端哈希；需要按 provider 做能力矩阵，并补“块损坏修复”路径。 |
| I 插件→内置迁移 | **高风险/不成立（空 base 首同步）** | 空 base 首同步对每个双方不同文件生成冲突副本；冲突副本本身计入文件数，可能把 20k/8MB 推爆，导致永远无法发布。导入 base/凭据可行，但键、账号、root、格式必须精确，且卸载插件会删掉插件存储与 secrets。 |
| J GC 与并发 | **有条件，且有明确漏洞** | 锁串行下 CDC 的 used-set 正确；但被淘汰的 legacy trash 条目块不回收、孤儿快照不回收、`ownLock`→`remove` 非原子、接管窗口可删掉新 head 引用的块。 |
| K 其他 bug | **见下** | 移动端路径、符号链接、非 UTF-8 文本、大小写/NFC、`.textus` 排除绕过、限额等。 |

### 2.1 移动端 content:// 文件层是硬阻塞（最严重）

**问题**：插件在 `Workspace.path()` 中把路径拼成 `root + "/" + relative`（`C:\Project\textus-plugins\development\cloud-sync\src\local.ts:49-52`）。桌面/iOS plain path 没问题；但 Android 未授予“所有文件访问”时 `root` 是 `content://.../tree/<tree>/document/<docId>`，拼出来的 URL 在 document id 里带未编码的 `/`，不是 `DocumentsContract` 的合法 document URL。`contentPluginFs.stat` 又是“列出父目录、按完整 URL 字符串比较”（`C:\Project\Textus\src\platform\content-plugin-fs.ts:46-54`），必然匹配不到，`read` 返回 null，`scan()` 静默看不到任何文件（`C:\Project\textus-plugins\development\cloud-sync\src\local.ts:112-146`）。更糟的是：
- `contentPluginFs` 的 `entryOf` 把 `size` 固定成 0、`modified_ms` 固定成 null（`C:\Project\Textus\src\platform\content-plugin-fs.ts:34-44`），`scan` 的 size/mtime 缓存全部失效，且 `readRaw` 的“先看 stat.size 再读”上限保护失效（`local.ts:59-69`），超大文件会先整块读入内存。
- SAF 的 `listFolder` 在原生层直接跳过 `.` 开头的名字（`C:\Project\Textus\src-tauri\plugins\textus-files\android\src\main\java\TextusFilesPlugin.kt:186-198`），而 `contentPluginFs.stat` 依赖 listing，所以 `.textus/agent.md`、`.textus/library/*.md`、`.obsidian/*` 在 content:// 下也不可达——这些正是插件要同步的 Textus 项目数据和 Obsidian 设置。
- 二进制下载：`contentPluginFs.write` 对 `base64` 直接抛错（`C:\Project\Textus\src\platform\content-plugin-fs.ts:108-110`），所有附件下载都会让整次同步失败。
- 删除：`contentPluginFs.trash` 直接拒绝（`content-plugin-fs.ts:139-141`）；iOS 的 Rust `user_file_to_trash` 在 `#[cfg(not(desktop))]` 下也返回错误（`C:\Project\Textus\src-tauri\src\atomic.rs:400-416`，经 `C:\Project\Textus\src-tauri\src\plugins\access.rs:294-306` 调用）。
- “打开文件原地重载”：`FILE_WRITTEN_EVENT` 的重载逻辑在 `mtime === null` 时直接跳过（`C:\Project\Textus\src\document\useExternalChangeReload.ts:91-99`），而 `fileMtimeMs` 对 scoped URL 恒为 null（`C:\Project\Textus\src\platform\ipc-files.ts:116-117`），所以 Android content:// 下不会原地重载。

**后果**：Android 的 scoped 模式要么“永远 unchanged”实际不同步，要么在附件/删除/项目数据上直接失败；这不是协议问题，是平台文件层问题。若 base 非空（导入/手工写入等异常路径），空扫描还可能被 plan 当成“远端文件本地已删”而发布 `deleteRemote`（`engine.ts:311-317`），有远端误删风险。

**建议方向**：手机 spike 先决定“必须授予所有文件访问（plain path）”，或补宿主能力：
1. `files.*` 接受相对路径并在宿主用 `absoluteIn`/`contentJoin` 拼 URL（不要把 `root+"/"+rel` 当 URL）；
2. 原生层提供隐藏文件访问（按 document id 直接构造子 URI，而不是 listing 过滤）；
3. 原生层支持二进制写或改为“写临时文件 + 流式”；
4. 提供 App 管理的 trash 目录（不能依赖 SAF 内 `.textus` 隐藏目录，见 2.5）；
5. 为 content:// 提供 lastModified（或明确接受每次全量 hash）；
6. 对 content:// 的打开文件，用版本 token 或显式“外部写入”通知重载，而不是 mtime。

**需要什么测试**：Android 模拟器或设备上用 `content://` 夹具（含嵌套目录、`.textus/agent.md`、`.obsidian/app.json`、`.png` 附件、>128MB 文件）跑一次完整同步；断言 `files.list` 返回的 `entry.rel`/`entry.path` 被正确使用、附件可下载、删除可恢复、打开文件收不到重载时不标记成功。

### 2.2 CDC 不只是“每块 ≤2MB”：块数 64 与 8MB 清单/历史

**问题**：旧客户端的 `checkEntry` 有三个硬约束：
- 每块 `b.size <= CHUNK_SIZE`（2MB），且 `b.size > 0`（`C:\Project\textus-plugins\development\cloud-sync\src\content.ts:41-50`）；
- `e.blocks.length <= ceil(MAX_FILE_SIZE / CHUNK_SIZE)`，即 **64**（`content.ts:37`）；
- `sum(blocks.size) === e.size`（`content.ts:52`）。

CDC 若下限 1MB：一个 128MB 文件至少 128 块，远超 64；一个 65MB 文件也可能超过 64。旧客户端的 `parseManifest` 会因此抛 `invalidManifest`；`parseHistory` 对每个 version 也调用 `checkEntry`（`history.ts:62-70`），因此 **只要某个旧版本是 CDC 大文件，旧客户端连历史都读不了，整次 sync 在 publish 阶段失败**。这不是“某个文件跳过”，是整个仓库不可用。

此外清单/历史都是 8MB 上限（`model.ts:7,12`；`content.ts:56`；`history.ts:44`；`publish.ts:88-90`）。CDC 让每个文件的 blocks 数组变长，块列表是清单 JSON 的主要体积；20k 文件或大文件多时，8MB 会比现在更早触发 `tooManyFiles`。

反过来，旧客户端上传固定 2MB、最多 64 块的 Entry，新客户端只要保持 `checkEntry` 接受 `1..CHUNK_SIZE`、不改变 `blockKey`/下载上传循环，就能处理——这部分是成立的。

**建议方向**：把“旧客户端可读”写成写入不变量，而不是读取时的宽容：
- 新客户端写出的**任何** Entry（head、history version、trash entry、pending 发布）都必须满足 `blocks.length <= 64`、`1 <= block.size <= 2MB`、`sum == size`；
- 对 >64MB 的文件（按最坏块大小计算）禁用 CDC，退回固定 2MB；或者把 CDC 的最小块提高到 `ceil(size/64)`，保证块数上限；
- 发布前做一次“旧客户端解析器”自检（把 `content.ts`/`history.ts` 的旧版本冻结成测试夹具，对新输出跑 `parseManifest`/`parseHistory`）；
- 评估清单 8MB 的余量：CDC 的块列表会让 20k 文件场景更早触顶，必要时 v1 仍限制块数/文件数，v2 再放开。

**需要什么测试**：用旧版 `checkEntry`/`parseHistory` 的冻结副本，对新 CDC 生成的 1MB、1.5MB、2MB 块、128MB 文件、含大文件历史的仓库做解析；断言新客户端在写之前就拒绝不合规的 Entry，而不是发布后让旧客户端失败。

### 2.3 head/history 不是一个原子对象：CAS 只保护 head 会造出不一致历史

**问题**：`publish` 的顺序是 snapshot → history → head（`publish.ts:92-96`）。`ownLock()` 在写 history 前和写 head 前各查一次，但：
- snapshot 在任何 `ownLock` 之前写（`publish.ts:92-93`），锁失效/被接管后仍会留下孤儿快照；
- `ownLock` 是“读锁 + 比较字节”，`remove(LOCK)` 也是先查后删（`engine.ts:122-129, 422-427`；`connection.ts:63-71`），两个动作之间不是原子的；
- 两个 publisher 若因租约接管重叠：A 写 history HA，B 写 history HB，A 写 head HA（CAS 成功），B 写 head HB（CAS 失败）。head=HA、history=HB，`history.head` 与 head.revision 不一致。当前 `skipped` 恢复逻辑把 `before.head !== remote.revision` 当作“旧客户端写过”，会去 `snapshotKey(before.head)` 取 B 的 manifest 并 `retire`（`publish.ts:57-66`），从而把从未在 head 上存在过的文件写成历史版本，污染历史。
- `ObjectStore` 接口没有 ETag/条件写（`model.ts:120-130`），`RemoteStore` 也没有暴露 ETag（`transport.ts:144-159`）；加密模式每次 `seal` 用随机 IV（`encryption.ts:115-135`），物理 head 的 ETag 只能表示“有发布”，不能表示明文内容。

**建议方向**（三条任选，不能只做 head CAS）：
1. **每 revision 一个不可变 history/commit 对象**：`v1/commits/<revision>.json` 同时含 manifest 与 history 摘要，head 里引用它；旧客户端仍读 `v1/head.json`/`v1/history.json`，新客户端以 commit 为准，并在发布后回写兼容镜像。这样 CAS 只针对 commit 指针。
2. **history 也参与条件写**：`If-Match` history 的 ETag；但 DAV 不可移植。
3. **读侧一致性校验**：任何 publish 前重新读 head + history，要求 `history.head === head.revision`（或明确的“崩溃后状态” `history.head === 新 revision && history.previous === head.revision`）；不一致就按“未知历史”处理，先恢复再写，绝不基于缓存 history 发布。这至少阻止污染，但阻止不了“history 被覆盖”。

**需要什么测试**：假 store 支持 `If-Match`/412；两个 MemoryStore 客户端交错 publish；模拟 A 写 history 后 B 写 head；断言新客户端不会产生 `history.head != head.revision` 的持久状态，且旧客户端仍能读兼容镜像。

### 2.4 租约与旧客户端、时钟、暂停的语义不成立

**问题**：
- 旧客户端只把锁当“存在”，`create` 失败即 `locked`（`engine.ts:121`）；它不会看 `expiresAt`，过期锁对它永远有效，只能人工解锁。旧客户端的 `recoverLock` 只读 `startedAt`（`connection.ts:50-62`），用户可能在一个新客户端的**活跃租约**上点“解锁”，删掉正在运行的锁。
- 若新客户端把“没有 expiresAt”当成过期，就会偷走**正在运行的旧客户端**的锁。必须规定：**缺省 = 永不过期，绝不自动接管**；否则混合舰队会 split-brain。
- 心跳必须能安全续租：`ownLock` 目前比较原始字节（`engine.ts:122-129`），心跳更新 `expiresAt` 后字节变化会被自己判成 `lockLost`；必须改为比较 owner id（并保留 startedAt），且续租用条件写或“读-比-写”+ 失败即中止。
- 条件写的可移植性：AWS S3 自 2024-11 支持 `PutObject If-Match`，R2 明确支持，MinIO 支持但有 read-quorum bug；WebDAV 规范有 `If-Match`，但实现差异大，现有代码自己就写了“conditional PUT is not portable across DAV servers”（`transport.ts:168-170`）；部分 S3 兼容（如 DigitalOcean Spaces）对 `If-Match` 直接 412。不能把租约/接管建立在“所有 S3-compatible 都支持 CAS”上。
- 时钟：`owner.startedAt` 用的是本地 `new Date()`（`engine.ts:114-117`），不是 `store.now()`。设备时钟偏快会把别人的锁看成过期；`store.now()` 只从响应的 `Date` 头校准（`transport.ts:89-90`），没有 `Date` 时退回 `Date.now()`。租约决策必须只用服务端时间；拿不到服务端时间就不要自动接管。
- 长上传/暂停：单个请求总超时 60s（`C:\Project\Textus\src-tauri\src\plugins\http.rs:76`），2MB 块在慢网/移动网可能超时；手机后台会冻结计时器，恢复时租约已过期。恢复后必须在**任何写之前**重读锁并确认 owner；`ownLock` 会抛 `lockLost`，但已经写出的 snapshot、已经应用的下载会留下副作用。
- 接管后重新计划：`synchronize` 的顺序是 lock → head → scan → plan（`engine.ts:121-210`），所以 head 是新的，计划本身正确；但 base 仍是旧的。如果上一次运行已经应用了下载、还没保存 base，而 head 在接管后又变了，下一次运行会把“已下载内容”误判为本地编辑，生成冲突副本。需要在 base/日志里记录“本次运行已下载的 hash”，或在接管时把与旧 head 匹配的本地内容视为已同步。

**建议方向**：租约作为**可选的优化**，按 provider 探测开启；无 CAS/服务端时间的 provider 保持“锁 + 人工解锁”。租约字段全部可选，缺省永不过期；心跳只更新 `expiresAt` 并比较 owner id；接管前必须重读 head/history；任何续租失败立即在发布前中止；为“已应用下载但未保存 base”增加运行日志。

**需要什么测试**：假 DAV 不支持 `If-Match`、假 S3 返回 412/400；两个客户端一个带租约一个模拟旧锁；设备时钟 +1h/-1h；租约中途暂停 2× lease 后恢复；断言不会双发布、不会删掉活跃锁、不会把下载误当编辑。

### 2.5 三方合并：base 文本现在没有可靠来源

**问题**：`Base` 只有 `Record<path, hash>`（`model.ts:113-119`；`content.ts:93-110`），`history` 的 `current` 只有 origin（`model.ts:99-112`），版本只在“被替换/删除”后进入 `versions`。因此取 base 文本只能：
- 去 `history.versions` 找 hash 相同的 Entry，再下载块；但 `thin` 会按小时/天桶、每路径最多 200 条、`fit` 按 8MB 裁掉最旧版本（`history.ts:108-158`）。如果本设备离线期间远端在 1 小时内改了多次，base 版本可能已被桶淘汰；如果 `fit` 触顶，base 也可能被裁掉；如果 head 被删后重建（`history.test.ts` 的 “starts again when the head is gone” 场景），history 可能来自旧仓库；崩溃/旧客户端写入还可能让 `previous` 链断裂。**这些都不是异常，是正常保留策略。**
- 用当前本地文件当 base 是错的：当前文件就是“本地改动后的内容”。

所以“文本三方合并”不能只改 planner；必须新增本地 base 内容存储。可行方案：每次成功同步后，把“与 head 相同的文本内容”按 hash 存到本地内容缓存（压缩、按 keepDays/容量上限淘汰）；合并时 base = 缓存里的 hash 内容。缓存缺失时**退化为冲突副本**，绝不猜。这个缓存是本地数据，不进入远端 v1 格式，兼容性最好。

其他边界：
- **front matter/YAML**：行级合并可能产出重复 key、破坏 YAML；建议把开头 `---...---` 当作一个不可分行合并的块：双方都改 front matter 就冲突副本，只有正文可行级合并。
- **Obsidian settings**：planner 已经是“远端赢”（`planner.ts:52-55`），合并必须显式排除 `isObsidianSetting`（`config.ts:171-173`）；注意空 base 首同步时这些文件是**静默远端覆盖**，连冲突副本都没有（`engine.test.ts:120-131` 验证了这一点），迁移时本地 Obsidian 设置会丢。
- **文件类型**：`isText` 包含 `.md/.markdown/.mdown/.mkd/.txt/.csv/.base/.canvas/.svg`（`config.ts:154-159`）。`canvas`/`base` 是 JSON，`svg` 是 XML，`csv` 是表格，行级合并都可能破坏结构；合并应只对 Markdown/纯文本白名单开放，其余冲突副本。
- **编码/BOM/CRLF**：`local.apply` 对文本用 `TextDecoder("utf-8",{fatal:true,ignoreBOM:true})`（`local.ts:239-257`），非 UTF-8 文本会抛错并中止整次同步；BOM 被保留为 `\uFEFF`，合并结果若丢掉/重复 BOM 会造成整文件差异；CRLF 若合并库归一化为 LF，会重写整个文件。必须检测并保持原换行风格/BOM；无法解码就冲突副本。
- **NFC/NFD**：路径在以 `normalize("NFC")` 折叠后做冲突检测（`content.ts:71-76`、`engine.ts:218-223`），但实际 key 仍是原字符串；macOS NFD 文件名与 Windows NFC 同名会被判 `caseCollision` 并中止整次同步，而不是合并/重命名。
- **合并结果再次冲突**：合并写入本地后若发布前 head 又变（旧客户端/CAS 失败），必须拿新 head 重新合并；不能把旧合并结果当 base 发布，否则会用“基于旧 base 的合并”覆盖新改动。
- **与旧客户端并发**：旧客户端永远生成冲突副本；新客户端合并成功后，旧客户端可能又生成一个内容相同的冲突副本，产生冗余文件。合并应保持确定性，并在合并结果与某侧完全相同时直接采用该侧，避免多余副本。

**需要什么测试**：base 版本被 `thin`/`fit` 淘汰后合并退化；YAML front matter 双方修改；CRLF/BOM/非 UTF-8；NFC/NFD 同名；合并期间 head 变化；与模拟旧客户端并发；合并结果等于 local/remote 时不多传。

### 2.6 head ETag 快进：单独用 304 会漏掉 history/keep/外部写

**问题**：
- `ObjectStore` 没有 ETag/条件 GET（`model.ts:120-130`），`RemoteStore.get` 只返回 bytes 或 null（`transport.ts:144-149`）。要做“304 快进”必须先扩接口，并让 `EncryptedStore` 映射物理对象的 ETag（`encrypted-store.ts:41-56`）。加密 head 每次 `seal` 的 IV 随机，物理 ETag 会随每次发布变化；它只能当“有没有发布”的指示器，不能当明文内容指纹。
- **head 不变 ≠ history 不变**：`publish` 先写 history，再写 head（`publish.ts:92-96`）。如果进程在两者之间被杀，history 已经变了（`history.head` 指向新 revision，`previous` 指向当前 head），head ETag 却不变。此时若用 304 跳过 history 读取，下一次发布基于旧 history 克隆，就可能把新 keep、被裁掉的版本、甚至 skipped 的旧客户端改动全部回退，或者让 `clean` 基于旧视图删块。
- **keep 变更**：当前 keep 变更会触发新 head（`publish.ts:68-83`），所以正常情况下 head ETag 会变；但崩溃窗口里 history.keep 可能已经变了而 head 没变，`onKeep` 也没被调用，UI 会显示旧设置。快进不能跳过“读 history 并核对 keep”。
- **远端被旧客户端改写**：旧客户端写 head 会改变内容，S3/R2 的强 ETag 会变；但 DAV 可能返回弱 ETag、每次请求都变的 ETag，或者根本没有 ETag。没有强 ETag 时必须退回读 revision。
- **本地索引脏标记**：`described` 只是内存缓存，靠 size + mtime + 2s 的 racy 检查（`local.ts:16-22, 112-146`）。持久化后同样会漏：mtime 粒度粗（FAT/SMB）、同大小同 mtime 的替换（`git checkout` 后 `touch -r`、某些同步工具）、Android content:// 无 mtime、应用崩溃/时钟回拨。事件也不可靠（应用未运行、外部写入、移动端无 watcher）。脏标记不能只靠事件；需要“写前 journal + 启动/崩溃后全量校验 + 歧义时重算 hash + 每次远端 revision 变化时重扫受影响文件”。

**建议方向**：把 `head.revision` 当作逻辑 ETag 持久化；304 只作为“省一次 body”的优化，不能作为“可以跳过 history/keep/清理”的依据。任何 publish 前必须重新读 head + history，并验证 `history.head === head.revision`（或可识别的崩溃状态）。本地索引写入与 base 保存放在同一个事务/日志里；对“元数据不可信”的文件一律重算 hash。

**需要什么测试**：假 DAV 返回弱/无 ETag；head 304 但 history 已变（模拟崩溃）；旧客户端改写 head；keep 只在 history 里变；同 size+mtime 改内容；Android 无 mtime；崩溃后索引/journal 恢复。

### 2.7 从插件迁移到内置：空 base 首同步可能永远发布不了

**问题**：
- 空 base + 已有远端时，双方都存在的不同文件全部走 `conflict`（`planner.ts:35-56`），`keepRemote` 生成 `Sync conflicts/...`（`planner.ts:82-87`）。这不是“几个副本”，而是“交集里每个不同文件一个副本”。冲突副本本身是文件，计入 `MAX_FILES=20000`（`model.ts:8`；`content.ts:69-77`）和 8MB 清单；例如 12k 个不同文件 → 冲突后 24k 文件，`publish` 在 `document.length > MAX_MANIFEST_SIZE` 或 `parseManifest` 处抛 `tooManyFiles`（`publish.ts:88-90`），而且本地已经写入了冲突副本，下一次重试仍然超限，**永久卡死**。
- `.obsidian` 的设置不生成冲突副本，而是**远端覆盖本地**（`planner.ts:52-55`；`engine.test.ts:120-131`），本地修改静默丢失。
- 插件 base 的实际键是 `encrypted-base:<sha256(root + identity(config) + "\n" + account)>`（`C:\Project\textus-plugins\development\cloud-sync\src\settings.ts:160-163`），`identity` 的定义是 `[transport, endpoint, bucket, region, pathStyle, prefix]`（`config.ts:142-151`）。内置实现必须逐字复刻 endpoint 归一化、DAV 清空 region/bucket、pathStyle 默认值等，否则算不出同一个键，导入失败且用户看不到原因。
- 插件 base 在 `ctx.storage.global` 的 `kv/` 下（`C:\Project\Textus\src-tauri\src\plugins\store.rs:28-55`，全局目录是 `<config>/textus/plugins/<id>/kv/`；`store.rs:40-42`），配额只有 50MB（`store.rs:12`）。凭据在 `<config>/plugin_secrets.json`（`C:\Project\Textus\src-tauri\src\plugins\files.rs:145-163`），里面同时有 S3 secret/sessionToken 和 E2E 同步密码；导入等于再存一份明文来源的机密。
- 加密仓库还有 `vault:<baseKey>` 的指纹 pin（`C:\Project\textus-plugins\development\cloud-sync\src\host.ts:174-188`），不导入它，内置客户端可能在换了仓库（同前缀、同密码、不同 salt）时静默接受。
- 插件被卸载时，全局存储会被移到系统 Trash（mobile 上 `to_trash` 是永久删除，`C:\Project\Textus\src-tauri\src\atomic.rs:379-395`；`store.rs:69-80`），secrets 被删除（`files.rs:223-229`；`install.rs:406-411`）。**必须先迁移再卸载**，否则 base 和凭据都没了。
- 插件 README 明确说官方 ID 不读别的插件私有设置/secrets（`C:\Project\textus-plugins\development\cloud-sync\README.md:44-45`）。迁移是例外，必须是用户触发的、一次性的、只针对 `catvinci.cloud-sync` 的流程，不能做成通用扫描。
- 插件和内置同时跑：两个自动同步循环，各自 base 不同，锁只保证串行不保证一致；应检测插件仍启用并阻止内置启动，或给出一键停用。

**建议方向**：
- 迁移前做 **dry-run**：只读 head/history/local，统计“双方不同”“仅本地”“仅远端”“Obsidian 设置”的数量，并估算冲突后文件数/清单大小；超过 `MAX_FILES`/8MB 时不允许“空 base + 冲突副本”方案，必须让用户选择“远端优先/本地优先/逐文件”，或导入插件 base。
- 导入 base 优先于凭空首同步；凭据建议重新输入（或一次性显式同意后加密导入），不要在日志里出现 secret；导入 pin 和 device 名；卸载/停用插件放在迁移成功之后。
- 内置实现必须兼容插件的加密信封（TCS2 magic、AES-GCM AAD `context\nkey`、HMAC 名字派生、PBKDF2 600k、salt/repositoryId 派生），否则不能读插件已加密的远端；这比“格式 textus-cloud-sync/1”更难，建议复用同一份加密测试向量。

**需要什么测试**：用真实插件存储/secret 夹具导入 base（含 parked、加密 pin）；20k 文件边界的 dry-run；冲突副本预检；插件未卸载时内置拒绝启动；加密仓库导入后能读历史；插件卸载顺序。

### 2.8 GC 与接管的明确漏洞

**问题**：
- **legacy trash 的块不回收**：`next.trash` 按 30 天过滤（`engine.ts:161-163`）并 `slice(-MAX_TRASH)`（`engine.ts:397`），但 `clean` 的候选只有 `dropped`（thin/fit 掉的版本）和 `before.previous` 的快照（`publish.ts:115-122`）；被过滤/截断的 trash entry 没有进入候选，`unusedBlocks` 虽然把 `next.trash` 算作“仍使用”（`history.ts:177-180`），但已经不在 `next.trash` 里的 entry 的块永远不会被删。pre-0.5 客户端留下的 trash 块会永久占空间。
- **孤儿快照**：`publish` 在写 history/head 之前就写 snapshot（`publish.ts:92-93`），崩溃会留下无人引用的 revision；`skipped` 读取的 `snapshotKey(before.head)` 也不会被删除（`publish.ts:57-66, 116-126`）。`ObjectStore` 没有 LIST（`model.ts:120-130`），新代码无法枚举这些键；只能靠“写快照前先在本地 journal 记录 revision”或让快照键可从当前 head/previous 推导。
- **pending marker**：`begin()` 用随机 UUID 创建 `v1/pending/<uuid>.json`（`pending.ts:77-82`），`done()` 删除；崩溃且 revision 已变时 `resume` 丢弃 pending（`pending.ts:46-59`），但 marker 永远留着。同样没有 LIST 无法扫。
- **`ownLock` → `remove(LOCK)` 非原子**：`engine.ts:422-427` 先读锁确认字节，再删除；中间若用户手动 unlock + 另一设备创建新锁，会把别人的锁删掉。`recoverLock` 也是“读两次 + 删”（`connection.ts:63-71`），中间窗口可删活跃锁。
- **clean 的 ownLock 检查间隔 50**：`publish.ts:124-130` 每 50 次删除才查一次锁。租约过期被接管后，原客户端若在第一次检查前已通过，可能删除新 head 正在使用的块（块按内容寻址，新 head 的文件块可能与旧客户端正丢弃的版本块相同）。这是低概率但真实的数据损坏路径。
- **上传时信任 `known`**：`engine.ts:188-198` 把远端所有块标记为“已存在”，上传时不再 `has/get`（`engine.ts:77-109`）。若远端块因 GC 竞争/手工删除而缺失，上传会发布引用缺失块的清单，之后所有设备的下载都 `integrityError`；当前没有修复路径（`download` 只抛错，`putBlock` 发现损坏也只抛错）。
- **旧客户端并发**：锁正常情况下串行；但手动解锁或租约接管后，旧客户端可能继续上传/发布。上传是内容寻址的，通常无害；发布是危险的（见 2.3）；clean 可能删块。需要“GC 宽限期/两阶段删除”：第一次只标记候选，隔一个周期或一个 head 才真正删除；或者在删除每个块前做一次条件锁校验。

**建议方向**：把 GC 改成 mark-and-sweep + 年龄阈值（例如块创建/最后引用时间超过 N 天，且连续两次 sweep 未引用才删）；候选集显式加入被淘汰的 trash entries；快照/pending 用可推导的键或本地 journal 以便清理；`ownLock` 用 owner id 比较并尽可能条件写；上传前对“新文件中引用的 known 块”做抽样/首次校验，下载失败时提供“从本地重传修复”的路径。

**需要什么测试**：淘汰 legacy trash 后块被回收；孤儿快照/pending 被清理；接管后原客户端 clean 不删新 head 的块；删除块前锁检查；已知块缺失时上传不发布悬空引用；下载遇到损坏块可修复或给出可操作错误。

### 2.9 移动端删除/App trash 的语义与可行性

**问题**：
- 远程删除到达时，`deleteLocal` 调 `local.remove`（`engine.ts:318-324`），桌面进系统 Trash，移动端没有 Trash（`atomic.rs:400-416`；content:// 直接抛错 `content-plugin-fs.ts:139-141`）。这意味着“移动端可移植删除”不是换一个函数，而是要新增宿主能力。
- 如果 App trash 放在 vault 内的 `.textus/trash`：在 Android content:// 下 `.textus` 对插件不可达（SAF listing 过滤隐藏名，见 2.1），`contentPluginFs` 无法创建/读取；放在非隐藏目录又会被 `inScope` 当成普通文件同步，或被其他设备/旧客户端看到并上传。
- 如果 App trash 放在 App 自己的容器：复制字节 + 删除源；大附件复制成本高，插件 `ctx.storage.global` 只有 50MB 配额（`store.rs:12`），不能当 trash。需要新增宿主级“每 vault 的 trash 目录 + 配额/保留策略”。
- 时序：`local.remove` 先 `holds(expected)` 再 `api.files.trash`（`local.ts:192-201`），中间用户保存了新内容；系统 Trash 会保存新内容，App trash 若“复制旧字节再删源”会丢新内容。实现必须是“移动/重命名”而不是“复制后删”，或移动后校验内容。
- 与“编辑赢过删除”的交互：远端删除 + 本地编辑 → planner 选择 `upload`（`planner.ts:44-49`），文件复活，删除被撤销；如果本地文件已在 App trash，复活的是本地路径，trash 里还留一份旧副本，恢复时可能覆盖新内容（`history-host.ts:49-68` 的 restore 在“本地等于 head”时会原地覆盖）。
- legacy `trash` 数组：pre-0.5 客户端用它展示可恢复删除；新客户端只过滤/截断，不再追加。`slice(-MAX_TRASH)` 默认“后写的在后”，若旧客户端是前插，会保留最旧的一批（`engine.ts:397`）。删除的 trash entry 块也不回收（2.8）。
- 误删恢复：移动端用户在系统/Textus 树里删除文件，宿主是永久删除（`C:\Project\Textus\src\platform\ipc-files.ts:86-89`；`capabilities.ts:83` 注释“phone has none”），只能靠远端 history 恢复；若删除尚未同步就卸载/清数据，远端还在（不丢），但若已经发布删除且 history 已淘汰，内容就没了。

**建议方向**：把 App trash 定义为宿主 API（每 vault、App 数据目录、配额、保留天数、原子 move），而不是插件自己拼目录；移动端 content:// 只支持“App 数据目录 trash + 删除源”，并在 UI 上明确“本设备可恢复，其他设备靠历史”；trash 清理单独保留策略；恢复前比较远端当前版本，避免用旧 trash 覆盖新内容。

**需要什么测试**：content:// 下远程删除后本地可恢复；App trash 清理；删除与保存竞态；编辑赢删除后 trash 陈旧副本的恢复行为；legacy trash 顺序/回收；移动端永久删除后 history 恢复。

### 2.10 上传校验优化：MD5 不可用、S3 已自带 payload 校验、DAV 无服务端哈希

**问题**：
- 当前 `putBlock` 是 `has()` → `put()` → `get()` + SHA-256 校验（`engine.ts:102-109`），每个块 3 个请求，GET 还回传整个 2MB；移动网络上代价高。
- `Content-MD5` 需要 MD5，而插件只用 WebCrypto（`crypto.subtle`，见 `content.ts:14-15`），WebCrypto 不提供 MD5；要么自带 MD5 实现，要么改用 `x-amz-checksum-sha256`。
- S3 的 SigV4 已经签了 `x-amz-content-sha256`（`transport.ts:61-75`），S3 会校验请求体，传输完整性本身有保障；`Content-MD5` 只是第二道，且不证明“落盘后被篡改”。`x-amz-checksum-sha256` 会存到对象上并在 HEAD/GET 返回，可以避免 GET body，但 AWS/R2/MinIO/其他 S3 兼容的支持面要逐个探测。
- WebDAV 没有通用服务端哈希；Nextcloud/ownCloud 有 `OC-Checksum`，但不能假设。读回是唯一通用校验，但成本最高。
- 失败重试：内容寻址的 PUT 幂等；但 `create` 的 DAV 临时文件 + MOVE（`transport.ts:160-187`）不是幂等的——MOVE 已成功但响应丢失时，客户端会以为失败；锁场景下会留下“locked”，需要人工 unlock。`request` 只在 429/502/503/504 重试，且只对 GET/HEAD/PUT（`transport.ts:91-96`）；网络异常直接抛 `networkError`，不重试。
- 单请求 60s 总超时（`http.rs:76`），慢网 2MB 块可能被中断；重试策略要区分“可安全重试的幂等请求”和 MOVE。

**建议方向**：按 provider 做能力探测并记录：S3 用 `x-amz-checksum-sha256`（或至少 `x-amz-content-sha256` 已够传输校验），跳过 GET 读回；DAV 保留读回或提供“快速/严格”选项；`has()` 对已存在块可省略（PUT 幂等覆盖相同内容），但要保留“块损坏修复”：GET 校验失败时用本地内容重 PUT 一次。MOVE 失败后先读目标，若内容/owner 是自己则视为成功。

**需要什么测试**：假 S3 返回错误 checksum / 400；假 DAV 无哈希；MOVE 已生效但响应丢失；429/500/408/网络超时；块损坏后重传修复；移动端流量/请求数统计。

### 2.11 v1 可加什么、v2 为什么是硬切

**问题（A/D 的展开）**：
- 可安全加的：head 顶层可选字段（旧客户端 spread 保留，`engine.ts:158-164`）、history 顶层可选字段（`structuredClone`/`{...history}` 保留）、trash entry 的额外字段（`parseManifest` 忽略）、lock 的额外字段（旧客户端只比较自己的字节）、**新的远端键**（旧客户端不读；但加密模式必须给 `EncryptedStore.physical` 加映射，`encrypted-store.ts:41-56`，否则新键会 `invalidPath`）。
- 不可安全加的：`format` 新值（`content.ts:60-62`；`history.ts:46-48`；`encryption.ts:41-58`）、`inScope` 之外的新路径/扩展名（`content.ts:72-76` 会整份拒绝）、`KEEP_DAYS` 新枚举（`history.ts:54-56`）、>2MB 或 >64 块的 Entry（2.2）、新的加密格式/KDF 迭代（`encryption.ts:4-5, 47-49`）。
- entry 级字段不持久：旧客户端上传时 `next.files[path] = l`，`l` 来自 `describe()`，只有 `{hash,size,blocks}`（`engine.ts:387-389`；`content.ts:20-28`）；旧客户端裁剪冲突副本时也一样。任何“新客户端依赖的 per-file 元数据”都不能只放在 Entry 里。
- history 的 `current` 在内容变化时被重建为 `{at, device}`（`history.ts:90-94`），per-path 元数据会丢；`versions` 会 spread 旧 Entry，能保留额外字段（`history.ts:97-101`），但旧客户端新建的 version 没有。
- 本地 `Base` 的未知字段会被旧插件丢掉：`engine.ts:174-186` 重建 `{format, files[, parked]}`；因此内置在 base 里加的 `repositoryId`/缓存索引，只要用户又跑一次旧插件就会消失。迁移必须是单向的，并检测插件是否仍在运行。
- **v2 放宽文件范围/升级加密不是渐进兼容**：旧客户端对 `format`、路径 `inScope`、加密格式都是全量严格校验；任何一条不满足就是整份 remote 不可读。v2 必须是显式硬切（新 format/新键空间/双写兼容镜像），并给旧客户端一个清晰的“请升级”错误，而不是让它看起来还能同步。

**repositoryId 的具体问题**：
- 加密 metadata 已经有 `repositoryId`（`encryption.ts:10-18, 169-183`），且参与指纹；在 manifest 顶层再加一个是冗余的，但可读；不要加到加密 descriptor 里（`parseEncryptionMetadata` 会 canonical 化，见 `encryption.ts:37-60`，加字段可能影响 pin 计算）。
- 它不是可信身份：可以被复制、备份恢复、手工改写；不能据此静默复用 base 或认定“同一仓库”。
- `baseKey` 含 `root`（`settings.ts:160-163`），vault 移动后 base/pin 全丢；要支持移动，应把 base 键改成 `identity + repositoryId + 本设备实例 id`，但“同一 vault 的副本”会共享 base（危险），需要一个随 vault 移动但不随复制共享的实例标识（或明确要求用户手动“关联到已有仓库”）。
- `baseKey` 还含 `account`（access key id）：换 IAM 用户/轮换 access key 会丢 base，导致一次大规模首同步/冲突。这是运维上的高频操作，建议 base 键不要含账号，账号只用于凭据查找。

**需要什么测试**：冻结旧客户端 `parseManifest`/`parseHistory`/`publish` 逻辑，喂入带新字段的 head/history，断言：顶层字段保留、entry 级字段被丢弃、format/scope/keep 违反时整份拒绝；加密 descriptor 加字段后 pin 仍稳定；base 加字段后旧插件重写会把字段丢掉。

### 2.12 单文件错误会拖垮整次同步；符号链接/编码/大小写/NFC 的边界

**问题**：
- 引擎是“任何异常即中止整次同步”：`local.scan` 遇到目录、>128MB、不可读、深路径 >48 层直接抛（`local.ts:61-69, 149-150`）；`apply` 遇到非 UTF-8 文本会抛（`local.ts:239-262`）；`parseManifest`/`parseHistory` 遇一份坏对象整份拒绝。结果是**一个符号链接、一个 GBK 文本、一个大小写孪生文件**就能让整个 vault 永远不同步。
- 符号链接：`plugin_fs_stat` 用 `fs::metadata`（跟随链接，`C:\Project\Textus\src-tauri\src\plugins\files.rs:16-31`），`plugin_fs_list` 用 `DirEntry::metadata`（不跟随）；两者不一致会导致“列表说是文件、stat 说是目录”或反之，`readRaw` 抛 `pathIsDirectory`（`local.ts:64`）。链接指向 vault 外时 `inside` 会拒绝（`C:\Project\Textus\src-tauri\src\plugins\access\paths.rs:137-167`），也会让同步失败；链接指向内时 `atomic::existing_target` 会写穿链接（`atomic.rs:46-59`），下载实际改的是目标文件，另一端看到的是普通文件。没有明确的“跳过符号链接/不同步链接”策略。
- 大小写/NFC：`caseCollision` 是整次中止（`engine.ts:212-223`），而 `names` 包含**本地不同步的远端文件**（`engine.ts:212-217`），一个被排除的远端孪生文件也能让同步失败。NFC/NFD 同名在 macOS/Linux 上很常见，当前会直接卡死。
- `.textus/agent.md`、`.textus/style.md`、`.textus/style.previous.md` 在 `scan` 里被无条件加入（`local.ts:169-173`），不检查 `scope.wants`；而 engine 的 plan 用的是**未过滤的 `files`**（`engine.ts:210`），所以用户的 exclude/`.gitignore` 对这三个文件无效，甚至可能生成冲突副本/覆盖排除规则。
- 冲突副本路径没有检查 `inScope`/排除规则：`.obsidian` 的冲突副本会落在 `Sync conflicts/.obsidian/...`，`inScope` 因 `.obsidian` 部分返回 false，`local.apply` 会抛 `invalidPath`（`planner.ts:82-87`；`config.ts:174-189`）。概率低，但属于“一个文件毁一次同步”。
- 空目录不同步，删除所有文件后远端/本地空目录残留；不是数据错误，但与用户预期不符。

**建议方向**：把“文件级错误”降级为 per-path 的 `deferred`/`problem` 列表，继续同步其他文件；扫描时显式识别并跳过符号链接（Rust `FsEntry` 增加 `is_symlink`）；文本应用失败时冲突副本/跳过而不是抛全局；大小写/NFC 冲突改成“确定性重命名或冲突副本”，至少不要中止全部；排除规则应用于所有扫描入口和冲突副本；修正 `.textus` 三个文件的 `wants` 检查。

**需要什么测试**：符号链接（文件/目录/指向内外）；GBK/UTF-16 文本；大小写孪生；NFC/NFD 同名；>128MB；48 层以上路径；排除 `.textus/agent.md`；`.obsidian` 冲突副本；一个坏文件不影响其他文件。

### 2.13 传输/限额/WebDAV 服务端差异

**问题**：
- 重试只覆盖 429/502/503/504，且只对 GET/HEAD/PUT（`transport.ts:91-96`）；S3 的 500 InternalError、408 不重试；429 的 `Retry-After > 5s` 直接失败（`transport.ts:98-99`），对坚果云这类限流服务是“同步失败”而不是“等待”。
- MOVE 不可重试（`transport.ts:160-187`）；响应丢失会留下锁/临时文件，后续显示 `locked`，只能人工解锁。
- S3 区域错误通常返回 301 + `x-amz-bucket-region`；reqwest 跟随重定向后签名 host 不匹配，用户看到的是签名/HTTP 错误，而不是“区域填错了”。S3 兼容服务（R2/MinIO/Spaces）对 `If-Match`、`If-None-Match`、`x-amz-checksum-*`、HEAD 行为差异大。
- WebDAV：`parents()` 对每个 PUT 都 MKCOL+PROPFIND（`transport.ts:111-126`），而 `RemoteStore` 每次同步新建（`host.ts:163`），`dirs` 缓存不跨 run；块目录有 256 个前缀，一次同步可能产生数百个 MKCOL/PROPFIND，坚果云会限流。`has()` 用 HEAD（`transport.ts:150-155`），部分 DAV 对缺失资源返回 403 而不是 404，会被当作权限错误。
- 60s 总超时（`http.rs:76`）+ 32MB 响应上限（`http.rs:16`）；单块 2MB 没问题，但慢网/移动网下 2MB 也可能超时；`net.fetch` 不接受 AbortSignal（`types/textus.d.ts:1215-1229`），用户取消只能在请求之间生效。
- 限额：`MAX_FILE_SIZE=128MB`、`MAX_FILES=20000`、`MAX_MANIFEST_SIZE/MAX_HISTORY_SIZE=8MB`（`model.ts:4-12`）。`history.fit` 只裁 `versions`，不裁 `current`（`history.ts:138-158`）；如果 20k 个长路径的 `current` 本身超过 8MB，`fit` 会一直抛 `tooManyFiles`，每次发布都失败。128MB 文件下载会整块分配（`engine.ts:56`），移动端可能 OOM；`TRANSFER_BYTES=32MB` 的“one always fits”让单文件独占内存。
- 加密每次同步都重新 PBKDF2 600k（`encryption.ts:5, 68-88`；`host.ts:180-187`），移动端每次自动同步都有秒级 CPU/耗电；`EncryptedStore.get(HEAD)` 还会额外读 descriptor 并校验（`encrypted-store.ts:32-40`）。

**建议方向**：补 500/408/网络超时的有限重试（幂等请求），429 长 `Retry-After` 改为等待/暂停而不是失败；MOVE 失败后读目标确认；S3 301 读取 `x-amz-bucket-region` 并给出可操作错误；WebDAV 持久化“已创建目录”集合，减少 MKCOL/PROPFIND；`parents` 只对 v1/blocks 的前缀做一次；提供 `AbortSignal`/cancelId；`history.fit` 同时约束 `current` 或给出明确错误；移动端流式读写/降低单文件上限；加密密钥在单次会话内缓存（不落盘）。

**需要什么测试**：假服务端返回 500/408/429+Retry-After/301/403 HEAD/MOVE 响应丢失；WebDAV 计数 MKCOL；20k 长路径 `current` 超 8MB；128MB 文件移动端内存；加密同步的 PBKDF2 耗时。

## 2. 错误假设 / 需要拍板的点

### 3.1 方案里的错误假设

1. **“旧客户端会忽略任何新字段”**：只对顶层 head/history 字段成立；Entry 级字段会被旧客户端上传时丢掉；`format`、`inScope` 路径、`KEEP_DAYS`、块大小/块数是全量严格校验，违反会整份拒绝。
2. **“CDC 只要每块 ≤2MB”**：还必须 ≤64 块/文件，且清单/历史 ≤8MB；1MB 下限会让 >64MB 文件（及其历史版本）被旧客户端整体拒绝。
3. **“head CAS 能保证一次提交”**：history 是先写的另一个对象；CAS 只保护 head，会造出 `head` 与 `history.head` 不一致。要么 per-revision commit，要么 history 也条件写，要么只做读侧一致性校验（仍不能防覆盖）。
4. **“WebDAV/S3 兼容层都支持 If-Match/304”**：现有代码自己就写了 DAV 条件 PUT 不可移植；AWS S3 2024-11 才支持 `If-Match`，R2/MinIO 支持但实现有差异，部分 S3 兼容直接 412。
5. **“旧客户端会尊重租约”**：不会。旧客户端只看锁是否存在，过期锁对它永远有效；人工 unlock 还可能删掉活跃租约。
6. **“base 文本可以从 history 取”**：history 会被 thin/fit/上限/崩溃/重建清掉；正常保留策略就会淘汰 base。
7. **“移动端只是缺一个 trash API”**：还缺 content:// 路径拼接、隐藏文件访问、二进制写、mtime、打开文件重载；SAF 下 `.textus` 隐藏目录不可达。
8. **“repositoryId 可以安全用于 vault 移动”**：base 键含 root，移动会丢；它也不是可信身份，复制/备份会共享；旧插件重建 Base 会丢掉新元数据。
9. **“空 base 首同步只是多几个冲突副本”**：冲突副本计入 20k 文件/8MB 清单，可能让发布永久失败；`.obsidian` 还会静默远端覆盖本地。
10. **“插件里可以做 SQLite 持久索引”**：插件存储是 50MB 配额、`kv/` 一键一 JSON、`writeText` 只有文本（`store.rs:12, 28-55, 145-175`）；SQLite 应属于 Rust 内置服务，不是插件阶段。
11. **“v2 可以渐进放宽文件范围/升级加密”**：旧客户端对 format/scope/加密格式是全量严格校验；v2 必须是硬切 + 双写兼容镜像或明确的“请升级”。
12. **“S3 的 Content-MD5 足够且通用”**：WebCrypto 没有 MD5；S3 SigV4 已经校验 payload；DAV 没有通用服务端哈希。
13. **“本地 mtime 索引可靠”**：content:// 无 mtime、FAT/SMB 粒度粗、同 size+mtime 替换、应用未运行/无 watcher；脏标记不能只靠事件。
14. **“插件和内置可以并存/先装内置再卸插件”**：两个同步循环会打架；卸载会删插件 base/secrets（mobile 上是永久删除，`atomic.rs:379-395`），顺序必须反过来。

### 3.2 需要拍板的点

1. **旧客户端支持期限**：v1 必须无限期可读，还是可以要求最低插件版本？这决定 CDC 块数、v2 文件范围、keep 枚举、加密升级能否做。
2. **租约/CAS 策略**：是否只在探测到 CAS 的服务上自动接管；WebDAV/坚果云是否接受“永久锁 + 人工解锁”？
3. **三方合并的产品语义**：默认开还是可选？只对 Markdown 正文？front matter 双方都改是否一律冲突副本？Obsidian 设置是否继续“远端静默赢”？
4. **移动端文件访问**：先要求 Android“所有文件访问”（plain path），还是投入补 content:// 的隐藏文件/二进制/trash/mtime/重载？iOS 是否先上、Android 后上？
5. **App trash**：放 App 数据目录还是 vault 内？配额/保留天数/大附件怎么处理？是否只对本设备可见、跨设备恢复只靠 history？
6. **凭据迁移**：自动导入还是重新输入？导入后是否删除插件 secrets？是否接受“读取另一个插件私有 secrets”的一次性例外？
7. **仓库身份**：repositoryId 不一致时拒绝还是询问？缺失时是否采纳？base 键是否去掉 root/account？vault 副本如何避免共享 base？
8. **限额**：保持 128MB/20k/8MB，还是 v2 提高？超限是跳过一个文件并提示，还是整次失败？
9. **加密 v2**：是否支持改密码/重加密？旧客户端如何被明确挡住？是否需要停机/单写者模式？
10. **HTTP 端点**：是否允许局域网 `http://` 的 WebDAV/MinIO？当前 `normalizeConfig` 只接受 https（`C:\Project\textus-plugins\development\cloud-sync\src\config.ts:89-96`），很多 NAS 用例会被挡。
11. **keepDays 枚举**：是否允许新增值（旧 `parseHistory` 会整份拒绝）？
12. **插件/内置切换**：内置是否检测插件并强制停用？迁移是否单向、是否保留回滚？

> 外部事实核对（条件写）：AWS S3 自 2024-11-25 起支持 `PutObject If-Match`；R2 文档明确支持 `If-Match`/`If-None-Match`；MinIO 支持但存在 read-quorum 相关已知问题；WebDAV 规范支持但实现差异大。参考：[AWS conditional writes](https://www.amazonaws.cn/en/new/2024/amazon-s3-adds-new-functionality-for-conditional-writes/)、[Cloudflare R2 conditional operations](https://developers.cloudflare.com/r2/api/s3/conditional-operations/)、[MinIO conditional writes](https://www.min.io/blog/leading-the-way-minios-conditional-write-feature-for-modern-data-workloads)。

## 3. 建议纳入设计文档的协议章节清单

1. 仓库标识与版本协商（format、revision、repositoryId、deviceId、v1/v2 切换）
2. 键空间与目录布局（head/history/snapshots/blocks/pending/commits）
3. 清单与块格式（size、chunk、块数上限、8MB 上限、0 字节/空块）
4. v1 兼容不变量（旧客户端可读的写入约束与禁止项）
5. 锁：租约、心跳、接管、人工解锁、无 CAS 降级
6. 提交协议（snapshot/history/head 原子性、CAS、崩溃恢复、history 一致性）
7. 历史与保留（thin/fit/keep/trash、旧客户端兼容）
8. GC 与孤儿对象（mark-sweep、宽限期、快照/pending/marker 清理）
9. 规划与冲突（base、编辑胜删除、冲突副本、排除规则）
10. 三方合并（base 内容缓存、适用文件类型、front matter、编码/换行/BOM/NFC、失败回退）
11. 传输与校验（provider 能力矩阵、ETag/条件 GET、checksum、重试/幂等、超时/取消）
12. 加密（信封格式、KDF、指纹/pin、密码轮换、v2 迁移）
13. 移动端文件访问（content://、隐藏文件、二进制、mtime、重载、App trash）
14. 本地索引与缓存（dirty journal、mtime 语义、崩溃恢复、容量）
15. 迁移（插件 base/secrets/pin 导入、空 base 首同步策略、插件停用/卸载顺序）
16. 错误码与恢复（401/403/404/409/412/429/507/5xx、MOVE 歧义、可操作提示）
17. 测试矩阵（双设备并发、断点/接管、服务端差异、移动端、限额边界）
