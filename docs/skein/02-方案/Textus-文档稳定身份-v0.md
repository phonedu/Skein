# 文档稳定身份 v0（spike）

> 状态：**已裁（2026-11-21，按 §9 建议全部采纳）；spike 未开工**
> 问题：Textus 以「路径」作文档身份；改名 + 改内容会被三路同步当成「删除 + 新建」，历史留在旧路径；两台设备各改一次名会留下两份。是否引入稳定文档 id，怎么引入？
> 前置：[outl 对照调研](../03-调研/outl-对照与吸收.md) §B2、《同步方案》§4.3/§4.4、《同步协议 v1》
> 性质：一页 spike。先验证，再决定；不碰块身份，不碰 CRDT，不改「md 是唯一真相」。

## 0. 结论先行

**建议：文档 id 用 front matter 里的 `textus_id` 作真值，同步清单里放一个可选的 `Entry.id` 作缓存。**（2026-11-21 用户批准按此执行；Q1–Q8 见 §9。）

- **真值在文件里**：`textus_id` 随文件走，E2EE 自动覆盖，外部编辑器/旧客户端即使不认识它，也只当成一条 front matter 保留。
- **缓存只在清单里**：`Entry.id` 让同步规划在清单里有 id 时**不下载文件**就能配对远端改名/移动；旧客户端重写清单时丢掉它也不丢数据——新客户端从文件 front matter 重建。
- **`.textus/` 旁车不走这条路**：同步的 `in_scope` 只带 `agent.md`、`style.md`、`style.previous.md`、`library/*.md`、`memory/*.md`、`skills/*.md`，放 `.textus/doc-ids.json` 不会跨设备。
- **块身份不在本 spike**：块 id 是另一问题（证据锚点/评论/AI 提案），等具体场景再立项。

这条路线只解决**身份**（rename + edit、跨设备 move、历史跟随），**不解决**两端同时改同一段内容——那仍是三路合并/冲突副本的问题。

## 1. 现状核对（源码事实）

| 事实                                                                                                          | 出处                                              |

| front matter 写入保留注释、顺序、未知键；改动的键原位写，新键追加                                             | `src/utils/frontmatter.ts`、`frontmatter-yaml.ts` |

结论：路径身份不是「没设计」，而是文件级同步、路径历史、文件撤销共同的结果。要加稳定身份，必须同时回答「谁来分配、谁看得见、旧客户端怎么办、E2EE 怎么办」。

## 2. 目标与非目标

**目标**

- G1：单设备「改名 + 改内容」后，新路径仍认作同一文档，历史跟随。
- G2：A 改名、B 改旧路径内容，同步后得到**一条**新路径（内容不丢），不产生两份。
- G3：两台设备各改名，能识别为同一文档分叉，给用户选择，不静默留两份。
- G4：旧客户端、官方 `/1` 插件仍能读写；新字段丢了可重建。
- G5：复制文件能被识别为分叉，不静默共用 id。
- G6：20k 文件规模下，扫描/清单体积/同步时间在预算内。

**非目标**

- 不做块身份、块级合并、CRDT、op log。
- 不做实时协同、多人共享仓库。
- 不改「md 是唯一内容真相」。
- 不做去重/GC/历史压缩。
- 不要求外部编辑器认识 `textus_id`（它只要不删就行）。

## 3. 三条路线

### R1：front matter `textus_id`（真值在文件）

```yaml
---
textus_id: 5f1c9a2e-4b7d-4c8a-9e3f-1a2b3c4d5e6f
title: ...
---
```

- 优点：随文件同步；E2EE 自动覆盖；旧客户端/外部编辑器通常原样保留；无协议字段；可读可迁移。
- 缺点：改用户可见 md；Obsidian 属性面板会显示；用户可能删；复制文件会复制 id（需检测）；两设备首次分配可能撞不同 id。
- 旧客户端：只要它保留未知 front matter 键，id 就不丢；即使丢了，新客户端按「缺失」处理，不影响内容。
- 适用：所有笔记，或先只对资产卡/被引用笔记。

### R2：`.textus/` 旁车（不进 md）

```text
.textus/doc-ids.json   # path -> id
```

- 优点：md 干净；机器维护；可存路径历史。
- 缺点：**当前不同步**（`in_scope` 白名单）；要改 `in_scope`/`descend` 和协议；旧客户端/插件可能不看；一个全局 map 并发写会冲突；E2EE 下需把新对象纳入加密映射。
- 结论：不作为第一版。除非产品明确「md 里不能多一个字段」。

### R3：清单 `Entry.id`（协议层）

```json
{
  "files": {
    "notes/a.md": { "hash": "...", "size": 123, "blocks": [], "id": "0193..." }
  }
}
```

- 优点：同步规划不下载文件就能配对；清单是同步的中心，天然可见；E2EE 下 `head.json` 被整体加密，id 不泄露。
- 缺点：改 `Entry` 形状；旧客户端重写清单会丢 `id`（serde 忽略未知字段，但序列化时没有这个字段）；需要版本化/回退；单靠它，文件离开清单（外部复制）就失去 id。
- 结论：**适合做缓存，不适合做唯一真值**。

## 4. 推荐：R1 真值 + R3 缓存（混合）

**真值**：`textus_id` 在 front matter。文件被复制/移动/外部编辑，id 跟着文件走。
**缓存**：`Entry.id` 可选字段，从文件 front matter 读出；同步规划优先用它配对，缺失时回退到路径/哈希。
**重建**：旧客户端写掉 `Entry.id` 后，新客户端下次扫描/同步从文件重建；`Entry.id` 永远不是唯一来源。
**不采用**：`.textus/` 旁车作为跨设备身份（scope 不覆盖）。

### 4.1 为什么不是「只 R1」

只用 R1，远端改名 + 改内容时，`head.json` 只有新路径和新哈希，规划器不知道新文件的 id；要配对必须**先下载**候选文件读 front matter。20k 文件、128 MiB 上限下，这会增加一次不必要的下载。`Entry.id` 让规划器直接配对；R1 保证 id 不因清单被旧客户端重写而永久丢失。

### 4.2 为什么不是「只 R3」

只 R3，id 只活在清单里。用户把文件复制到库外再放回、用外部工具移动、或旧客户端重写清单，id 就没了。front matter 是唯一随文件走的位置。

### 4.3 为什么不是 `.textus/` 旁车

同步的 `in_scope` 只带 `.textus/agent.md`、`style.md`、`style.previous.md`、`library/*.md`、`memory/*.md`、`skills/*.md`。要让 `.textus/doc-ids.json` 跨设备，得改 `in_scope` 和 `descend`，还要处理旧客户端/插件的 `/1` 兼容；收益不如 front matter 直接。**如果将来产品决定「md 里绝对不能多字段」，再评估这条。**

## 5. 身份语义

### 5.1 格式

- 第一版用 **UUIDv4**：`uuid` crate 已在同步里用（`new_revision`），无新依赖；不要求可排序。
- 若希望按创建时间排序/便于调试，可用 **UUIDv7** 或 **ULID**；这是实现细节，不影响协议形状。
- 字段名用 **`textus_id`**，不用 `id`：资产卡已有 `id`（语义 id），普通笔记也可能有用户自己的 `id`；`textus_id` 是 Textus 的内部身份，避免撞名。
- 值用带连字符的小写 UUID；也接受无连字符/大写，读入时归一化。

### 5.2 分配时机

1. 在 Textus 内新建文档时立即分配。
2. 打开/同步一个没有 id 的既有文档时分配（首次写入前）。
3. 外部编辑器新建的文件：Textus 首次打开/同步时分配。
4. 两端同时给同一路径分配不同 id：**首次发布者赢**；另一台设备若本地内容未变，采用远端 id；若两端都改了，按冲突处理（见 5.5）。

### 5.3 改名 / 移动

- 同 id、路径变化 → move：新路径继承 id，历史从旧路径迁移到新路径（见 §7）。
- 同哈希、无 id（旧文件）→ 保留现有 `moves()` 配对。
- 同 id、旧路径消失、新路径出现 → move，不产生冲突副本。
- 同 id、两个路径同时存在 → 分叉/复制（见 5.4）。

### 5.4 复制 / 分叉

- 同一 id 出现在两个路径：**分叉**。
- 规则：保留历史更长/更旧的一侧 id；另一侧分配新 id；给用户一句提示（冲突中心或通知），不静默共用。
- 如果一侧路径是另一侧的旧路径（旧路径已从清单消失），按 move 处理，不按复制。
- 用户显式「另存为/复制」时，直接分配新 id，避免先撞后修。

### 5.5 两端同时改

- A 改名、B 改旧路径内容：id 配对成功 → 结果是新路径 + B 的内容；如果 A 也改了内容，则内容冲突，按现有冲突副本规则保留两份，但两份共享同一 id 会成为分叉；冲突副本应分配新 id，避免 id 重复。
- 两端各改名到不同路径：同一 id 两个路径 → 分叉；保留一个，另一个分配新 id 并提示。
- 两端同时给无 id 文件分配不同 id：首次发布者赢；另一侧若内容未变则采用，若内容变了则冲突/分叉。

### 5.6 删除 / 恢复

- 删除：id 随文件进 history/trash；不立即复用。
- 恢复：同 id 回到路径 → 认作恢复，历史接上。
- 删除后另一设备用同 id 新建同路径 → 按 move/恢复处理，不产生重复 id。

### 5.7 缺失 / 被用户删除

- 文件没有 `textus_id`：回退到路径身份；下次写入时分配。
- 用户手动删了字段：等同于缺失；重新分配。内容不丢，历史按路径继续。
- 用户手动改 id：视为新身份；旧 id 的历史留在旧路径（与今天 rename+edit 的行为一致）。

### 5.8 旧客户端 / 官方插件

- 读：旧客户端 serde 忽略 `Entry.id`；front matter 未知键通常原样保留。
- 写：旧客户端重写 `head.json` 会丢 `Entry.id` → 新客户端从文件重建；不丢内容。
- 旧客户端打开带 `textus_id` 的文件：只要它不重写 front matter，字段保留；若它重写并丢掉，下一次 Textus 打开会重新分配（身份短暂丢失，内容不丢）。
- `/1` 插件：协议形状不变（`Entry.id` 可选、未知字段忽略）；插件不认 id 时按路径工作，不阻塞。

### 5.9 E2EE

- `textus_id` 在 md 里，随文件进入加密对象；对象名是 HMAC，不泄露 id。
- `Entry.id` 在 `head.json` 里，E2EE 下映射到 `v2/head.bin`，整份加密；只有 `v1/head.json` 是明文描述符。
- 不在明文对象名/明文清单里放 id；不新增明文 sidecar。

## 6. 协议改动

### 6.1 `Entry.id`（可选）

```rust
pub struct Entry {
    pub hash: String,
    pub size: u64,
    pub blocks: Vec<Block>,
    /// Document identity from the file's front matter. A cache: never the
    /// only source; rebuilt from the file when missing.
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub id: Option<String>,
}
```

- 旧客户端读：忽略。
- 旧客户端写：丢掉；新客户端重建。
- 校验：`id` 若是 `Some`，必须是合法 UUID（或至少非空、长度上限）；非法值按缺失处理，不阻止同步。
- 清单体积：每文件多约 40–50 字节；20k 文件约 1 MB，在 `MAX_MANIFEST_SIZE` 8 MB 内；spike 要实测。

### 6.2 `plan()` 的配对

- 现在：`plan()` 只看 local/remote/base 的 path/hash；`moves()` 用同哈希配对。
- 改动：在 `plan()` 之前，用 `local.id` / `remote.id` 建索引：
  - 同 id、不同 path → move 候选；
  - 同 id、同 path → 普通比较；
  - 同 id、多 path → 分叉；
  - 无 id → 回退到现有哈希/路径逻辑。
- 不改变 `Kind` 的名称；新增内部 pairing 结果即可。

### 6.3 历史迁移

- `History.current` / `versions` 按 path；改名时把旧 path 的 history 迁到新 path（append 到 `versions[new]`，保留旧记录一段时间或直到 `keepDays`）。
- 第一版可以只做「复制历史到新路径」；旧路径的历史随 keepDays 淡出。不要重写历史。
- 如果将来要做「历史按 id」，那是 v2；本 spike 不动。

### 6.4 Base

- `Base.files` 是 path → hash；改名成功后，把 base 从旧 path 搬到新 path。
- 不改 base 形状。

### 6.5 冲突副本

- 冲突副本继续用现有 `Sync conflicts/<path> (<device>) <time>.<ext>` 命名。
- 冲突副本**分配新 id**（或删除 id），避免与原文件重复 id。
- 冲突中心可以显示「与原文件同源」的 id（可选，不泄露给 UI 之外）。

## 8. 工作量与风险

**Spike 核心**（E1–E4、E6、E12）约 **3–5 人天**：先把身份语义和配对跑通，再决定是否完整落地。下表是完整落地估算。

| 项                         | 估算             | 说明                                                             |
| -------------------------- | ---------------- | ---------------------------------------------------------------- |
| 文档 id 读写 + 分配        | 1–2 天           | front matter 读写用现有 `frontmatter.ts`；Rust 侧读 front matter |
| `Entry.id` + `plan()` 配对 | 2–3 天           | 协议字段、索引、回退、校验                                       |
| 历史/base 迁移             | 1–2 天           | 路径迁移、测试                                                   |
| 分叉/复制/冲突策略         | 1–2 天           | 规则 + 提示                                                      |
| 旧客户端兼容测试           | 1 天             | 引擎级模拟                                                       |
| 20k 性能                   | 1 天             | 扫描/清单/同步                                                   |
| **完整落地合计**           | **约 7–11 人天** | 不含 UI/迁移引导                                                 |

**风险**

- **两设备分配竞态**：首次发布者赢的规则要写死并测试；否则会出现同路径两个 id。
- **复制/分叉语义**：用户复制文件是常见操作，不能静默共用 id；提示文案和默认动作要定。
- **旧客户端丢字段**：id 是 best-effort，不能把「id 丢失」当数据损坏；任何路径都要能回退。
- **front matter 用户可见**：Obsidian 属性面板会显示 `textus_id`；需要产品接受或提供隐藏方案。
- **历史迁移**：复制历史可能让 history 变大；要按 `keepDays` 淡出，不能无限增长。
- **清单体积**：20k 文件加 id 约 1 MB；要实测，接近 `MAX_MANIFEST_SIZE` 时要有策略（压缩/只对部分文件存 id）。
- **扫描开销**：只读 front matter 头，不读全文；要实测 20k 文件。

| Q4  | 改名 + 内容冲突                         | 保留两份冲突副本 / 一份 + 提示    | 保留两份，但副本新 id；不静默合并       |
| Q5  | 复制文件                                | 自动新 id / 询问                  | 自动新 id + 通知；不打断                |
| Q6  | 历史迁移                                | 复制到新路径 / 历史按 id（v2）    | 复制到新路径，旧记录按 keepDays 淡出    |
| Q7  | 旧客户端                                | 要求升级 / best-effort            | best-effort；id 丢了可重建              |
| Q8  | `textus_id` 可见性                      | 接受 front matter 可见 / 隐藏旁车 | 先接受可见；若用户反对再评估 R2         |

**推广触发点**：Q1 的「先资产卡 + 被引用笔记」验证通过（E1–E4、E6、E12 有测试证据），且用户确认后，才推广到全部笔记；推广前不默认给普通笔记写 `textus_id`。

## 10. 不做

- 不做块身份；块 id 仍按内容哈希，等证据/评论/AI 锚点的具体需求。
- 不做块级合并、CRDT、op log。
- 不做实时协同、多人共享。
- 不改「md 是唯一真相」；id 丢了不影响内容。
- 不做历史重写/GC；只做路径迁移 + 现有 keepDays。
- 不要求外部编辑器认识 `textus_id`。
