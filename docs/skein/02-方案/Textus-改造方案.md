## 0. 结论摘要

1. **不重写，不换栈。**不需要迁移到 Flutter 或 React Native。Textus 本身已经是 React + Rust 的多端应用。
2. **Textus 不是"没有移动端"。**iOS 路径相对完整，Android 已有可安装包、系统文件选择器和 Kotlin 插件，但工程成熟度明显低于 iOS。
3. **大改业务层，小改桌面端。**真正缺的是"交付 → 结果 → 边界 → 触发"的沉淀闭环，以及手机端的高频入口，而不是跨平台底座。
4. **产品定位：本地优先的笔记工作台，Agent 把真实交付中的判断沉淀成可复用资产。**
5. **理论修正：资产不是写出来的，是被下一次真实交付验证出来的。**旧的三卡模型缺少结果、边界、触发和形态，会退化成任务台账。
6. **实施顺序：理论小样本验证 → 插件验证闭环 → 宿主下沉受控写入 → 补齐多端。**不要一开始就同时改同步、账号、移动端外壳。

## 1. 现状核对

### 1.1 技术栈

| 项目     | 现状                                                 |
| -------- | ---------------------------------------------------- |
| 桌面框架 | Tauri 2                                              |
| 前端     | React 19 + TypeScript + Vite                         |

| 能力                | 位置                                                  | 复用方式                                      |
| ------------------- | ----------------------------------------------------- | --------------------------------------------- |
| 多端能力统一入口    | `src/platform/capabilities.ts`                        | 新增功能按同一模式做平台门控                  |
| 插件沙箱与 RPC      | `src/plugins/host/`                                   | 资产插件运行在同一沙箱内                      |
| 插件贡献点          | `src/plugins/contributions/`                          | 列表页、Webview 页、文件编辑器、命令、AI 工具 |
| 插件 API 权限表     | `src/plugins/api-permissions.ts`                      | 判断资产插件需要哪些权限                      |

| 版本化读写          | `src/plugins/host/broker-files.ts`（`files.process`） | 第一版乐观并发控制基础                        |
| 原子写入            | `src-tauri/src/atomic.rs`                             | 桌面路径直接复用，无需重写                    |
| AI / Agent 基础设施 | `src-tauri/src/ai/`、`src-tauri/crates/aicompat/`     | 增加资产相关工具即可                          |
| 文档保存与冲突检测  | `docs/dev/documents.md`                               | 沿用 mtime、草稿恢复、外部修改重载            |
| iOS 文件授权        | `src-tauri/plugins/textus-files`（Swift）             | 安全作用域、书签恢复                          |
| Android 文件访问    | `src-tauri/plugins/textus-files/android/`（Kotlin）   | SAF、`content://` 读写                        |

### 1.3 移动端真实情况

**iOS**

- 手机布局、抽屉、ActionSheet、底部输入区、手机 AI 页、手机插件页均已存在。
- 与桌面共享插件、主题、Skills、tracked changes。
- 文件访问通过 Swift 插件完成，支持安全作用域目录授权。
- 有手机布局的端到端测试和模拟器 smoke test。

**Android**

- 已提供 APK 发布物。
- 有系统文件选择器、`content://` 读写、持久授权和 Kotlin 插件。
- 插件平台层会把声明支持 iOS 的插件同时视为 Android 可用。
- **但 CI 中 Android 构建是非阻塞检查，允许失败**；目前只能证明"可构建"，不能证明真机功能与 iOS 对齐。
- Kotlin 侧写入是直接打开输出流覆盖，缺少桌面路径那样的临时文件替换语义。

**结论**

> 不是"从没有移动端变成有移动端"，而是"移动端已有底座，缺少资产业务界面和 Android 工程验证"。

### 1.4 不可违反的架构约束

来自项目自身约定：

- 只有 `src/platform/` 和 `src/dev/` 可以直接引用 `@tauri-apps/*`，其他模块必须经过平台层。
- `src/platform/bindings/` 是生成文件，不能手改。
- 平台差异统一走 `src/platform/capabilities.ts` 和 Rust 的 `#[cfg(desktop)]` / `#[cfg(mobile)]`。
- 面向用户的字符串需要同步全部语言文件。
- 新增能力应遵守现有懒加载、测试与原生验证要求。

## 2. 产品定位

### 2.1 三种可能形态

| 形态                    | 主体         | Agent 角色 | 问题                     |
| ----------------------- | ------------ | ---------- | ------------------------ |
| 编辑器 + AI 侧栏        | 笔记文件     | 问答、改写 | AI 是配角，难以形成资产  |
| 聊天式笔记 Agent        | 对话         | 主界面     | 同质化严重，笔记沦为附件 |
| **工作台 + 常驻 Agent** | **笔记文件** | **加工层** | **推荐：产物可复用**     |

### 2.2 一句话定义

> **本地优先的笔记工作台，Agent 常驻在真实笔记上工作，把每一次真实交付沉淀成下一次可调用的判断。**

这里有两个关键词：

- **本地优先**：Markdown 文件是唯一真相，任何编辑器、同步工具、脚本都能读写。
- **常驻**：Agent 不是一个独立聊天 App，而是编辑器旁边的加工层，能读、能提议、不能擅自定稿。

### 2.3 真正的差异点

不要试图做"更聪明的笔记 AI"，而是做**"敢让 Agent 动手的笔记软件"**。

支撑这个定位的，是 Textus 已经具备、而多数笔记软件难以同时具备的四件事：

1. 插件沙箱与权限表；
2. 读写前的版本检查；
3. Rust 侧原子写入；
4. 桌面与手机共用同一份 Markdown。

Agent 的能力上限由这四件事决定，而不是由模型决定。

### 2.4 产品循环

```text
收集 → 整理 → 晋升 → 调用 → 记录
```

| 阶段 | 谁主导               | 主要发生端 |
| ---- | -------------------- | ---------- |
| 收集 | 用户                 | 手机、桌面 |
| 整理 | Agent 提议，用户确认 | 桌面为主   |
| 晋升 | 用户确认             | 桌面、手机 |
| 调用 | Agent / 用户         | 桌面、手机 |
| 记录 | 系统                 | 全端       |

"晋升"是整条链路的关键动作：**普通笔记不会自动变成资产，必须经过一次人工确认。**

### 2.5 结果闭环

产品循环之上，还有一条必须成立的工作循环：

```text
真实交付 → 先做后记 → 结果判定 → 边界提炼 → 可调用形态
     ↑                                              │
     └────────────── 下一次交付复用 ─────────────────┘
```

四条硬规则与 7/30 天淘汰机制以《笔记资产理论》§4 为准，本节不复制条文。这条循环不成立时，界面做得再好也只是台账。

## 3. 架构改造

### 3.1 目标分层

```text
┌────────────────────────────────────────────┐
│ 界面层                                       │
│  桌面：今天 / 编辑器 / 资产库 / Agent 面板      │
│  手机：收集 / 今天 / 确认 / 资产调用            │
├────────────────────────────────────────────┤
│ 资产领域层（新增，纯 TypeScript，不依赖 Tauri） │
│  卡片模型、状态机、晋升规则、来源链、校验        │
├────────────────────────────────────────────┤
│ Agent 工具层（新增）                          │
│  搜索、读取、建草稿、提议修改、请求确认、记录调用  │
├────────────────────────────────────────────┤
│ 存储适配层（新增统一接口）                      │
│  Rust 普通路径 / iOS Swift / Android Kotlin SAF │
├────────────────────────────────────────────┤
│ Markdown 独立库（唯一真相）                    │
└────────────────────────────────────────────┘
```

### 3.2 新增模块职责

| 模块         | 职责                                 | 位置建议                           |
| ------------ | ------------------------------------ | ---------------------------------- |
| 领域模型     | 卡片类型、状态机、字段校验、晋升规则 | `src/features/assets/domain/`      |
| 存储适配     | 统一读写接口，屏蔽平台差异           | `src/features/assets/storage/`     |
| Agent 工具   | 七个窄接口（含触发检索），供 AI 调用 | 插件内或 `src-tauri/src/ai/tools/` |
| 桌面界面     | 今天、复盘、资产库、关系视图         | `src/features/assets/`             |
| 手机界面     | 收集、今日、确认、调用               | `src/features/mobile/` 扩展        |
| 宿主写入服务 | 正式状态迁移、历史、归档             | `src-tauri/src/assets/`（阶段 2）  |

### 3.3 硬性边界

1. 领域层不得引用 `@tauri-apps/*`，只能依赖存储适配接口。
2. 界面层不得直接拼文件路径，必须经过存储适配。
3. Agent 工具不得直接操作文件系统，只能调用领域服务。
4. 原始证据只追加，不修改。
5. 正式状态迁移只能由宿主或用户界面发起，不能由插件或 AI 工具直接写入。

## 4. 数据模型

### 4.1 目录结构

```text
<vault>/asset-library/     # 主库内子目录（2026-11-19 用户裁）
├─ inbox/                  # 未整理的原始笔记
├─ tasks/                  # 任务卡
├─ judgments/              # 判断卡
├─ assets/                 # 资产卡
├─ attachments/<task-id>/  # 原始证据
├─ _usage/<card-id>.jsonl  # 使用记录（record_use，只追加；D1b）
└─ _history/<card-id>/     # 修改前版本
```

### 4.2 通用 Front Matter

```yaml
schema_version: 1
theory_version: 1
id: T-20261114-a1b2
type: task
title: 调研本地家电清洗需求
status: active
created_at: 2026-11-14T10:00:00+08:00
updated_at: 2026-11-14T10:00:00+08:00
revision: 1
created_by: user
source_ids: []
```

约束：

- 稳定 `id` 才是卡片身份，文件名可以改。
- `revision` 每次写入递增，用于乐观并发控制。
- `source_ids` 保留来源链，允许从资产反查证据。
- 正文继续保存人类可读的上下文，不做纯结构化存储。

### 4.3 结果与复用字段

任务卡在 `done` 前必须补齐三段：

```yaml
expected_outcome: "2 周内交付，客户一次通过"
actual_outcome: "18 天交付，返工 1 次"
variance: "低估了外部确认时间"
```

资产卡必须有四项：

```yaml
boundary:
  applies_when: ["周期 ≥ 15 天", "外部依赖 ≤ 2 方"]
  fails_when: ["周期 < 15 天", "需求方未定稿"]
  counterexample: "上一次 10 天项目，因材料等待延期 6 天"
trigger:
  stage: before_delivery # before_delivery / during_task / after_result / on_demand
  label: "报价前"
reuse_form: checklist # checklist / template / prompt / script / decision_table / doc
last_used_at: null
```

激活门槛：

- 资产从 `draft` 转 `active` 前，`boundary`、`trigger`、`reuse_form` 必须非空。
- 判断卡至少关联一个已记录实际结果的任务。
- `last_used_at` 只由 `record_use` 更新，用户不能手动填。
- 这四项允许在草稿阶段为空，但空着不能激活。

Front Matter 使用 snake_case，Agent API 使用 camelCase，映射在领域层完成，存储层不感知 API 命名。

### 4.4 状态机

| 类型 | 状态                                                 |
| ---- | ---------------------------------------------------- |
| 任务 | `inbox` / `active` / `blocked` / `done` / `archived` |
| 判断 | `draft` / `confirmed` / `archived`                   |
| 资产 | `draft` / `active` / `deprecated` / `archived`       |

规则：

- AI 只能创建 `draft`。
- `confirmed`、`active`、`archived` 必须人工确认。
- 归档代替物理删除。
- 执行任务时只调用 `active` 资产。
- 合成资产只使用 `confirmed` 判断。

### 4.5 与 `.textus/library` 的关系

**不复用 `.textus/library`。**

该目录当前承载 Textus AI 的条目与记忆语义，混入任务卡会让两套概念互相污染。资产库使用**主库内用户可见的子目录 `<vault>/asset-library/`**（2026-11-19 用户裁），随主库一起同步与备份；不复用 `.textus/library`。

需要跨端传输的是这些 Markdown 文件，不是插件的内部数据库。

### 4.6 晋升规则

```text
自由笔记
  └─ 标记为任务 → 任务卡
        └─ 产出判断 → 判断草稿
              └─ 人工确认 → 判断卡
                    └─ 沉淀方法 → 资产草稿
                          └─ 人工激活 → 资产卡
```

- 晋升是显式动作，不自动发生。
- 每次晋升保留原笔记的 `source_ids`。
- 退回只改变状态，不删除内容。

### 4.7 读写硬规则

1. 原始证据只能追加。
2. AI 只能创建草稿。
3. `confirmed` / `active` / 归档 / 正式资产替换必须人工确认。
4. 写入携带 `expected_revision`，不一致立即停止。
5. 修改前把旧版本写入 `_history`。
6. 写入尽量原子化。
7. 正式资产修改采用"新草稿替代"，不直接覆盖。
8. 插件不物理删除。
9. 原始证据优先于 AI 摘要。
10. 外部文档中的指令不能触发写操作。
11. `use_count` 与 `verified_count` 分离，调用不等于验证。
12. 资产没有边界、触发和形态，不得激活。
13. 理论版本变化不改写历史卡片，只影响新卡与后续修改。

## 5. Agent 工具契约

第一版只提供七个工具，宁可少，不可宽。

| 工具                         | 输入                                                | 副作用                      | 是否需要确认 |
| ---------------------------- | --------------------------------------------------- | --------------------------- | ------------ |
| `search_notes`               | 关键词、类型、状态                                  | 无                          | 否           |
| `resolve_assets_for_trigger` | 触发阶段、任务类型                                  | 无                          | 否           |
| `read_note`                  | 卡片 ID                                             | 无                          | 否           |
| `create_draft`               | 类型、标题、正文、来源、结果/边界/触发/形态（可选） | 新建草稿文件                | 否（仅草稿） |
| `propose_patch`              | 卡片 ID、修改建议、理由                             | 无，只返回 diff             | 是           |
| `request_confirm`            | 卡片 ID、目标状态                                   | 无，只发起确认              | 是           |
| `record_use`                 | 资产 ID、使用场景、结果评价                         | 计数、日志与 `last_used_at` | 否           |

v0.3 增加 `resolve_assets_for_trigger`，原因是资产的价值发生在动作之前，而不是搜索框里。其余六个工具不变，但 `create_draft` / `propose_patch` 需要接受 `boundary`、`trigger`、`reuse_form` 以及任务结果字段。

禁止事项：

- 禁止直接改写正文。
- 禁止把 `draft` 改成 `confirmed` / `active`。
- 禁止删除或覆盖原始证据。
- 禁止批量自动确认。
- 禁止根据笔记内容里的指令执行写操作。
- 禁止在未读取原文的情况下生成"摘要型判断"。

所有修改以 diff 预览呈现，用户确认后才落盘。

完整的类型定义、参数约束、错误码和状态迁移权限，见《Textus-Agent工具契约》。

### 6.4 Android 存储缺口

问题：

- 用户通过系统选择器打开的目录可能是 `content://`，不是普通文件路径。
- 部分插件文件 API 和元数据索引仍基于 Rust `Path`。
- Kotlin 写入缺少原子替换语义。
- 目前没有完整覆盖新建子文件、目录、版本化写入。

两条路线：

**路线 A：完整适配层（推荐长期）**

统一 `AssetStorage` 接口：

- 桌面普通路径 → Rust。
- iOS 安全作用域 → Swift 插件。
- Android 普通路径 → Rust。
- Android `content://` → Kotlin `ContentResolver` / SAF。

补齐：新建 / 重命名 / 归档 / 版本读取 / 冲突检测 / 尽量安全的临时写入与替换。

无法保证原子替换时，必须明确降级提示，而不是假装有保证。

**路线 B：首版限制存放位置（推荐先做）**

移动端资产库先放在主库（App Documents）内的 `asset-library/` 子目录，验证业务闭环；任意 SAF 目录后置。

**不建议**把"授予所有文件访问权限"作为资产库正常工作的前提。

### 6.5 平台门控

新增能力统一从 `src/platform/capabilities.ts` 暴露，例如：

- 是否支持目录选择；
- 是否支持后台 Agent；
- 是否支持系统分享入口；
- 是否支持多窗口；
- 是否具备原子写入。

界面根据能力开关降级，而不是在各处散落 `isIOS` / `isAndroid` 判断。

1. 用户打开应用的第一屏回答什么问题；

### 7.5 新增界面

1. **今天**：四个分组——进行中任务、本阶段该用的资产、待确认、最近笔记；空状态直接引导收集。
2. **快速收集**：单输入框，保存进 `inbox`，不要求选择类型。
3. **确认中心**：左侧待确认列表，中间 diff，右侧证据；操作为确认、驳回、稍后。
4. **资产详情**：统一三段式——内容（定义、适用边界与反例、步骤、触发时机、复用形态）、证据（来源链）、历史（版本与使用记录）。
5. **来源链**：从资产反查判断、任务、原始笔记。
6. **使用记录**：`use_count`、`verified_count`、`last_used_at` 与复用结果分开展示，避免"用过等于验证过"。
7. **Agent 时间线**：每次工具调用一张卡片，显示工具名、参数摘要、结果和确认状态。信息架构参照 WorkBuddy「专家·技能·连接器」；时间线 / 任务进度的 UI 可收编 BoardUI 智能体组件（MIT 免费部分，收法见附录 B §3.0 同款翻译流程）。

### 7.6 统一交互规则

- 一个主窗口，不新增独立 App 或独立聊天窗口。
- 所有详情页统一"内容 / 证据 / 历史"三段式。
- 列表行统一字段：标题、状态、更新时间、来源数。
- Agent 的任何写操作必须以卡片形式出现，带 diff 和确认按钮，不能藏在聊天气泡里。
- 危险操作二次确认；归档代替删除。
- 手机只保留四个动作，其余功能降级或不提供。
- 不做数据仪表盘式首页。
- 不用红黄绿装饰状态，除非确实表达风险。

### 7.9 块与呈现扩展（候选池 · 2026-11-20）

> **定位**：Notion 式「交互层 ＋ 丰富块」在 Textus 上做不做得、值不值得的结论册。**任务挂账 =《任务清单》ED 组。**本节只立判据与候选，不排期。

**结论先行**：交互层照做（成本低，块菜单 / 把手 / slash / 浮条已有或已补）；丰富块按下面三条红线过筛，能插件化的绝不进内核。**不做**的是 Notion 的数据层（块树入库、任意嵌套、多视图数据库），那条路与「md 是唯一真相」互斥。

#### 7.9.1 三条红线（替代「md 有没有原生语法」的粗筛）

1. **信息无损**：呈现效果之外，全部内容以 md 可读形态存在；别的编辑器打开至少降级可读。
2. **真相单一**：呈现/视图状态不成为第二真相源；不落盘，或落成 md 里的普通文本。
3. **往返字节一致**：`markdown-roundtrip` 门禁照过，导出永远拍平成长文。

**推论**：多列布局、图片画廊、筛选视图这类「本来就可以换种方式达成」的形态全部合规——内容块照常存在，只是渲染换了排布，导出拍平零丢失。**红线不画在「语法是否原生」，画在「信息是否无损、真相是否单一」。**

#### 7.9.2 两条承载台阶

| 台阶         | 能力                                                                                                 | 成本                      | 适用                                                                 |
| ------------ | ---------------------------------------------------------------------------------------------------- | ------------------------- | -------------------------------------------------------------------- |
| 内核块       | ProseMirror schema 节点 ＋ md 解析/序列化 ＋ 菜单条目（callout / math / table / task-list 同款路径） | 每块 1–2 周               | md 有稳定真身的块；需深度编辑交互的块                                |
| **插件轨道** | manifest `contributes.codeBlocks`：注册围栏语言 ＋ 自绘渲染视图（`frame: none` / `size: interface`） | 天级，**rebase 成本 ≈ 0** | 代码栅栏一族（Mermaid / 图表 / 运行预览 / 嵌入）与一切「渲染类」扩展 |

**取舍律**：能在插件轨道落地的，绝不加内核节点——fork 的上游 rebase 成本与内核节点数成正比，与插件数无关。

#### 7.9.3 候选清单

| 候选                    | md 真身                                             | 承载               | 编辑态量级                                                | 判定                                     |
| ----------------------- | --------------------------------------------------- | ------------------ | --------------------------------------------------------- | ---------------------------------------- |
| Mermaid / 图表          | 围栏 ` ```mermaid `                                 | 插件轨道           | 只读渲染                                                  | **做**（试点第一件）                     |
| 图片画廊                | 连排图片块                                          | 插件轨道或渲染开关 | 只读＋点开大图                                            | **做**                                   |
| 筛选视图（文件级排布）  | 文件本身 ＋ 筛选条件（不导出）                      | 插件轨道           | 只读＋点行跳转                                            | **做**（视图本就不该导出）               |
| 网页书签 / 嵌入预览     | 普通链接或围栏                                      | 插件轨道           | 只读渲染                                                  | 做，便宜                                 |
| 附件块                  | 链接                                                | 插件轨道           | 轻交互                                                    | 做，便宜                                 |
| 多列布局                | 子内容 ＋ 容器语法（`::: columns` 族）或 fence 参数 | 内核容器节点       | **全交互（光标跨列 / 拖拽进出 / 选区跨界 / 移动端手感）** | **做，但单独立项**——渲染便宜，编辑态周级 |
| toggle 折叠块           | 无稳定真身                                          | 待定               | 全交互                                                    | 暂缓（md 互操作面待评）                  |
| 块数据库 / 多视图数据库 | 无真身且要第二真相源                                | —                  | —                                                         | **不做**                                 |
| 任意嵌套子块            | 缩进列表已是 md 嵌套上限                            | —                  | —                                                         | **不做**（= 换数据层）                   |

**2026-11-22 增补（AutumnMark 对照）**：代码栅栏标注（`title` / `{n-m}` / `max-lines`）判为**做**（ED2）；单文件 Markdown 便携判为**插件轨道**（ED3，不占内核）；内容选项卡**暂缓**（U19）；折叠块注释**不做**。理由、边界与任务见[《Textus-文档便携与呈现扩展方案》](Textus-文档便携与呈现扩展方案.md)。

#### 7.9.4 视图/呈现状态的四档存放（按污染程度）

1. **运行时推导**：如连续 N 张图自动成画廊——零落盘，缺点是不可精确控制。
2. **fence 参数**：` ```gallery{cols=3} ` 一类——真身是普通文本，字节保真稳过；别的编辑器里降级为代码块。**首选**。
3. **容器语法**：`::: columns` 族——子内容是真块、可编辑可嵌套，代价是语法发明的互操作面；只给多列布局这类需要真块的用。
4. **frontmatter / 侧车**：页面级排布 hint，或完全不碰 md。

#### 7.9.5 优先序（需求驱动，非排期承诺）

**Mermaid 插件试点**（同时验证插件轨道能承载富块）→ 图片画廊 → 筛选视图 → 多列布局（单独立项磨编辑态）→ 其余按需求。

**与既有裁决的关系**：手机格式工具栏（裁决 31 / PH1）是交互层，不受本节影响；墨契 0.7.1「网格是视图、md 是真身」与本条 7.9.1 是同一律的两处应用。

- iOS 真机由上游验收；本 fork 不重复。
- 记录 Android 实际能力与不支持项；iOS 差异由上游记录。

**验收**

**不做**

- 不做界面。
- 不做 AI 工具。

### 阶段 0.5：理论小样本验证

**目标**：先验证这套笔记理论在你的工作里是否成立，再决定产品投入。

**交付**

- 4 周内选 10 个真实交付物。
- 每个交付只记七行：情境、动作、预期、实际、偏差、边界、触发。
- 至少封装 3 条可调用资产，并在后续交付中实际调用一次。

**验收**

- 复用率 ≥30%：按**每条资产自激活起 30 天内是否被再次使用**计；观察期 4 周结束后，对最后激活的资产再续观 30 天结算。
- 复用后的结果有可观察改善，或返工率下降。
- 明确记录至少 3 条反例。

**不成立时**

- 如果复用率低于 30%，先修改理论，不修改工具。
- 如果记录本身拖慢交付，减少字段，而不是增加功能。

## 12. 维护与升级策略

### 12.1 法律与工程是两件事

Textus 使用 MIT 许可证，允许修改、分发，包括闭源分发，只需保留版权与许可声明。所以"能不能改"不是问题。

真正的问题是：**改完之后，谁来跟上游的更新。**

### 12.2 三种维护模式

| 模式     | 改动范围                   | 与上游冲突 | 长期成本 | 适用阶段                                             |
| -------- | -------------------------- | ---------- | -------- | ---------------------------------------------------- |
| 纯插件   | 插件目录 + 少量注册        | 极低       | 低       | 阶段 1                                               |
| 薄 fork  | 新增模块 + 少量接入点      | 中         | 中       | 阶段 2                                               |
| 深度分叉 | 导航、编辑器、同步、发布链 | 高         | 高       | 不建议；**同步已改为受控深分叉（S 组，crate 隔离）** |

### 12.3 纯插件模式

能做：

- 今天视图、资产列表、卡片详情；
- 晋升流程与确认弹窗；
- 七个 Agent 工具；
- 手机端收集与确认。

不能做：

- 强制写入规则（插件拿到的是通用文件权限）；
- 修改导航结构；
- 改同步机制；
- 改编辑器内核。

升级方式：直接跟随上游版本，只需验证插件 API 兼容性。

### 12.4 薄 fork 模式

原则：

- 保留 `upstream` remote，主分支只用于同步。
- 新功能放在独立目录，不散落修改现有文件。
- 尽量不改生成文件、编辑器内核和既有 i18n key。
- 必须触碰的接入点集中记录，形成自己的 patch 清单。
- 未完成功能用 feature flag 包住。

建议新增目录：

```text
src/features/assets/              # 领域模型与界面
src-tauri/src/assets/             # 受控写入服务
src-tauri/plugins/textus-assets/  # 如需原生存储能力
```

预计需要触碰的现有文件：

- 一级导航注册入口；
- `src/platform/capabilities.ts`；
- `src-tauri/tauri.conf.json`（权限与插件声明）；
- 语言文件（新增 key）；
- 插件权限表（仅当新增 API）；
- **同步/宿主新增（2026-11-19 补）**：`src-tauri/Cargo.toml`（workspace/依赖）、`src-tauri/src/lib.rs`（`sync::init`）、`src-tauri/src/invoke_handler.rs`、`src-tauri/src/bindings.rs`、Settings 页注册（`settings-pages.tsx` / `builtin-pages.tsx`）、移动端文件/回收站原生 API（若做）。

### 12.5 升级流程

1. 拉取上游 release tag（`git fetch upstream --tags`）。
2. 从工作分支新开临时同步分支 `sync/upstream-X.Y.Z`，在它上面 `git merge vX.Y.Z --no-ff`；工作分支在验证期间保持可发布。
3. 解冲突，保住 patch 清单（§12.4）。
4. 跑 `typecheck`、`lint`、`format`、`check:repo`、全量 `vitest`、`cargo test --lib` 与 `textus-sync` 测试。
5. 桌面 built app smoke + Android smoke（iOS 归上游）；e2e 按上游壳写的用例与 H0 壳冲突时记录差异，不为变绿改断言。
6. 验证通过后回工作分支 `git merge --ff-only sync/upstream-X.Y.Z`，删临时分支；长期只留 `main` + 工作分支，`main` 不并。
7. 打自己的版本号，同时保留上游版本号便于追溯；在 `archive/` 写合并记录（tag、合并提交、取舍、验证、未做项）。

操作步骤以[工程菜谱 R5](../01-纪律/工程菜谱.md#r5-跟上游-tag-并线)为准；最近一次 v1.4.6 的记录见 [2026-11-22-b3-v1.4.6.md](../archive/2026-11-22-b3-v1.4.6.md)。

### 12.6 结论

- **自己用**：可以始终跟随上游，纯插件路线几乎不增加维护负担。
- **改宿主**：就要维护一个 fork，但把改动限制在新增目录内，成本可控。
- **对外分发**不在本基线内：若将来做，签名 / 商店 / 更新通道成本另议，与是否 fork 无关。
- **降低成本的唯一办法**：把通用能力（存储适配、受控写入）尝试提回上游，减少长期分叉面。

### 12.7 跟上游的节拍与独立维护触发点（2026-11-16 补）

**判定：跟随上游（按 release 节奏），独立维护只是触发点后的退路。**理由：全部差异化住在新增目录（上游改不到）；上游持续供给的恰是 solo 最不该自己扛的部分（编辑器内核 / 安全修复 / 五端适配 / 新特性）。独立维护的真实成本 = 一人扛整条产品线的安全修复与平台更新——不做此假设。

**节拍**：

- 主基线 = 上游 **release tag**（原 v1.4.5；2026-11-21 清账并入 v1.4.6-rc.3；2026-11-22 已并入稳定 tag v1.4.6，合并 `457f6693`）；每次上游发新版 → 拉 tag → 按临时同步分支流程并线（§12.5；五个旧接入点 + 同步/宿主新增注册点）→ 跑门禁 → 真机 smoke → 打自己的版本号。
- **不追 main**（开发线，半成品密集——Settings 重构 / 浮层格式条都在进行时）。
- 通用能力继续提 PR 回上游（§12.6），每提回一条分叉面小一分。
- 接触面收敛为三类接口：`aiTools` 贡献、`broker-files`、导航/视图注册 + i18n——**接口稳定就一直跟得动；接口破坏才是分叉时刻**。

**独立维护触发点（可证伪，满足任一才转）**：

1. 连续两次上游 release 的适配成本 > 3 人天（patch 清单失控信号）；
2. 上游 > 6 个月无 release 且 main 无实质提交（停摆信号）→ 评估接管社区版或转独立；
3. 上游做了与资产闭环正面冲突的功能且拒绝差异化共存（产品撞车）。

触发后从最后一次成功的 rebase 点分叉转独立维护；之前的跟随投资不浪费。触发前，独立维护是一个**不需要花钱的选项**。

**B.3.2 方法论（方案已在用，补个名字）**
