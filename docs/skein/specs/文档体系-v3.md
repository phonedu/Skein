# 文档体系 v3

> 目标：每个承诺有入口，每个任务有规格，每个代码提交有任务号，每个完成/冻结的文档离开 `specs/`。
> 这是文档系统的规格，不是产品路线；产品/界面/同步仍以各自规格与 `decisions/` 为准。
> `DOC-v3` 已归档（2026-11-24，见 [archive](../archive/2026-11-24-DOC-v3.md)）；本规格作为现行文档系统的契约保留。

## 1. 四层

| 层          | 目录                                     | 允许状态                    | 用途                         |
| ----------- | ---------------------------------------- | --------------------------- | ---------------------------- |
| L0 宪法     | `AGENTS.md`、`discipline/`、`decisions/` | —                           | 入口、行为规则、为什么       |
| L1 工作     | `status.yaml`、`inbox.yaml`、`STATUS.md` | —                           | 现在做什么、未分诊承诺、待裁 |
| L2 在用规格 | `specs/`                                 | `active`（契约可 `frozen`） | 当前实现的唯一规格           |
| L3 参考     | `research/`                              | `reference`                 | 证据，不当路线图             |
| L4 历史     | `archive/`                               | 任意                        | 冻结，只增不改               |

生成物：`STATUS.md`、`INDEX.md`、`COMMANDS.md`、`archive/INDEX.md`。禁止手改。

## 2. 台账

- `status.yaml` 保持现有 schema：`workstreams`、`tasks`、`later`、`waiting`、`questions`。
- 任务加 `kind: task | chore`；chore 不等同于六行任务，用于小改，但仍需 ID 和证据。
- `later` 是未来项；`docs:task start <id>` 把它提升为 `tasks` 的 `doing`，仍要求六行。
- 每个 task/later 必须有 `spec`；目标的 front-matter 必须有 `tasks: [id]`，双向可查。
- 每条工作线有一个主 `spec`；相关规格放进 `also`。每个 task/later 的 `spec` 必须等于所属工作线的主规格或 `also` 中的一条，否则 `docs:check` 失败。
- `inbox.yaml` 独立保存“说过但未分诊”的承诺；`docs:wrap` 要求清零。

## 3. 生成页

`STATUS.md` 第一屏固定 `## 0. 承诺一览`，下面直接是 **一张总任务清单**：

- `## 1. 任务清单`：所有 `doing`、`todo`、`later` 同表，序号连续；排序为进行中 → 待做 → 以后，同组按 `status.yaml` 顺序。
- 每行保留状态、ID/标题、验收/说明、规格、估算；`later` 的说明取 `note`。
- 承诺一览仍汇总现在 / 下一批 / 以后 / 待裁 / 未分诊；不再分别生成 Now、Next、Later 三张表。
- 工作线、Waiting / Blocked、待审 / 触发点、Inbox 继续保留在任务清单之后。

## 4. 命令

| 命令           | 作用                                                                       |
| -------------- | -------------------------------------------------------------------------- |
| `docs:capture` | 一句话承诺 → `inbox.yaml`；`--list / --check / --resolve / --drop`         |
| `docs:audit`   | 扫 `specs/`、`proposals/` 的“待做/后续/暂缓/待补/待定/未做/待审”，输出候选 |
| `docs:wrap`    | `capture --check`（inbox 清零）→ `audit --summary` → `docs:check`          |
| `docs:task`    | `brief / start / done / add`；chore、later 提升；`add --next` 插到 Next 最前；状态机校验 |
| `docs:review`  | 给外部评审 AI 的只读包：规则 + 规格 + 裁决 + diff + 验证命令               |
| `docs:doctor`  | inbox、audit 候选、无在办项的 active 规格、缺六行、过期 verified、重复标题 |
| `docs:archive` | 把规格移入 `archive/`，打印引用，生成归档索引                              |
| `docs:propose` | 把草案/暂缓移入 `proposals/`                                               |

## 5. 硬检查

`npm run docs:check` 除现有链接/元数据/裁决 ID/预算外，还查：

- task/later ID 唯一；`spec` 存在；目标的 front-matter 的 `tasks` 反向包含；状态合法。
- 工作线 `spec` 存在；`also` 是存在的路径列表；task/later 的 `spec` 属于所属工作线的主规格或 `also`。
- `specs/` 只允许 `active/frozen`；`proposals/` 只允许 `draft/deferred`；`research/` 只允许 `reference`。
- 裁决 ID/`supersedes`/`spec` 有效；生成页与归档索引新鲜。
- 活文档无修订记录/版本头。

## 6. 硬门禁

- 代码提交（`src/`、`src-tauri/`、`e2e/`、`scripts/`）的 message 必须有 `Task: <id>`；
  ID 必须是 `doing` 的 task/chore。merge 与纯文档提交豁免。
- `.githooks/pre-commit` 跑生成页新鲜度 + `check-skein-docs`。
- `.githooks/commit-msg` 做上述任务号检查，失败时打印修复命令。
- CI 的 `check-commits` 对 PR 范围重查，抓 `--no-verify`。
- `docs:wrap` 是 AI 会话收工门；inbox 未清零即失败。

## 7. 生命周期动作

- 完成规格：把现行规则合进当前规格，完整历史移 `archive/`；原路径若被裁决 `spec` 引用，保留 redirect stub。
- 草案/暂缓：移 `proposals/`，不参与当前实现。
- 归档：`archive/INDEX.md` 生成；`archive/README.md` 只留规则与分类。
- 裁决不合并；`decisions/README.md` 增加按 spec/领域分组。

## 8. 验收

- `STATUS.md` 第一屏能看到 T2；`docs:task start T2` 的 context 含主题规格。
- `docs:capture` → Inbox 出现 → `docs:wrap` 失败 → 分诊/`--resolve` → 通过。
- 代码提交无 `Task:` 被拒；`todo` 任务号被拒；`doing` 通过；纯文档提交通过。
- `docs:archive` 移动后 `check-links` 通过；`archive/INDEX.md` 出现。
- `docs:check`、`release:check`、`check:repo`、`verify` 全绿。
