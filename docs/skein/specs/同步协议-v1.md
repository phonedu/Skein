# 同步协议 v1 规范（冻结）

> **状态**：冻结，2026-11-19（S0b）。协议标识 `textus-cloud-sync/1`。
> **用途**：官方 Cloud Sync 插件的 `/1` 仓库是兼容基线；本 fork 的插件参考实现与内置 Rust 实现都按本文读写。**不向上游 PR 本文件**。
> **原则**：v1 只做旧客户端能读的写入；任何改变路径范围、块布局、加密参数含义的改动 = v2 硬切。旧客户端必须 fail closed，并给「请升级」错误。
>
> **实现状态（2026-11-21）**：明文 `/1`、锁、history、冲突、S3/WebDAV 已在内置 Rust 与插件实现；E2EE（§9）的 crate 密码学、加密封装、每库密码、命令、built app + 真实 WebDAV 与真实 S3 引擎级验收已完成（S2b 归档）；插件真机跨端已由 S2-3 验收通过。服务器 Date（§10）、签名（§11）、32 MiB 传输预算尚未实现，归 S5。文档稳定身份（`textus_id` + 可选 `Entry.id`）已裁决并完成，见《[Textus-文档稳定身份-v0](../archive/2026-11-21-document-identity-v0.md)》（归档）。

## 1. 仓库布局

一个仓库 = 一个 `prefix` 下的对象空间：

```
<prefix>/v1/head.json
<prefix>/v1/history.json
<prefix>/v1/lock.json
<prefix>/v1/blocks/<hash 前 2 位>/<hash>
<prefix>/v1/snapshots/<revision>.json
```

加密仓库：

```
<prefix>/v1/head.json              # 加密描述符（明文；旧客户端看到 e2ee format 即拒绝）
<prefix>/v1/lock.json              # 锁（明文，owner 可见）
<prefix>/v2/head.bin              # 加密清单
<prefix>/v2/history.bin           # 加密历史
<prefix>/v2/blocks/<name 前 2 位>/<name>  # name = HMAC-SHA256(nameKey, 明文块键)
<prefix>/v2/snapshots/<revision>.bin
<prefix>/v2/probes/<uuid>.bin     # 连接探测，可选
<prefix>/v2/pending/<uuid>.bin    # 中断上传的块日志，可选
```

- 明文与加密**不混用**：一个仓库要么 `/1` 明文，要么“`v1/head.json` 描述符 + `/v2` 对象”的加密仓库。加密仓库不会在 `/1` 写明文 head。
- `prefix` 由绑定决定；新库默认 `<connection prefix>/<slug>-<vaultId 前 8 位>/`。
- 对象键大小写敏感；路径分隔符统一 `/`；不允许 `..`、绝对路径、反斜杠。

## 2. 常量与上限

| 常量                  | 值                     | 说明                                                                |
| --------------------- | ---------------------- | ------------------------------------------------------------------- |
| `FORMAT`              | `textus-cloud-sync/1`  | head/history/base 的 `format`                                       |
| `CHUNK_SIZE`          | `2 * 1024 * 1024`      | v1 固定 2MB，**不做 CDC**                                           |
| `MAX_FILE_SIZE`       | `128 * 1024 * 1024`    | 单文件上限                                                          |
| `MAX_BLOCKS_PER_FILE` | `64`                   | 旧客户端硬校验 `blocks.length <= ceil(MAX_FILE_SIZE / CHUNK_SIZE)`  |
| `MAX_FILES`           | `20000`                | 清单文件数上限                                                      |
| `MAX_MANIFEST_SIZE`   | `8 * 1024 * 1024`      | head/history 单对象大小上限                                         |
| `MAX_HISTORY_SIZE`    | `8 * 1024 * 1024`      | history 上限                                                        |
| `TRANSFER_BYTES`      | `32 * 1024 * 1024`     | 单次运行在内存中的传输字节预算（内置当前顺序传输，未强制；S5/S2-2） |
| `TRASH_DAYS`          | `30`                   | 旧 trash 语义保留期（history 接管后仅兼容读取）                     |
| `MAX_TRASH`           | `2000`                 | 旧 trash 数组上限                                                   |
| `KEEP_DAYS`           | `30 \| 90 \| 365 \| 0` | `0` = 永久保留                                                      |
| `MAX_VERSIONS`        | `200`                  | 每路径版本上限                                                      |

v1 **不新增必填字段或新对象**：CDC/变长块、强制签名、KDF 升级、后台同步协议。`Entry.id` 是 S2c 设计中的**可选**缓存字段，旧客户端可丢弃；详见 §3.1。

## 3. JSON 形状

### 3.1 `Block` / `Entry`

```json
{ "hash": "<sha256 hex>", "size": 2097152 }
```

```json
{
  "hash": "<sha256 hex of bytes>",
  "size": 4194304,
  "blocks": [
    { "hash": "…", "size": 2097152 },
    { "hash": "…", "size": 2097152 }
  ],
  "id": "<optional: document's textus_id, a cache>"
}
```

- `hash` 是块/文件字节的 SHA-256 十六进制小写。
- `size` 是字节数，不是 UTF-16 长度。
- `blocks` 按文件内偏移升序；相邻块恰好拼接为文件字节；不重叠、不留空。
- Entry 的三个必填字段是 `hash`、`size`、`blocks`；S2c 另加**可选** `id`（来自 front matter `textus_id` 的缓存）。旧客户端重写 Entry 时会丢掉 `id`，这是允许的：新客户端从文件重建，`id` 永不作为唯一来源。

### 3.2 `Manifest`（head）

```json
{
  "format": "textus-cloud-sync/1",
  "revision": "<uuid>",
  "updatedAt": "<ISO 8601>",
  "files": { "Notes/a.md": { "hash": "…", "size": 123, "blocks": [] } },
  "trash": []
}
```

- `revision` 每次发布新值，UUID 字符串；旧客户端会原样 spread 顶层字段。
- `updatedAt` 服务器时间优先，其次设备时间；仅用于显示/排序，不用于正确性。
- `files` 的键是相对 `prefix` 的路径；JSON 对象顺序不承载语义。
- `trash` 可选，只为旧客户端兼容；新实现以 history 为准。

### 3.3 `History`

```json
{
  "format": "textus-cloud-sync/1",
  "current": { "Notes/a.md": { "at": "<ISO>", "device": "<string?>" } },
  "versions": {
    "Notes/a.md": [
      {
        "hash": "…",
        "size": 123,
        "blocks": [],
        "at": "<ISO>",
        "device": "…",
        "until": "<ISO>"
      }
    ]
  },
  "previous": "<revision?>",
  "head": "<revision?>",
  "keep": { "days": 90, "at": "<ISO>" }
}
```

- `current` 是每个当前文件的来源；`versions` 是旧内容，新到旧。
- `previous` 是上一个 head 的 revision，其 snapshot 必须保留。
- `head` 是写这份 history 时对应的 head revision；读侧校验 `history.head === head.revision`（缺失视为旧客户端/未启用 history）。
- `keep` 是仓库级保留策略；`keepDays` 只取枚举值。

### 3.4 `Lock`

```json
{ "id": "<uuid>", "startedAt": "<ISO 8601>" }
```

- v1 锁只有这两个字段；**没有** `expiresAt`、`lease`、`ownerDevice` 的强制语义。
- 旧客户端把「存在即占用」；新实现可以读写更多字段，但不得依赖旧客户端理解它们。

### 3.5 本地 `Base`（不上远端）

```json
{
  "format": "textus-cloud-sync/1",
  "files": { "Notes/a.md": "<hash>" },
  "parked": {}
}
```

- 本地 base 按 `(vaultId, deviceId, repositoryId)` 隔离；不属于远端协议。
- `parked` 是排除路径上次同步的 hash，重新纳入时用。

## 4. 路径与 scope

- 路径是相对仓库根的 UTF-8 字符串；比较按字节，**不做 Unicode 归一化**。落盘时，发布方拒绝仅大小写/Unicode 组合不同的孪生路径（避免 Windows/macOS 互相覆盖）；读侧遇到孪生清单 fail closed。
- 长度限制按 JS `String.length`（UTF-16 code unit）计：单段 ≤ 255，总路径 ≤ 1024；与旧客户端一致。
- 拒绝：空段、`.`/`..`、绝对路径、反斜杠、NUL、控制字符、结尾 `/`。
- `inScope` 是路径白名单：只同步用户库内、非隐藏元数据目录的普通文件；`.textus/`、`.git/`、插件私有目录、系统回收站/App trash 不进仓库。
- 排除规则按 `.gitignore` 语义；被排除路径不传、不拉、不删。
- `format`、`inScope` 接受范围、`KEEP_DAYS` 枚举是 v1 不变量；改变它们 = v2。

## 5. 写入不变量

每个 Entry 必须满足：

1. `1 <= block.size <= CHUNK_SIZE`；
2. `blocks.length <= 64`；
3. `sum(blocks.size) == size`；
4. `size <= MAX_FILE_SIZE`；
5. 文件数 `<= MAX_FILES`；head/history 编码后 `<= MAX_MANIFEST_SIZE`；
6. `format === FORMAT`，且不依赖任何 **Entry 级**新字段；
7. 不依赖 head/history 顶层可选字段做正确性判断；旧客户端可能丢弃它们；
8. 不改变 `inScope` 的路径接受范围、块布局、加密参数含义。

任何一条不满足，写入方必须 fail closed，不得发布半份清单。

## 6. 发布顺序

一次成功同步的远端写入顺序：

1. 取锁 `create(v1/lock.json)`；失败 → `locked`。
2. 读 head/history；history 损坏 → `invalidHistory` 停；`history.head ≠ head.revision` 时，若 `previous == head.revision` 说明上次写完 history 没写 head（剔除其重复退休项后继续），否则先折入缺失的 snapshot，不丢版本。
3. 上传缺失块（`create` 或 `put`，按字节 SHA-256 校验；已存在但内容不符 → 重写/报错）。
4. 写 `v1/snapshots/<next.revision>.json`（下一 head 的完整清单）。
5. 写 `v1/history.json`（含 `head: next.revision`、`previous: head.revision`）。
6. 写 `v1/head.json`（最后一步；旧客户端以 head 为提交点）。
7. 读回 head，确认 revision/字节一致；失败 → `publishFailed`，不删锁。
8. 释放锁（仅在锁仍属于自己时删除）。

**顺序理由**：history 先于 head，旧客户端读 head 时 history 已经可读；head 是唯一提交点。history/head 非原子，读侧必须用 `head` 字段校验，不能假设两者同时更新。

## 7. 锁

- `create` 必须是「仅当不存在才创建」的语义：S3 用 `If-None-Match: *`（阿里云 OSS 用 `x-oss-forbid-overwrite: true`）；WebDAV 用临时对象 PUT + `MOVE` `Overwrite:F`（不同 DAV 服务器条件 PUT 不通用）。
- 旧客户端的 412/409 处理不完整：新实现必须把 `create` 放进 try，412 时读回锁：
  - 锁 owner 的 `id` 与自己相同 → 视为自己已持有（重试/恢复）；
  - owner 不同 → `locked`，**不自动抢**。
- 无 `expiresAt` 的旧锁永远不自动过期；只能用户手动 unlock。v2 再引入 lease + 签名。
- 释放锁前再读一次，确认 `id` 仍是自己；不是自己 → `lockLost`，不删除别人的锁。
- 锁丢失后不得继续发布；已上传块可留给下次/GC。

## 8. 删除、冲突、历史

- 删除 = 从 head 移除 Entry；旧内容进 history（`versions`），30/90/365/0 天按 `keep` 淡出。
- 冲突 = **两份文件**，不静默覆盖：
  - **本地版本保留原路径并上传**；远端版本写到 `Sync conflicts/<原路径> (<远端内容 hash 前 8 位>)<扩展名>`（与插件 `conflictPath` 一致；`.textus/` 映射为 `Textus project/`，`.obsidian/` 映射为 `Obsidian settings/`；中文界面可显示「同步冲突」目录，实际路径稳定）。
  - 冲突副本也进入 head/history，参与文件数/大小上限。
- `trash` 仅旧兼容；新实现不再往 `trash` 追加。
- **文档身份是路径，不是哈希**：head 的 `files` 以相对路径为键；hash 只标识内容。改内容路径不变，旧内容进该路径的 history。
- **v1 没有 rename 操作**：本地移动 = 旧路径删除 + 新路径新增；远端同哈希的新路径可被本地当作 move 应用。历史按路径，不跟随改名；移动+编辑并发时可能同时留下旧路径与新路径，属不静默覆盖。详见[同步方案 §4.3–§4.4](同步方案.md#43-文档身份路径不是哈希)。
- 大批删除保护（H3）：base 非空而本地扫描为 0 → 中止；删除比例 >20% 或 >50 个 → 二次确认。插件与内置都执行。
- 空扫描不得当作「远端全删」；宁可 `needsAttention`。

## 9. 加密（E2EE v1，设计；S2b 已实现并验收归档）

### 9.1 描述符

`v1/head.json`（明文描述符；加密仓库用它让旧客户端 fail closed）：

```json
{
  "format": "textus-cloud-sync-e2ee/1",
  "repositoryId": "<uuid>",
  "kdf": "PBKDF2-SHA256",
  "iterations": 600000,
  "salt": "<32 bytes hex>",
  "verifier": "<AES-GCM(key-check) hex>"
}
```

- `repositoryId` 必须是 UUID；`salt` 32 字节；`iterations` 固定 600000；`verifier` 长度 = `(len("Textus encrypted workspace key check") + 32) * 2`（4 字节 magic + 12 字节 IV + 16 字节 tag）。
- 描述符 pin：客户端记住首次见到的描述符 hash；变化 → `encryptionChanged`，不自动接受。

### 9.2 密钥派生

1. `PBKDF2-SHA256(password, salt, 600000) -> 32 bytes master`；
2. `HKDF-SHA256(master, salt=repositoryId, info="textus-cloud-sync-e2ee/1/content") -> AES-256-GCM key`；
3. `HKDF-SHA256(master, salt=repositoryId, info="textus-cloud-sync-e2ee/1/names") -> HMAC-SHA256 key`。

密码长度 12–1024，去空白后非空。

### 9.3 对象加密

- 明文对象（head/history/blocks/snapshots）先序列化，再用 AES-256-GCM：
  - 12 字节随机 IV；
  - AAD = `JSON.stringify(header)\n<对象键>`，其中 `header` 只含 `format/repositoryId/kdf/iterations/salt`；
  - 密文 = `"TCS2"` (4 bytes) + IV (12) + GCM ciphertext/tag。
- 对象名 = `HMAC-SHA256(nameKey, 明文对象键)` 的 hex；块按前 2 位分目录。
- 加密仓库的 head 写在 `v2/head.bin`，不在 `/1` 写明文 head；旧客户端看到 `v2` 会 fail closed。

## 10. 时间、排序、错误

- 时间：ISO 8601 UTC（`toISOString()`）；服务器 `Date` 优先，设备时钟只作 fallback。时钟回拨不得删除历史（`clamp` 到已见最大值）。实现：内置当前用本地时钟，服务器 Date 与 clamp 归 S5。
- 排序：文件路径按 UTF-8 字节序；版本按 `until`/`at` 降序；同时间按 hash 稳定排序。
- 错误码（稳定字符串，UI 负责翻译；实现以 `SyncError.code` 为准，完整表见 `src/i18n/errors.json` 与设置页映射）：
  - 锁：`locked` / `lockLost`
  - 清单/历史/条目：`invalidManifest` / `invalidHistory` / `invalidEntry` / `invalidLock` / `missingBlock` / `integrityError`
  - 路径/上限：`tooLarge` / `tooManyFiles` / `invalidPath` / `invalidPrefix` / `caseCollision`
  - 保护：`emptyScan` / `bulkDelete` / `remoteMissing` / `unsafeServer` / `conditionalWriteUnsupported`
  - 网络/权限：`networkError` / `permissionError` / `rateLimited` / `quotaError` / `httpError`
  - 本地/发布：`localReadError` / `localWriteError` / `localTrashError` / `localMoveError` / `localChanged` / `fileOpen` / `publishFailed`
- 旧客户端遇到未知 `format`/字段必须 fail closed，不得猜测写入。

## 11. 签名（v1 best-effort）

- v1 **不强制** head 签名；`head.signature` 若存在，旧客户端会忽略，新客户端可校验但不得因缺失拒绝。
- v1 的正确性依赖：`revision` 单调 + 锁 + 读回校验 + 本地 `lastRevision`（S5 硬化）。
- v2 才把 signed head + `lastRevision`（拒绝非上次/非后代）作为强制；届时旧客户端 `unsupportedVersion`。

## 12. 兼容性测试与向量

- Golden vectors：空仓库、单文件、多块文件、删除、冲突、history 淡出、加密往返、锁 412、history/head 不一致。
- 差分互通：官方插件 0.6.x ↔ 内置 Rust，双向读写同一 `/1` 仓库；旧客户端不升级仍可读写。
- 属性测试：任意块序列 `sum == size`、块数 ≤64、路径 scope、history 解析失败不崩溃。
- 真机向量：华为 PKT0220512001548 前台同步、杀进程、弱网、冲突副本。

## 13. v2 硬切条件

出现以下任一变化，必须新开 `textus-cloud-sync/2`：

- 改变块布局/CDC/块上限；
- 改变路径接受范围（放宽/收紧 `inScope`）；
- 改变加密参数含义（KDF、AAD、对象命名、描述符字段语义）；
- 强制 signed head 或 `lastRevision` 作为写入前提；
- 改变 `KEEP_DAYS` 枚举或历史语义。

v2 对象只作为新键，不覆盖 `/1`；旧客户端读 `/1` 继续工作，遇到 `format` 不认识时 fail closed。

## 14. 与实现的关系

- 插件 `catvinci.cloud-sync` 0.6.x 冻结为 `/1` 参考实现；只修安全问题，不新增功能。
- 内置 Rust 协议层按本文实现（S2/S3，2026-11-21）：fake store → S3/WebDAV → 设置/冲突/历史；引擎级差分互通、S2 验收与 S3 移动端均已归档。E2EE crate 的密码学与 `EncryptedStore` 已与插件双向互解；设置/命令已接线，加密仓库引擎 round-trip 与 built app/真实 S3 验收已过。
- 宿主文件层（H1–H8）与传输层（S3/WebDAV/LAN）不在本文范围；它们只提供 `ObjectStore` 与 `LocalFiles`。

## 15. 一句话

**v1 的自由度只在「head/history 顶层可选字段」；块、路径、加密参数、锁语义全部冻结。任何想改这些的念头，先开 v2。**
