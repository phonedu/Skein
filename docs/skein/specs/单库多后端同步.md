# 单库多后端同步

> **裁决 66（2026-11-25）**：一个库可以有多个后端；每个后端是独立仓库，各留自己的 base/last；同一台设备同一时刻只有一个 active 后端。普通切换不再清空另一个后端的 base。
>
> 内置同步的协议、分层与历史模型仍以 [同步方案](同步方案.md) 为准；本文件只定“一库多后端”的状态、切换与质量边界。

## 1. 问题

现在一个 vault 只有一个 binding、一份 base。切到另一个连接时：

- `remote_changed` 为真；
- 旧 base/last 被删；
- 生成新的 `repository_id`；
- 首轮按新仓库全量对账。

结果是“局域网 ↔ S3”每切一次都重新来一遍，无法像用户参考的笔记软件那样：平时局域网，切 S3 上传/检查，之后切回来只同步差异。

参考软件的实际模型不是“一个仓库挂多个入口”，而是 **一个本地库 + 多个独立后端**。设备切换的只是“当前用哪个后端”；两个设备只有选到同一后端时才互相看见。

## 2. 数据模型

```text
Vault
  ├── activeBackendId
  ├── BackendState: 局域网 Hub
  │     ├── connection_id / prefix
  │     ├── repository_id
  │     ├── base（本机对该远端上次同步的文件哈希）
  │     ├── last（上次结果）
  │     └── encrypted / 密码引用
  └── BackendState: S3 / WebDAV
        ├── connection_id / prefix
        ├── repository_id
        ├── base
        ├── last
        └── encrypted / 密码引用
```

- **BackendState 是每库每后端一份**，不是每库一份。
- `base` 只跟 `(vault, backend)` 走，不跟全局走。
- 每个后端仍是完整独立的仓库：head/history/blocks/lock 都在各自远端。
- 连接仍然可以被多个库共享；每个库在每个连接下有不同 prefix。
- 加密：同一库的所有后端必须使用同一加密状态与密码；不一致时拒绝切换。

## 3. 切换语义

### 3.1 普通切换

- 只改 `activeBackendId`，不清任何后端的 base/last。
- 目标后端已有 BackendState：用它自己的 base 做增量。
- 目标后端没有 BackendState：进入“首次对账”。
- 正在同步、有锁、插件 Cloud Sync 运行时：先阻断，等结束。
- 同一设备同一时刻只有一个 active 后端；不并行同步。

### 3.2 首次对账

| 目标 | 行为 |
| --- | --- |
| 目标远端为空 | 本地文件全部上传；保存该后端的 base；另一台设备之后切来即可看到 |
| 目标非空、本地为空 | 全部下载 |
| 两边都有、只有一边有某文件 | 只有本地的上传，只有远端的下载 |
| 两边同路径、内容不同 | **冲突副本**，不覆盖、不删除 |
| 两边同路径、内容相同 | 视为已同步 |

第一轮必须预览/确认，禁止自动空扫描和大批删除。空 base 的首次对账不做删除推断。

### 3.3 之后切回旧后端

- 使用该后端自己的 base；
- 本地在其他后端改过的文件作为“本地变更”上传；
- 旧后端上的变化下载/冲突；
- 若两边都改同一路径，走现有冲突副本规则；
- 不是全量，除非该后端没有 base。

## 4. 三种用户

| 用户 | 用法 | 产品行为 |
| --- | --- | --- |
| 局域网主力，S3 备份/远程 | 平时 Hub；偶尔切 S3 上传/检查 | 两个独立后端，各留状态；切 S3 首次上传/对账，切回 Hub 用 Hub 的 base |
| S3/WebDAV 主力，局域网辅助 | 平时 S3；偶尔局域网传大文件 | 两个独立后端；局域网首次对账/上传，之后各记各的账 |
| 单后端 | 只用 S3 或 WebDAV | 保持现有单连接模型，不增加额外状态 |

两个设备可以各自选不同后端；此时它们不互相看见，这是预期行为。要互相同步，两台设备必须选同一后端。

## 5. 不做

- 不做 Hub 与 S3 同时 active、同时写。
- 不做“一个仓库多入口”的自动复制/迁移；那是另一层能力，等确有需要再做。
- 不把 LAN 和 S3 的内容当同一份；它们是两个独立仓库。
- 不在首次对账时自动删除任何一边的数据。
- 不改变 /1 协议、块大小、head/history 格式。

## 6. 质量边界

必须守住：

1. 同一设备同一时刻只有一个 active 后端。
2. 每个后端的 base/last/repository_id 独立，不能串用。
3. 切换前检查同步锁/插件运行；切换中不允许后台同步。
4. 首次对账只做上传/下载/冲突，不做删除推断；必须预览。
5. 冲突永远保留副本，不静默覆盖。
6. 目标后端不可达时允许保存选择，但首轮同步报错，不偷偷换回旧后端。
7. 加密状态不一致时拒绝切换。
8. 同一后端被两个库共用时，prefix 必须不同；同 prefix 仍拒绝。
9. 旧后端的 base 不因切换而删除；只有用户明确“清除该后端同步状态”才清。

## 7. 测试矩阵

### store / schema

- 同一库建 LAN 与 S3 两个 BackendState；切换后两份 base/last 都在。
- 切到已有状态的后端，使用该后端 base，不全量。
- 切到没有状态的后端，进入首次对账。
- 删除/重建后端状态；连接/prefix 改变时只失效该后端状态。
- 加密不一致拒绝；同 prefix 共用拒绝。

### engine

- 首次对账：本地空/远端空/两边有/同路径不同 → 上传/下载/冲突，不删除。
- 第二次切换：只传/取差异；大文件改一块只取一块（S12）。
- 冲突副本、删除传播、空扫描/大批删除保护在首次与后续切换都成立。
- 切换时正在同步/有锁/插件运行 → 阻断。

### e2e

- 两台设备都 LAN → 同步 → 都切 S3 → 同步 → 都切回 LAN → 只同步差异。
- A 先切 S3 上传，B 后切 S3 检查/下载，不产生假冲突。
- A 在 S3 改、B 在 LAN 改，切到同一后端产生冲突副本，不丢数据。
- 一台 LAN、一台 S3 时互不看见；都切同一后端后恢复同步。
- 手机/桌面各切换一次，状态行显示当前后端与上次结果。

### 真实 provider

- 七牛/缤纷/本机 DAV 各切一次；上传/下载流量符合预期。
- 首次 S3 上传免费；第二次切换不全量下载。

## 8. 开放问题

- 是否允许“继承来源后端 base”来减少首次切到 S3 的假冲突；第一版先按空 base 安全对账。
- 后端状态是否显示在连接列表（当前后端/上次同步），归 S15。
- 同一库后端数量上限；第一版不设硬上限，UI 只列已配置连接。
