## 1. 当前判断（2026-11-19）

**当前分支**：`base-ui-settings`；基线 = 上游 v1.4.5（`c467a7b5` 已并线）。手机线是当前最活跃的工程线；同步评审完成、S2 内置桌面已到第七片（协议 crate、双 transport、引擎、设置页、冲突/历史、审计修复）；整体仍待 S0a supersede 落档。

**顺序**：

1. **Now**：H3 内置侧代码完成（引擎闸 + 设置页确认），待 built app 复核；S2 继续差分互通与规模/故障验收。
2. **Next（4–9 周；S2 与 D1 择一，D0.5 并行）**：S2 已开工（协议 crate 第一片）；或 D1 资产闭环剩余；S3b 七牛/阿里适配按需；PH3/PH4 手机核查；D0.5 理论验证。
3. **Later（3–6 个月；按人周估算）**：内置同步移动端 → 局域网 Hub → 硬化；D2 受控写入、D3 多端完善。
4. **Ongoing**：上游跟随（下一 tag v1.4.6）、设置遗留、手机打磨、分支收口、文档维护。

**为什么不是直接开内置同步**：内置是 12–22 人周的长项目；插件 spike 只要 1–3 周，能先拿到手机能否可靠上传/下载的真实数据。插件 spike 的前置是宿主文件层（H 组），而这些同时是 D0/D3 的验收项——先做它们不是为同步单独铺路。

## 8. 偏差 / 缺口

- **D-1（2026-11-19，PH1 真机；当日已解决）**：Android 图片选择器返回 `content://com.android.providers.media.documents/...`；规格假设 `pickImageFile` + `copyToImageFolder` 能直接读，实际 `read_binary_file_base64` 只走 `fs::read`，图片实际插入失败。处置：`textus-files` 新增 `pick_image`（带文件名）＋ `read_data`（ContentResolver），`pickImageFile`/`readBinaryFileBase64` 走插件；真机 actual insertion 通过（draft assets URL）。H1 不再承接该项。
- **S2 未验收（2026-11-20）**：第七片只过单测/静态检查；锁恢复、history 迁移、打开文件延后、`Sync conflicts` 展示仍需 built app 真机/桌面复核；与官方插件差分互通、20k 文件、128 MiB 单文件、弱网/崩溃发布注入未做。
- **密钥静态保护（项目级）**：`sync_secrets.json` 沿用 `provider_keys.json` 的 `0600`（Unix）写法；Windows 仅依赖用户目录 ACL，尚未接 DPAPI/Keychain。若要更强保护，应作为全项目密钥存储改造，而不是只改同步。
- **其余暂无。** 下一个真实偏差按 [AI 协作纪律 §六](../01-纪律/AI协作纪律.md) 记「D-2」。
