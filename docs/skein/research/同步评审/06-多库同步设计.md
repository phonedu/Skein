# 多库同步设计

> 状态：讨论稿；已定项已收口进[同步方案 §14](../../specs/同步方案.md)，S2a 已按此实现并归档（2026-11-20）。日期：2026-11-18（2026-11-20/21 注）。
> 关联：[00-汇总与建议.md](00-汇总与建议.md)。
> 本文只回答“多个库怎么同步”，不涉及具体代码实现。

## 讨论记录（2026-11-18，部分已定）

以下为用户已拍板；未列出的仍待讨论。

- **连接配置**：默认**共享一个连接**。
- **新库布局**：默认**子仓库**（`<prefix>/<slug>-<id8>/`）。
- **加密密码**：**每库一个**（覆盖本文 §4.5 原先“每连接一个”的建议；同一连接的多个库可以各自不同密码）。
- **并发**：接受**桌面 2 库 / 手机 1 库**。
- **库的副本**：默认**分叉成新库**。
- **资产库**：**作为主库的子目录**，随主库自动同步（见 §4.13；主库内部的子目录天然随主库同步，不需要“关联库”）。
- **三种同步方式**：局域网 / S3 / WebDAV 是**三种 transport，共用一套同步协议**（见 §4.14）。

## 0. 结论先行

把“多库同步”拆成三层，答案就清楚了：

| 层         | 结论                          | 一句话                                                                                   |
| ---------- | ----------------------------- | ---------------------------------------------------------------------------------------- |
| **数据层** | **一个库一个仓库**            | 每个库自己的 `head/history/lock/base/repositoryId`。**绝不能让多个库共用一个清单。**     |
| **连接层** | **可以共享一个连接配置**      | 同一个 S3/WebDAV 账号下，每个库一个独立远端前缀；不同服务商/不同同步密码的库用不同连接。 |
| **服务层** | **一个同步服务管多个 runner** | 全局状态、暂停、队列、网络策略；每个库一个 runner，远端锁按仓库而不是按连接。            |

所以：

- “不同的库单独同步”——**数据层是对的**；
- “所有库共用一个同步”——**服务层可以，数据层不行**；
- “所有库共用一个仓库/一个清单”——**拒绝**。

## 1. 先区分三种“多库”

不谈清楚这三种，设计一定打架：

| 场景                                 | 定义                                                 | 应该共享什么                                   | 不应该共享什么                                          |
| ------------------------------------ | ---------------------------------------------------- | ---------------------------------------------- | ------------------------------------------------------- |
| **A. 同一库、多设备**                | 一个库（一个文件夹）在手机/桌面/另一台电脑上各有一份 | 远端仓库、`repositoryId`、历史、加密密码       | 本地 base、设备 ID、冲突副本的本地路径                  |
| **B. 同一设备/同一账号、多个独立库** | 工作库、个人库、资产库……内容互不相干                 | 可以共享连接配置、网络策略、调度器             | **仓库、清单、锁、base、加密盐**                        |
| **C. 库的副本/分叉**                 | 用户复制了一个库文件夹，想独立发展                   | 最初的 `vaultId`/`repositoryId` 可作为识别线索 | 之后必须分叉成新 `vaultId` + 新远端仓库，否则两边互相打 |

本文主要回答 B；A 是现有同步模型本来就要支持的；C 是多库设计里最容易漏、后果最重的一种。

## 2. 现状：插件其实已经“按库独立”，但没有全局模型

现有插件：

- 配置按根路径存：`config:<sha256(root)>`（`cloud-sync/src/settings.ts:32-34`）。
- 凭据按 `root + identity` 存：`connection:<sha256(root + identity)>`（`settings.ts:44-46`）。
- base 按 `root + identity + account` 存：`encrypted-base:<...>`（`settings.ts:160-163`）。
- 每个窗口一份 `Controller`/`Pacer`（`host.ts:453-483`），没有进程级单例。
- 没有“库列表”，没有“同步全部”，没有副本检测，没有双开检测。

所以它**事实上是“每库独立同步”**（方案 1），但：

- 两个窗口各跑一份，可能同时对不同库同步，也可能对同一个库重复跑（靠远端锁串行，第二个报 `locked`）。
- 用户看不到全局状态，也不知道另一个库在传什么。
- 库移动/复制后，key 由 `root` 计算，配置和 base 会“消失”。
- 没有“这个库属于哪个连接/哪个远端仓库”的记录。

内置阶段要保留“按库独立”的正确性，同时补上全局模型。

## 3. 四种候选方案

### 方案 1：完全独立（每库一套连接、一个 prefix、一套配置）

```
连接 A（工作 S3） → vault Work   → prefix textus/work
连接 B（个人坚果云）→ vault Personal → prefix textus/personal
```

- 优点：隔离最彻底；不同服务商/不同密码天然支持；迁移简单（沿用插件现状）；一个库坏了不影响另一个。
- 缺点：用户要为每个库重复填账号/密钥；手机输入成本高；没有“同步全部”的一键体验。
- 适用：不同服务商、不同安全级别、不同团队/身份的库。

### 方案 2：共享连接、每库独立仓库、每库独立 prefix

```
连接 A（工作 S3 + 一个加密密码）
  ├─ vault Work     → prefix textus/work
  └─ vault Personal → prefix textus/personal
```

- 优点：一次配置，多库使用；每个库仍是独立仓库（独立清单/锁/base）；迁移时可以直接沿用插件已有的 prefix。
- 缺点：prefix 由用户手填，容易撞名/写错；加密密码被所有库共享（或需要多套连接）。
- 适用：同一个账号下多个库，愿意自己管理 prefix。

### 方案 3：共享连接、统一“同步空间”、每库一个标准子仓库

```
连接 A（S3 + 一个加密密码），根 prefix textus/
  ├─ vault Work     → textus/work-3f2a1c9d/v1/...
  ├─ vault Personal → textus/personal-7b1e42aa/v1/...
  └─ vault Assets   → textus/assets-c09d51fe/v1/...
```

- 优点：一次配置；每个库仍是独立仓库；prefix 由系统生成，不会撞名；UI 可以“同步全部”；迁移时可以“沿用原 prefix”或“搬进空间”（搬是后续能力）。
- 缺点：远端目录多一层；用户手动在 S3 控制台看时是 `slug-id8`；旧插件要指向具体子仓库的 effective prefix，而不是父 prefix。
- 适用：推荐作为**新库的默认布局**。

### 方案 4：所有库共用一个仓库/一个清单（拒绝）

```
prefix/v1/head.json
  files: {
    "work/notes/a.md": ...,
    "personal/notes/a.md": ...,
    "assets/...": ...
  }
```

看起来“一个同步”最简单，实际是灾难：

| 问题                | 后果                                                                                  |
| ------------------- | ------------------------------------------------------------------------------------- |
| 路径命名空间        | 两个库都有 `notes/a.md` 时要么撞名、要么强制加库名前缀，用户移动/改名都会改变远端路径 |
| 一个 base           | 一个库的扫描 bug/授权失效（本地 0 文件）会让 planner 把另一个库的文件也判成删除       |
| 一个清单上限        | 20k 文件/8MB 清单被所有库共享，一个库先触顶，全部停摆                                 |
| 一个锁              | 同步工作库时个人库只能等；长上传会阻塞所有库                                          |
| 一个加密密码/一个盐 | 无法按库不同策略；一个库泄露影响全部                                                  |
| 一个 history/trash  | 删除、版本、保留期跨库混在一起；恢复时容易选错库                                      |
| 冲突副本            | `Sync conflicts/` 在根上，跨库副本混在一起                                            |
| `.textus` 项目数据  | 两个库的 `.textus/agent.md`、`library/` 等路径直接冲突                                |
| 旧插件迁移          | 插件本来就是“一个根 = 一个仓库”，迁移到单清单要重写全部路径和 base                    |
| 用户心智            | 库是一个整体；删除/移除同步应该以库为单位，而不是从一个大清单里摘路径                 |

**结论：方案 4 不进入候选。**

## 4. 推荐模型：方案 2 + 方案 3 的组合

### 4.1 实体

| 实体                  | 作用                 | 关键字段                                                                                                    |
| --------------------- | -------------------- | ----------------------------------------------------------------------------------------------------------- |
| **ConnectionProfile** | 一个存储服务账号     | `id`、provider、endpoint、bucket、region、credentials 引用、默认 prefix、网络策略                           |
| **Vault**             | 一个本地库（文件夹） | `vaultId`（UUID）、显示名、本地路径                                                                         |
| **SyncBinding**       | 库 ↔ 连接的绑定      | `vaultId`、`connectionId`、**effective prefix**、`repositoryId`、**同步密码引用**、自动同步、排除规则、暂停 |
| **Repository**        | 远端的一个 `/1` 仓库 | 由 effective prefix 定位；有 head/history/lock/blocks                                                       |
| **Device**            | 本安装               | `deviceId`、设备名；base 按 `(vaultId, deviceId, repositoryId)` 隔离                                        |

### 4.2 身份规则

- **`vaultId`**：本地库的稳定身份，存 `.textus/sync-vault.json`（**不参与同步**，旧客户端的 `inScope` 本来也不认它）。库移动/改名后跟着走；用户复制库文件夹会得到同一个 `vaultId`——这是副本检测的依据。
- **`repositoryId`**：远端仓库身份。加密仓库已有（加密描述符里）；明文仓库在 head 顶层加一个可选字段（v1 旧客户端会忽略）。用于“这个远端是不是同一个仓库”的判断。
- **`deviceId`**：本安装的稳定 UUID，存 App 数据目录；base/cache/pending 按设备隔离，不能只按 `vaultId`。
- **副本检测**：同一台设备上出现两个不同路径、同一个 `vaultId` → 提示“这看起来是副本”，默认建议“分叉成新库”（新 `vaultId` + 新远端子仓库）；不默认允许两个本地库同时同步同一仓库。
- **跨设备**：两个设备上同一个 `vaultId` 是正常的（同一库的两台设备）；base 按 `deviceId` 分开，互不覆盖。
- **库移动**：`vaultId` 跟着文件夹走；binding 在 App 数据里按 `vaultId` 查找，路径变化只更新本地路径。
- **库改名**：显示名变；**远端 prefix 不变**（否则要搬远端对象）。UI 要写清楚“改名不会改远端文件夹”。

### 4.3 服务模型：一个服务，多 runner

- **一个进程一个 `SyncService`**，不按窗口复制。窗口只发命令、收事件。
- **每个 binding 一个 runner**；runner 有独立状态机、base、cache、pending。
- **远端锁按仓库**：不同库可以并行，同一仓库永远串行。
- **进程内互斥**：同一 effective prefix 只允许一个 runner；两个库误绑到同一仓库时在绑定阶段就拒绝。
- **全局队列**：桌面最多 2 个库同时传，手机 1 个；库内块并发沿用现有参数（S3 4–8、WebDAV 2–4、坚果云 1–2）。
- **连接级限流**：同一个连接下的多个库共享请求预算（坚果云/WebDAV 尤其需要），避免“同步全部”把账号打到 429。
- **全局暂停 / 单库暂停**：全局暂停停所有 runner；单库暂停只停一个 binding。
- **状态聚合**：全局“2 个库同步中、1 个冲突”；展开看每个库的时间/错误/冲突数。

### 4.4 默认远端布局

- **新库**：`<connection.defaultPrefix>/<slug>-<vaultId 前 8 位>/`
  - 例：`textus/work-3f2a1c9d/v1/head.json`
  - `slug` 由库名生成，只用于可读；`id8` 保证唯一；库改名不重命名远端。
- **从插件迁移的库**：**沿用插件原来的 prefix**（例：`textus/work`），不要求重新上传；UI 显示“原 Cloud Sync 远端”。
- **用户手动指定**：允许；绑定前检查该 prefix 下是否已有 `v1/head.json`，有则提示“加入已有仓库 / 换一个 prefix”，绝不静默合并。
- **旧插件兼容**：每个库的 effective prefix 就是一个标准 `/1` 仓库；旧插件把它填进 prefix 就能读写。**不要**让旧插件指向父 prefix（`textus/`），那里没有 `v1/head.json`。

### 4.5 加密密码的归属（已定：每库一个）

- **每个库（SyncBinding）一个同步密码**，即使多个库共用同一个 ConnectionProfile。每个仓库仍各自不同的 salt/`repositoryId`，所以一个库的密钥材料不能解密另一个库。
- **同一个连接下可以有不同密码**：工作库和个人库可以用不同密码，不需要建两个连接。
- **可以复用**：UI 在新建绑定时提供“使用与另一库相同的密码”，但这是用户选择，不是系统强制。
- 理由：隔离更好；从插件迁移时，插件本来就是按 root 存密码（`connection:<hash(root+identity)>`），**每库一个更贴近现状**，迁移更自然。
- 代价：用户要记住多个密码。UI 必须做到：每个库的设置里能看到“这个库的同步密码”（不回显，只显示已设置/未设置 + 更换）；密码管理器提示；丢失不可恢复的警告按库显示。

### 4.6 设置的作用域

| 作用域 | 放什么                                                            | 例子                           |
| ------ | ----------------------------------------------------------------- | ------------------------------ |
| 全局   | 网络策略、默认调度、并发上限、诊断                                | 仅 Wi-Fi 传附件、桌面 2 库并发 |
| 连接   | provider、endpoint、bucket、region、凭据、默认 prefix             | 工作 S3 账号                   |
| 库     | binding、effective prefix、**同步密码**、排除规则、自动同步、暂停 | 工作库排除 `drafts/`           |
| 仓库   | `keepDays`（跨设备共享）、仓库级历史策略                          | 保留 90 天                     |
| 设备   | `deviceId`/设备名、base、cache、pending、lastRevision             | 手机/Mac 各自的 base           |

### 4.7 UI 形态

- **设置 › 同步**（不新增一级入口）：
  - 顶部：全局状态（“2 个库同步中 / 1 个冲突”）+ “同步全部” + “全部暂停”。
  - 列表：每个库一行——库名、连接、effective prefix、状态、最后同步时间、冲突数。
  - 选中一个库：连接、加密、排除、自动同步、历史、冲突中心。
- **手机**：首页脚注显示当前库状态；库切换 sheet 里每个库带一个小状态点；设置页是同一套列表。
- **桌面多窗口**：窗口只“看”自己打开的库；同步页默认选中当前库，也可以看全部库。
- **不要**把“同步全部”做成默认自动行为；新库默认关闭自动同步，用户明确开启。

### 4.8 迁移（多库）

- **按库迁移**：每个库独立 dry-run → 导入 base/凭据 → 停用旧插件（该库）→ 首次同步 → 验证。
- **批量迁移**：扫描 App 已知的 recent folders + 当前打开的库；对每个 root 计算插件配置的 key，存在则列出；用户勾选要迁移的库。
- **每个库独立成败**：一个库认证失败/配额满，不影响其他库；迁移报告按库列出。
- **不导入的情况**：用户选择“重新输入连接”或“换新远端”；此时首次同步可能是空 base，必须 dry-run 并提示可能产生冲突副本。
- **顺序**：迁移成功并验证后，才停用旧插件；**迁移完成前不卸载**（移动端卸载会永久删插件 base/secrets）。
- **双开检测（按库）**：如果插件已启用且该 root 有插件配置，内置对该库禁止自动同步，显示“这个库仍由 Cloud Sync 插件同步”；手动同步也建议先停插件。

### 4.9 副本/分叉

| 情况                       | 检测                                        | 默认处理                                                              |
| -------------------------- | ------------------------------------------- | --------------------------------------------------------------------- |
| 同设备复制库文件夹         | 两个路径同一 `vaultId`                      | 提示“副本”；默认“分叉成新库”（新 vaultId + 新子仓库）；不默认同时同步 |
| 另一台设备复制库文件夹     | `vaultId` 相同、`deviceId` 不同             | 正常多设备；提醒“这是同一个库的另一份，会互相同步”                    |
| 从压缩包/导出恢复          | 没有 `.textus/sync-vault.json`              | 当作新库；用户可手动“加入已有远端”                                    |
| 用户想两个库同步到同一远端 | 同一 effective prefix 被第二个 binding 使用 | 绑定阶段拒绝；提示“换 prefix 或分叉”                                  |

### 4.10 删除与解绑

- **解绑（Remove sync）**：只删本地 binding/base/cache/凭据引用；**不删远端**。UI 明写“云端数据不受影响”。
- **删除远端仓库**：单独的危险动作，二次确认；可以先把 prefix 改名为 `<prefix>.trash-<date>`，保留一段时间再真删（S3/WebDAV 都支持 copy/rename 的成本不同，第一版可以先不做）。
- **删除本地库**：不自动删远端；如果用户勾选“同时删除云端”，走上面的危险动作。
- **库被移走/删除**：binding 仍在；下次打开时提示“库不在了”，可以“重新定位”或“解绑”。

### 4.11 失败隔离

- **一个库的失败不阻塞其他库**：runner 独立状态机；全局队列继续调度其他库。
- **连接级熔断**：同一连接连续 401/403/429/507 时，暂停该连接下的自动同步，通知用户；其他连接不受影响。
- **单库熔断**：某个仓库连续 `invalidManifest`/`invalidHistory`/完整性错误时，只停该库，标记“需要修复”，不反复重试。
- **全局暂停**：用户手动；恢复后按队列顺序继续。

### 4.12 验收矩阵（多库）

| 场景                         | 预期                                              |
| ---------------------------- | ------------------------------------------------- |
| 两个库、同一连接、不同子仓库 | 各自独立同步；远端路径不撞；状态分别可见          |
| 两个库、不同连接/不同密码    | 各自独立；一个 401 不影响另一个                   |
| 同一库、两台设备             | 一个仓库、两个 base；双端收敛；冲突副本按设备可辨 |
| 同设备复制库                 | 提示分叉；不允许两个本地库同时同步同一仓库        |
| 库改名/移动                  | binding 跟随；远端 prefix 不变                    |
| 解绑一个库                   | 远端不动；其他库继续                              |
| 删除远端仓库                 | 二次确认；只影响该库                              |
| 插件 + 内置同一库            | 内置拒绝自动同步并提示；其他库不受影响            |
| 一个库清单损坏               | 只停该库；其他库正常                              |
| “同步全部”中途失败           | 每库独立结果；失败库可重试；成功库不回滚          |
| 连接级限流                   | 同连接多库共享预算；不把账号打到 429              |

### 4.13 资产库：主库子目录，随主库自动同步（已定）

用户已定：**资产库作为主库的子目录**，随主库自动同步。

- 它属于主库仓库，不需要单独绑定，天然随主库同步。
- 资产库里的 Markdown 与附件都在主库文件夹内：
  - 普通文档图片默认落在**文档所在文件夹下的 `assets/` 子目录**（`imageFolder` 默认 `"assets"`；可设为与文档同文件夹，或由文件夹约定/Typora front matter 指定别的子目录）——`src/prefs/image-folder.ts:9`、`src-tauri/src/commands/fs.rs:239-282`。
  - 计划中的证据目录 `attachments/<task-id>/` 也在资产库子目录内。
  - 因此主库同步一并覆盖，不需要额外的“关联库”。
- **不引入“关联库/同步组”作为默认**；只有将来用户把资产库改成独立顶层文件夹时，才需要 linked vault（保留在下面作为备选）。
- 仍然不建议把资产库做成**第二个仓库**再合并清单；它是主库内的子目录，不是第二个仓库。

**备选（如果以后改成独立文件夹）**：把它作为“关联库”（linked vault）绑定到主库的**同步组**：

- 仍然**一库一仓库**（自己的 head/history/base/lock），不合并清单。
- 主库同步时，组内关联库自动按队列同步；主库暂停/恢复也作用于组。
- 状态聚合：主库行显示“含 1 个关联库”；关联库可展开看自己的状态。
- 失败隔离：关联库失败不阻塞主库；主库成功不因关联库失败而回滚。
- 解绑主库不自动解绑关联库；删除关联库的远端要单独确认。

> 现有《改造方案》§4.1/§4.5 写的是独立顶层目录 `asset-library/`（`docs/skein/specs/Textus-改造方案.md:223,304`）。本决定要求改成**主库子目录**（例如 `<vault>/asset-library/`）。等讨论定稿后再回写方案，本轮不改现有文档。

### 4.14 三种同步方式：LAN / S3 / WebDAV（已定：三种 transport，一套协议）

它们是**三种 transport，不是三套协议**。数据层仍是 `/1` 仓库（head/history/blocks/lock），三种方式共用同一套 planner/history/冲突逻辑。

| 方式                        | 数据层   | 当前状态                                      | 还需要补什么                                                       |
| --------------------------- | -------- | --------------------------------------------- | ------------------------------------------------------------------ |
| **S3**                      | 对象存储 | 插件已支持（aws4fetch/SigV4，`transport.ts`） | 内置 Rust transport；条件写/校验；provider 矩阵（AWS/R2/MinIO/B2） |
| **WebDAV**                  | 对象存储 | 插件已支持（Basic/Nutstore 预设）             | 服务器差异（MKCOL/MOVE/HEAD/If-Match）、自签名/HTTP、TLS 策略      |
| **LAN（本地 WebDAV/NAS）**  | 对象存储 | 只要对方是 WebDAV，就是 WebDAV                | 不是新同步功能；只是预设 + 局域网 TLS/HTTP 策略                    |
| **LAN（内置 Hub）**         | 对象存储 | 新功能                                        | 桌面内嵌本地 HTTP/WebDAV 服务 + 发现/配对 + 防火墙/休眠            |
| **LAN（真 P2P，无服务器）** | 新协议   | 不做 v1                                       | 发现、配对、直连、双方存储、冲突；单独立项                         |

建议把“局域网同步”定义为**内置 Hub**：桌面（以后也可 Android）跑一个本地仓库服务，手机连它；复用 WebDAV/ObjectStore，不新造协议。真正的无服务器 P2P 留到以后，不放进 v1。

### 4.15 推荐实施顺序

1. **插件阶段**：S3 → WebDAV。插件不能做 LAN Hub；局域网若已有 NAS/WebDAV，就是 WebDAV。
2. **内置阶段**：协议核心 + fake store → S3 → WebDAV → LAN Hub。
3. 如果“家里手机↔电脑”是最高优先：WebDAV → LAN Hub 可以排在 S3 的产品化之前；但 S3 仍是引擎最便宜的第一个真实 transport，建议保留在 WebDAV 之前做验证。

## 6. 开放问题

> 未定项已汇总到[任务清单 §7 待审/触发点](../../STATUS.md#7-待审--触发点)；U7–U11 归入 S2a 收口。

1. **“同步全部”默认用哪个连接？** 如果用户有多个连接，需要先选一个默认连接，或按库上次使用的连接。
2. **资产库和主库的关系**：如果资产库在主库内部，它就是普通文件夹；如果独立，是否希望“主库同步时自动带上资产库”？建议不自动，避免隐式多仓库操作。
3. **远端子仓库改名**：库改名不重命名远端；如果用户坚持要改，需要一个“搬远端”动作（copy objects + rewrite head），第一版不做。
4. **同一个库在两台设备上用不同连接**（一台 S3、一台 WebDAV）能否指向同一仓库？技术上可以，但凭据/加密必须一致；建议 UI 明确“同一仓库必须同 provider/prefix/密码”，否则拒绝。
5. **多用户共享一个远端仓库**：当前模型不支持（一个仓库一个库），也不建议第一版支持；共享桶请用不同 prefix。
6. **库的“只读”模式**：手机端画板有“手机上只读”开关；如果启用，手机只下载不上传，冲突副本也不产生。这属于单库策略，不是多库问题，但要在 binding 里留字段。

## 7. 一句话回答

**“不同的库单独同步”是数据层必须坚持的；“所有库共用一个同步服务”是服务层可以做的；“所有库共用一个仓库/清单”是必须拒绝的。连接可以共享，仓库不能共享。**
