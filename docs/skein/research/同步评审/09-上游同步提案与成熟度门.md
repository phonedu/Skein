# 同步回馈上游：形态、成熟度门与测试边界

> **背景（2026-11-24 核对）**：`upstream/main` @ `9b94807e` **没有内置同步**——`src-tauri/crates/` 只有 `aicompat`，没有 `textus-sync`；`src/settings/pages/` 没有 Sync 页；上游的同步只有 **Cloud Sync 插件**（独立 `textus-plugins` 仓）。本仓的内置同步是 fork 新增的核心功能。
> **用户裁定**：坚果云不推荐；国内优先局域网 + S3。**回馈上游**可以讨论，但按 [publishing-gate](../../discipline/publishing-gate.md)，用户没点明仓与形式前不动上游。
> **不做**：不把整个 fork 一次性提交上游；不把上游/社区测试当我们的验收门；不在本文里开上游 issue/PR。

## 1. 上游现状

| 项 | 上游 `upstream/main` | 本 fork `base-ui-settings` |
| --- | --- | --- |
| 同步形态 | Cloud Sync 插件（JS/HTML，独立仓） | 内置 Rust 引擎 + 设置页 + 手机 |
| `textus-sync` crate | 无 | 有（planner/history/publish/lock/encryption/transports） |
| Sync 设置页 | 无 | 有（连接/多库/加密/冲突/历史/迁移） |
| 多库 / 连接共享 | 插件无 | 有 |
| 条件写 / 锁 | 插件有，但服务商差异多 | Standard/Oss/Kodo 三 flavor |
| 手机 | 插件可装 | 内置 v1（App Documents/trash/状态） |
| 迁移/回滚 | 无 | S6（插件 → 内置可回滚） |

结论：**“功能”是 fork 的现状，“插件”是上游的现状。** 两者不是同一件事。

## 2. 三种回馈形态

| 形态 | 内容 | 优点 | 风险 / 代价 | 适合谁 |
| --- | --- | --- | --- | --- |
| A. 插件 transport 修复 | 在 Cloud Sync 插件里加 Qiniu Kodo 原生 create、重试/退避、provider 兼容修正 | PR 小；不碰上游核心；直接惠及现有插件用户；能先拿到真实 provider 反馈 | 不能带来内置引擎、多库、原生 trash/keychain、手机内置；插件 API 有边界 | 想低风险回馈、先修 provider 兼容 |
| B. `textus-sync` crate 作为库 | 只提纯 Rust crate + 测试（无 Tauri/UI） | 边界干净；上游可先当独立库评估；PR 可分段 | 上游目前没有 Rust 同步消费方；没有 UI 就没有用户价值，可能被搁置 | 想先让上游评审数据层 |
| C. 内置同步作为核心功能 | 整个引擎 + 命令 + 设置页 + 手机 + 迁移 | 一步到位；原生体验最好 | 体量最大；与上游“同步=插件”的现有路线冲突；需要先 RFC、再分段 PR；周期长 | 上游明确想要内置同步时 |

## 3. 推荐路线

**先插件、后功能；先 RFC、后 PR。**

1. **现在能做的（A）**：把 S3q 的 Kodo 原生 create、429/5xx 重试、provider 判定等**移植进 Cloud Sync 插件**，用我们的真桶与 S3t harness 验证。理由：上游已有插件架构，PR 小、可 review、能立刻让插件用户用上七牛；这也是一次“上游是否愿意接受我们改动”的低成本试探。
2. **想要内置同步（C）时**：先开 **RFC/issue**（不是 PR），带：架构分层、与插件的关系/迁移、真桶与桌面证据、S3t 报告、平台策略、性能/安全边界。维护者认可后再分段提：
   - PR1：`textus-sync` crate + 测试（纯 Rust，无 Tauri）
   - PR2：Tauri 命令 + 设置页 + 迁移（桌面）
   - PR3：手机（App Documents/trash/状态）
   - PR4：多库/加密/冲突中心的剩余部分（按上游要求拆）
3. **不建议**：把 fork 的 `base-ui-settings` 整条分支当一个大 PR；也不要把 `docs/skein/`、内部代号、中文文案带进上游范围。

## 4. 成熟度门（到哪一步再提 PR）

### 4.1 插件 PR（A）的门

- Kodo：真实桶 probe（第二次 614）、首次/改/删/冲突；token 单测；插件 e2e 至少覆盖 create/read/delete。
- 重试：429/502/503/504 的退避与上限；不重试 PUT 造成重复写；`Retry-After` 处理。
- 不回归：Bitiful/标准 S3、WebDAV、现有插件用户的 `/1` 仓库可读。
- 仓库规范：`textus-plugins` 的测试、lint、英文注释/提交；不带 fork 文档与内部代号。

### 4.2 内置功能 PR（C）的门

**数据安全（硬门）**

- 锁：原子 create、412/614/409 语义、崩溃留锁与手动解锁；重复运行不重复发布。
- 发布：snapshot → history → head 顺序、读回校验；失败不写 base。
- 冲突/删除：两份都保留；改 vs 删不丢；空扫描/大批删除保护。
- 加密：新连接默认开；错密码/描述符变化拒绝；迁移后仍可读。
- 迁移/回滚：插件 → 内置 dry-run、双开阻断、断开回滚；插件数据不被动。
- 已知数据丢失问题为零；有外部复现的丢数据报告就先修再提。

**覆盖（硬门）**

- S3t harness 绿：文字/PNG/JPEG/MP4/PDF/二进制/空文件、2 MiB 边界、32 MiB、128 MiB（opt-in）、特殊名。
- 多库/多 prefix/同 prefix 拒绝/共享连接/并发。
- Provider：Bitiful、Kodo、本地 WebDAV、Docker Nextcloud/MinIO（见 §5）；第三方/境外标“未实测”，不写成通过。
- 平台：Windows/Linux/macOS 至少编译与设置页 smoke；Android 真机/模拟器；iOS 只做能做的 gating（本机无 Apple 设备）。
- 门禁：`npm run check`、`cargo test`、`check:native`、e2e、built app smoke、启动预算、10 语言包。
- 规模：20k 文件、128 MiB、锁恢复；S5 的 32 MiB 预算与 128 MiB 峰值给出结论。

**产品/上游适配**

- 与插件共存/迁移的 UX 定稿；默认不自动同步；设置页不破坏上游现有设置结构。
- 维护者明确同意“内置同步”方向与拆 PR 方式（RFC 通过）。
- 英文注释/提交/文档；无 `docs/skein/`、无内部代号、无中文（`src/i18n/` 豁免）。
- 依赖审查：`reqwest`/`hmac`/`sha1`/`base64` 等新增依赖的必要性与体积。
- 安全：凭据存储（Keychain/Credential Manager/Keystore）、日志脱敏、重定向/TLS 策略。

**建议时点**

- A（插件）：Kodo + 重试在插件里跑通即可，不必等 S5。
- C（内置功能）：**S3t 全绿 + S5 核心安全项（signed head/lastRevision/GC/凭据/预算）+ 维护者 RFC 同意**之后；S4 LAN Hub 可作为后续 PR，不阻塞首轮。

## 5. 测试：Docker 与家用 NAS

### 5.1 本机现状

- 当前机器**没有 Docker，也没有 WSL**（2026-11-24 核对）。要用容器，需要先装 Docker Desktop + WSL2；这会改机器环境，属于用户决定。
- 不装 Docker 也能覆盖一部分：
  - **MinIO**（Windows 单文件）：标准 S3；验证 `If-None-Match`/HEAD/GET/PUT/DELETE。
  - **rclone serve webdav / dufs**（单文件）：最小 WebDAV；验证 MOVE/MKCOL/HEAD。
  - **sabre/dav**（PHP）或 Apache mod_dav：更接近经典 DAV 实现。
  - **Nextcloud 演示实例**：只做冒烟，不稳定、不适合大文件。

### 5.2 容器化后能覆盖什么

| 容器/服务 | 近似对象 | 能证明 | 不能证明 |
| --- | --- | --- | --- |
| Nextcloud（官方镜像 + DB） | 自建/托管 Nextcloud | 标准 DAV：MKCOL/MOVE/HEAD/大文件/应用密码 | 商业限流、NAS 反向代理、自签证书 |
| MinIO | AWS/R2/B2 的标准 S3 | SigV4、条件 PUT、HEAD/GET/DELETE、分块 | 各家边缘行为、配额/限流 |
| dufs / rclone serve webdav | 极简 DAV、家用小服务 | MOVE/Overwrite/404/412 语义 | 完整 DAV、锁、2FA |
| Apache mod_dav / sabre/dav | 经典企业 DAV | 老实现的状态码/路径行为 | NAS 厂商定制 |
| SeaweedFS / Garage | 另一类 S3 | 条件写与一致性差异 | 商业云 |

**家用 NAS（群晖/威联通）**：物理设备测不了；容器 Nextcloud 只能近似标准 DAV，NAS 的 WebDAV Server 包、反向代理、自签证书、休眠/唤醒仍是外部项。可以请有 NAS 的用户/上游测试，结果记“外部反馈”。

**LAN Hub（S4）**：容器可当“局域网里的 WebDAV 服务”测发现/配对的一半；真正的同 Wi-Fi、防火墙、睡眠唤醒需要第二台设备/手机，仍归真机。

### 5.3 建议的落地方式

- 在 S3t 里加 `--provider nextcloud|minio|dufs` 的 compose/binary profile；默认只跑已有真桶，Docker 场景显式开启。
- 先做 **MinIO + dufs**（无需 Docker，单文件即可），再决定是否装 Docker Desktop 跑 Nextcloud。
- 境外 provider：由上游/社区开发者用真实账号跑同一份 harness/清单；报告记“外部反馈”，不写成我们的验收。
- 家用 NAS：不阻塞；等有测试者再登记。

## 6. 不建议

1. 把 fork 整条分支当上游 PR；上游 review 不了，也不符合发布闸门。
2. 先提 PR 再问方向；正确顺序是 RFC/issue → 维护者同意 → 分段 PR。
3. 把未实测的 provider 写成“支持”；上游用户会按支持矩阵使用。
4. 用上游当我们的测试门；外部证据无法复现，也不能替代 S3t。
5. 把 Docker/家用 NAS 的近似结果当成商业服务商验收。

## 8. 执行顺序与时间

原则：先做本仓能验证的，再碰上游；上游动作以门禁为准，不以日历承诺。

| 阶段 | 动作 | 仓库 / 形式 | 前置 | 估算 |
| --- | --- | --- | --- | --- |
| 0 | S3t1 harness：双实例、文字、报告、清理 | 本仓 | 无 | 1–2 天 |
| 1 | S3t2：媒体/大文件 + MinIO/dufs profile | 本仓 | S3t1 | 2–3 天 |
| 2 | 插件 Kodo + 重试原型与测试（本地，不推送） | `textus-plugins` 的临时 clone | S3t2 的 Kodo 证据；用户同意准备插件改动 | 3–5 天 |
| 3 | 插件 PR（提交上游） | `CatVinci-Studio/textus-plugins`，`pr/<主题>` | 用户明确“可以给插件提 PR”；全新 clone；英文；测试绿 | review 周期不定 |
| 4 | S3t3 多库 + S3t4 边界 + S5 核心安全项 | 本仓 | S3t2 | 3–5 天 + 2–3 周 |
| 5 | 内置同步 RFC/issue（**不是 PR**） | `CatVinci-Studio/Textus` 的 issue/discussion | S3t 全绿 + S5 核心项 + 维护者愿意谈 | 1–2 天写 + 讨论 |
| 6 | 分段 PR：crate → 桌面 → 手机 → 迁移 | `CatVinci-Studio/Textus`，各自 `pr/<主题>` | RFC 同意；全新 clone；英文；发布闸门全绿 | 按拆分的 PR 估 |

**现在能做的**：阶段 0、1（本仓）。阶段 2 需要你一句“可以准备插件改动”并指定仓库；阶段 3 需要你明确“可以给 `textus-plugins` 提 PR”。阶段 5/6 需要维护者先认可方向。

**现在不做的**：不 contact 上游；不在 `C:/Project/textus-plugins`（e2e 用的上游 checkout）上留未提交改动；插件原型用临时 clone，避免污染。

## 9. 插件改动如何回馈 fork

| 上游插件的变化 | 会自动到 fork 吗 | 我们的处理 |
| --- | --- | --- |
| 插件代码 / UI（transport、页面） | **不会**进内置 Rust 引擎 | 需要时更新 `C:/Project/textus-plugins` checkout；只影响 e2e/catalog，不影响引擎 |
| `/1` 协议或语义变化 | 不会自动，但**必须兼容** | 内置继续读写同一仓库；靠 S6 互操作与真机测试发现；必要时手写移植 |
| 新 provider / 服务商经验（限流、MOVE 差异等） | 不会自动 | 把语义与坑记进 08；需要时在 Rust 里做对应 flavor |
| 插件 host API / 规范变化 | e2e 可能变红 | 更新 checkout，按 testing.md 处理版本错位 |
| 我们提交的插件 PR 被合并 | 代码不回 Rust | pull 插件 checkout 得到验证与 e2e 覆盖；内置引擎仍独立 |
| 上游将来做内置同步 | 不适用 | 那就是另一套代码；以协议兼容和迁移为界 |

结论：**插件回馈是“验证 + 经验 + e2e”的回馈，不是代码回灌。** 想让内置引擎直接受益，只有两条路：把同样的语义手工移植进 Rust，或把内置同步本身推上游。两者都按 §4 的成熟度门走；不要为了“回馈”在 fork 里维护一份插件补丁，那会和上游 drift。
