# 架构与维护评审（子代理）

> 来源：子代理独立评审，2026-11-18；只读分析，未修改任何文件；未经逐条人工复核。
> 路径缩写：`T` = `C:/Project/Textus`，`P` = `C:/Project/textus-plugins`。

---

## 1. 结论

**方向可行，但“插件多端 → 内置”应被定义为一次有退出条件的 spike + 迁移，而不是“把插件翻译成 Rust”。** 现有云同步插件已经是 4,300 行左右、协议语义相当完整的实现；Rust 内置要兼容 `textus-cloud-sync/1`，本质上是在第二语言里重实现整套同步协议。若没有协议规范、共享向量和双实现互通测试，语义漂移几乎必然发生，后果不是“界面不一致”，而是两端互相制造冲突副本、重复上传、甚至拒绝读取远端。

### 1.1 推荐架构

```text
[协议规范 + 向量]  docs/skein/... + T\src-tauri\crates\textus-sync\tests\vectors
        │
[textus-sync crate]  纯 Rust、无 Tauri：
  model / content / config / scope / planner / history / publish /
  engine / crypto / transport(ObjectStore) / local(LocalFiles trait)
        │
[T\src-tauri\src\sync]  Tauri 适配层：
  service / commands / config+secrets / local fs / events / lifecycle / migrate
        │
[T\src\platform\ipc-sync.ts + T\src\platform\bindings\sync.ts]
        │
[T\src\features\sync]  lazyModule：
  Settings 页 / 状态 / 冲突中心 / 历史
```

**模块边界（问题 1）**

- **核心放 `T\src-tauri\crates\textus-sync`，不放 `src-tauri/plugins/`。** `plugins/` 是给需要 iOS/Android 原生桥的 Tauri 插件用的（`T\src-tauri\plugins\textus-files` 就是 Swift/Kotlin 桥）；同步是纯 Rust HTTP + 文件，不需要原生插件壳。`crates/` 与 `crates/aicompat` 的定位一致：无 Tauri、可单测、可被 app 依赖。`T\docs\dev\architecture.md:252` 把 aicompat 描述为“no Tauri in it”，同步核心应遵循同一形状。
- **app 适配层放 `T\src-tauri\src\sync/`，与 `plugins/`、`schedule/`、`background/` 平级。** 它复用 `atomic`、`net`、`app_dirs`、`json_file`、`trash`、`settings::file_name/dir_name`、`errors`、`settings::emit_to_all`；核心 crate 不依赖 app crate，避免循环。
- **不要做成 `src-tauri/plugins/textus-sync` Tauri 插件 crate**：它拿不到 app 的私有 helper（`app_dirs`、`atomic`、`json_file`、`net`），只能复制一套，违反 `T\docs\dev\reuse.md` 的“one place per need”；而且 `T\scripts\check-code-shape.mjs:54-56` 只检查 `src-tauri/src` 与 `src-tauri/crates`，不检查 `src-tauri/plugins`，放 `plugins/` 会绕过 500 行规则。
- **服务单例**：Rust 进程内一个 `SyncService`，管理多个 folder runner；按 remote identity 串行化（同一 S3/WebDAV 前缀只允许一个 run）。窗口只发命令、收事件，不再像插件那样每个窗口各起一个 `Controller`（`P\development\cloud-sync\src\host.ts:453-483` 是每个窗口一份，`T\src\plugins\manager.ts:113-167` 的 `loadPlugins` 每个窗口各跑一次）。
- **cfg**：核心 crate 里不要用 `cfg(desktop)`。`tauri-build` 只给 app crate 设置这个 cfg（`T\docs\dev\ios-code-map.md:11-15`）；`T\src-tauri\plugins\textus-files\src\lib.rs:41-53` 已经在用 `#[cfg(any(target_os = "ios", target_os = "android"))]`，这是正确先例。核心用 `target_os` 或 feature，适配层才用 `#[cfg(desktop)]`。

**数据与服务边界（问题 4、5）**

- 远端：严格保持 `v1/head.json`、`v1/history.json`、`v1/lock.json`、`v1/blocks/<xx>/<hash>`、`v1/snapshots/<uuid>.json`、`v1/pending/<uuid>.json`；加密态 `v2/...`（`P\development\cloud-sync\src\model.ts:2-15`，`P\...\encrypted-store.ts:41-56`）。不新增旧客户端会误读的远端文件。
- 本地：`config/sync[.dev]/{config,secrets}.json`；`data/sync[.dev]/<folder-id>/{base,cache,pending,status}.json`。**P1 不建议上 SQLite**：协议自己把文件数限制在 20,000（`P\...\model.ts:8`），base/cache/pending 都是几十 MB 以内的有界 JSON；插件的 base/pending 本来就是 JSON（`P\...\settings.ts:160-163`，`P\...\pending.ts:111-121`），直接复用形状还能降低迁移成本。SQLite 的 C 编译、移动端交叉编译、迁移、锁竞争，都是为“有界数据”付出的不必要成本；等资产检索真的需要 FTS5 时再单独评估。
- 用 `settings::dir_name`/`file_name` 的 `.dev` 约定隔离 dev 与安装版（`T\src-tauri\src\settings\store.rs:16-28`）。现在插件数据没有这个隔离（`T\src-tauri\src\plugins\mod.rs:105-122` 直接 `own_data_dir()/plugins`），dev 与安装版可能对同一远端双重同步；内置不要重复这个坑。
- 密钥：沿用 owner-only 文件（`T\src-tauri\src\plugins\files.rs:145-231`，`T\src-tauri\src\atomic.rs:107-111`），不把同步密码放 SQLite/日志。Keychain/Keystore 作为 P2，不作为 P1 前置；全仓目前没有任何 keychain 调用，突然引入会多出三端原生代码和备份/锁屏语义。
- 设备 ID：config 里持久化 UUID + 可读名（“Mac 3f2a”），不要用主机名/MAC；`Origin.device` 最多 64 个 UTF-16 单元（`P\...\history.ts:32-40`）。
- 错误：核心返回 `{code, args}` 稳定错误码，适配层转成 UI 文案；不要把 Rust 英文串直接给用户。全局 `errors.json` 只放少量顶层码（`T\src-tauri\src\errors.rs:20-28`，`T\src\utils\error-explain.ts:57-64`），同步细节码由 sync feature 自己的错误表覆盖，并测试所有 10 个 locale 都有模板。

**启动与懒加载（问题 4）**

- 启动只做一件事：读一次 `config/sync/config.json`；没有配置就返回，不建索引、不开网络、不起 watcher。`T\src-tauri\src\lib.rs:191` 对 background 的“off 时一次 settings 读”是同一纪律。
- 前端唯一入口 `T\src\features\sync\lazy.ts` 用 `lazyModule("sync-feature", () => import("./index"))`，模式照 `T\src\features\settings\lazy.ts:12-16` 与 `T\src\features\settings\settings-module.test.ts`。Settings 页用 `lazyComponent` 挂进 `T\src\settings\builtin-pages.tsx:21-49` 的映射，避免把整页打进 Settings chunk。
- 状态条 P1 建议只放在 Settings 页和错误 notice；窗口栏状态是额外上游文件改动（`T\src\app\frame\WindowBar.tsx:24-31` 已有插件状态的 lazy 模式，可 P2 再照做）。实际预算要按 **1.00 MB** 算：`T\vite.startup-budget.ts:7` 是 `1_000_000`，而 `T\docs\dev\code-style.md:76` 还写着 1.25 MB，文档已过期。

**依赖与体积（问题 3）**

P1 的“零重型新依赖”方案是可行的：

| 用途            | 复用已有                                                                      | 新增           | 说明                                                                                                 |
| --------------- | ----------------------------------------------------------------------------- | -------------- | ---------------------------------------------------------------------------------------------------- |
| HTTP/S3/WebDAV  | `reqwest`（`T\src-tauri\Cargo.toml:80`）                                      | 无             | 复用 app 的 `net::public_client` 代理/超时策略（`T\src-tauri\src\net.rs:21-37`）                     |
| 哈希            | `sha2`（`Cargo.toml:79`）                                                     | 无             | SHA-256                                                                                              |
| 加密            | `ring`（已在 lock，`T\src-tauri\Cargo.lock:3734`）                            | 无（直接依赖） | ring 0.17 已有 PBKDF2-HMAC-SHA256、HKDF、HMAC、AES-256-GCM；与 WebCrypto 语义可对齐                  |
| 时间/JSON/编码  | `chrono`、`serde_json`、`base64`、`percent-encoding`、`unicode-normalization` | 无             | 已全部在树                                                                                           |
| UUID            | `uuid`（目前只在 desktop 依赖，`Cargo.toml:160-171`）                         | 移到共享依赖   | 或直接用 `getrandom` 生成 v4；不要留成 mobile 缺失                                                   |
| 本地状态        | 无                                                                            | 无             | JSON + `atomic`；不引入 `rusqlite`                                                                   |
| 文件监听        | 无                                                                            | 无 P1          | 周期扫描 + 保存/重命名/删除事件 + focus 已够；`notify` 是 P2 桌面加速项，不是正确性依赖              |
| SigV4           | `ring` + `sha2` + `chrono`                                                    | 无             | 手写约 200 行，跑 AWS SigV4 测试向量；不要引入 `aws-sdk-s3`                                          |
| 文本 diff/merge | 无                                                                            | 无             | `/1` 的冲突是“保留双方副本”（`P\...\planner.ts:82-87`），不需要 `diffy`；引入 merge 会制造第三种语义 |

`aws-sdk-s3` 是体积/编译时间的主要风险：它会拉 aws-smithy 一串 crate，移动端交叉编译面也大；`aws-sigv4` 相对小但仍不如手写可控。`rusqlite` 的 bundled SQLite 是第二个风险：C 编译、iOS/Android 工具链、约 1 MB 级体积；在 20k 文件上限下收益不足。`notify` 只在桌面可用，放 `[target.'cfg(not(any(target_os = "ios", target_os = "android")))'.dependencies]` 或 P2 再加。

**复用与协议（问题 2、9）**

- 不共享代码，只共享**协议规范 + 测试向量 + 文案**。插件的纯函数模块已经分得很好：`planner`、`history`、`content`、`encryption`、`scope`、`pending`、`pool`、`pacer` 都可直接产出向量；`engine` 的 `ObjectStore`/`LocalFiles` trait 也已经把副作用隔离（`P\...\model.ts:120-148`）。
- 在插件里先补三件事：**可注入的 clock/uuid**（现在 `engine.ts`、`publish.ts`、`pending.ts` 里直接用 `new Date()`/`crypto.randomUUID()`，无法生成确定性向量）、**Node CLI harness**（用 `LocalFiles` 的 Node `fs` 实现跑完整 engine）、**fixture remote**（plain/encrypted 各一套）。这三件事不改变插件行为，却能让 Rust 侧做差分测试。
- 协议所有者只能有一个。建议：插件 0.6.x 作为 `/1` 的参考实现；内置发布后，内置成为规范所有者，插件冻结（只修安全），或明确支持窗口。两套都持续演进 = 必然漂移。

**发布与维护（问题 8）**

- 这是计划自己定义的“深度分叉”：`T\docs\skein\specs\Textus-改造方案.md:772` 把“同步”列在深度分叉一栏，且“不建议”；阶段 1 还写着“不改同步”（同文件 `:650`），D3 只要求“第三方同步说明与冲突提示”（`:684`），§11 裁决是“首版第三方，自建放最后”（`:742`）。**在写代码前必须先改这份裁决并留档**；否则实现本身违反了仓库的唯一真相源。注意区分“自建云/账号体系”（`:725` 明确不做）与“用户自有 S3/WebDAV 的内置客户端”——后者不是托管云，但仍是宿主同步机制，属于 `:772` 的深分叉。
- 发布：`docs/releases/next/` 新片段；工程文档放 `docs/skein/`（spec/方案），不重写上游 `docs/dev/*`；不要碰 `docs/dev/plugins/reference.md`（生成文件）。
- 格式承诺：`textus-cloud-sync/1` 与 `textus-cloud-sync-e2ee/1` 在 1.x 内只增可选字段，不改语义；未知 `format` 一律拒绝，不自动迁移、不原地重写。回滚：关闭内置、重开插件，远端仍可读；本地 base 丢失只会触发一次“首次同步”，最坏产生冲突副本，不丢数据。
- 上游若将来自己内置同步：本 crate 可整体移除；因为格式相同，迁移成本低。这是把同步隔离在 crate 里的主要理由之一。

**工作量（问题 10）**：不是一个小改动。插件非测试源码约 4,317 行（其中 engine/protocol 约 3,100 行）；Rust 忠实移植 + 向量 + 传输 + app 适配 + React 页面 + 移动端文件后端，粗略 12–22 人周；桌面 P1 约 9–14 人周。最大不确定性在 iOS/Android 文件后端，不在 Rust 协议层。

### 1.3 “薄 fork”影响评估

**文件数可控，机制上是深分叉。** 需要触碰的上游文件大致是：

- `T\src-tauri\Cargo.toml`（workspace member + 依赖）
- `T\src-tauri\src\lib.rs`（`mod sync;` + 一次 `sync::init(app)`）
- `T\src-tauri\src\invoke_handler.rs`（一组命令）
- `T\src-tauri\src\bindings.rs`（一个 bindings group）
- `T\src\settings\settings-pages.tsx` + `T\src\settings\builtin-pages.tsx`（一个页面注册）
- `T\src\utils\events.ts` + `T\src\app\useSaveWrites.ts`（如果要“保存即同步”事件）
- `T\src\app\tabs\useTabState.ts` 或 `useWindowDocuments`（open-docs 注册表）
- `T\src\i18n\locales\*.ts`（10 个）
- 可能 `T\src-tauri\Info.ios.plist`（本地网络/加密出口合规）
- 可能 `.github/workflows/ci.yml`（真实服务器/差分测试，单独 PR）

这已经超出 `T\docs\skein\discipline\薄fork魔改原则.md:29-31` 列的五个接入点（导航、capabilities、tauri.conf、i18n、插件权限表）。**必须把“后端服务注册（lib.rs/invoke_handler/bindings）”和“Settings 页注册”补进 patch 清单**，否则下一次 rebase 会按旧清单漏检。

降低冲突的写法：

- 核心全部放 crate；app 适配只留一个 `sync::init(app)`，lib.rs 只加两行；
- 命令用一个宏在 `sync` 模块里展开，invoke_handler 只加一行块；
- Settings 页只在一处注册，组件用 `lazyComponent`；
- P1 不动 `WindowBar`、菜单、tray、`docs/dev/*`；
- 通用宿主钩子（open-docs 注册表、file-saved 事件、移动端文件/回收站 API）优先尝试提回上游（按 `publishing-gate.md` 在全新 clone 里做），把分叉面留给同步本身；
- 每个上游 release 后记录实际冲突文件与人天；超过计划 §12.7 的“3 人天/两次 release”就触发回退评估。

## 2. 盲区清单（按严重程度）

### [P0] 2.1 决策与文档冲突：这是计划自己定义的“深度分叉”

- **问题**：仓库现状不包含“内置同步”的裁决、任务或规格；相反，阶段 1 写“不改同步”，§11 写“首版第三方，自建放最后”，§12.2 把“同步”列为深度分叉且不建议。
- **证据**：`T\docs\skein\specs\Textus-改造方案.md:650`、`:684`、`:694`、`:725`、`:742`、`:772`；`T\docs\skein\05-状态\Textus-改造任务清单.md:113`（D3 验收只有“同步冲突不静默覆盖”）；`T\docs\skein\discipline\薄fork魔改原则.md:29-31`。
- **后果**：实现一开始就绕开唯一真相源；后续无法判断“做到哪算完成”；维护姿态从“薄 fork”变成事实上的深分叉，却没有对应的成本预算。
- **建议**：先写一份 supersede 记录（为什么插件不够、验证了什么、自建客户端与“自建云/账号”的区别、维护与退出条件），更新 D3/任务清单和 patch 清单；用户签字后再动代码。
- **验证**：`docs/skein/` 中出现裁决记录、任务拆解、验收口径；没有则 P0 不通过。

### [P0] 2.2 两套实现、没有协议规范/向量：语义漂移是默认结局

- **问题**：`textus-cloud-sync/1` 目前只由插件代码定义，没有独立规范或机器可读向量；内置是第二套实现。
- **证据**：远端常量与上限在 `P\development\cloud-sync\src\model.ts:2-15`；同步决策在 `P\...\planner.ts:18-59`；发布顺序在 `P\...\publish.ts:91-101`；加密在 `P\...\encryption.ts:4-7`、`:113-159`；加密键映射在 `P\...\encrypted-store.ts:41-56`；作用域/排除规则在 `P\...\config.ts:174-197`、`P\...\scope.ts:20-122`；冲突命名在 `P\...\planner.ts:82-87`。插件的 82 个协议/逻辑测试（`P\development\cloud-sync\README.md:22-24`）只验证 JS 自己。
- **后果**：任何一处差异都会让两端对“谁改了、谁删了、谁是冲突”判断不同：重复上传、重复冲突副本、`invalidManifest` 拒读，严重时两端互相覆盖 base。
- **建议**：把 `/1` 冻结为规范；用插件纯函数生成 `planner/scope/history/encryption/content/config` 向量，内置测试读取；再做一个 Node CLI 对同一 remote fixture 跑完整 engine，与 Rust 结果比较。协议所有者只保留一个。
- **验证**：Rust 全量通过向量；差分测试在 plain/encrypted/conflict/delete/rename 五类场景下 remote 归一化状态一致；故意改一个向量能让测试失败。

### [P0] 2.3 跨语言陷阱：UTF-16 长度、AAD JSON、排序、时间、BOM

这些不是“实现细节”，而是会直接导致远端不可读或路径被拒的协议语义。

- **问题/证据**：
  - JS 的 `.length` 是 UTF-16 码元：`relativePath` 的 1024 上限（`P\...\config.ts:40-56`，`:42`）、`validatePassword` 的 12–1024（`P\...\encryption.ts:32-35`，`:33`）、`device` 的 64 上限（`P\...\history.ts:32-40`，`:36`）。Rust 用 `chars().count()`/`len()` 会接受/拒绝不同的字符串（例如 10 个 emoji 的密码在 JS 是 20 个长度单位，在 Rust 是 10 个字符）。
  - 加密 AAD 是 `` `${context}\n${key}` ``，`context` 是 `JSON.stringify(header(metadata))`，字段顺序固定为 format/repositoryId/kdf/iterations/salt（`P\...\encryption.ts:24-30`、`:113-125`）。Rust 必须产生**逐字节相同**的 header JSON，否则已有加密远端无法解密。
  - `plan` 用 `Object.keys(...).sort()`（`P\...\planner.ts:24-30`），JS 默认按 UTF-16 码元排序；Rust `str` 按 UTF-8/码点排序，对补充平面字符（emoji）与 BMP 字符的相对顺序不同。它会影响 action 顺序、manifest 键顺序，极端情况下影响冲突副本命名。
  - `changed` 用 `JSON.stringify([files, trash])` 比较（`P\...\publish.ts:47-51`）；Rust 用 map 相等比较更稳，但要注意“内容相同、键序不同”不应发布新 head。
  - 服务器时间：`store.now()` 读响应 `Date` 头（`P\...\transport.ts:36-38`、`:89-90`），用于 trash/history 老化；Rust 要解析 RFC 1123 并在缺失时回退本地时间。
  - 文本写入：`TextDecoder("utf-8", {fatal:true, ignoreBOM:true})`（`P\...\local.ts:239-253`）会保留 BOM 为 U+FEFF；Rust 用 `String::from_utf8` 也要保留，不能 `trim_start_matches('\u{feff}')`。
- **后果**：同一密码/路径在插件可用、内置拒绝；内置写出的加密 header 让插件解不开；两端 conflict 文件名不同，产生重复副本。
- **建议**：规范里单列“跨语言约束”；Rust 实现 `utf16_len`；header 用固定字段顺序的 struct 序列化并做 golden 字节测试；排序实现 JS 等价的 UTF-16 比较器；时间统一 RFC3339 毫秒；BOM/非法 UTF-8/NFD 都进向量。
- **验证**：固定输入下 JS/Rust 的 header 字节、密钥、HMAC 名、密文（同 IV）一致；emoji/CJK/NFD/组合字符/控制字符路径的 plan 与 conflict 名一致；属性测试对随机字符串比较两端长度判定。

### [P0] 2.4 移动端：删除、文件访问、文件身份是硬阻塞，不是“适配一下”

- **问题/证据**：
  - 插件删除本地文件走 `api.files.trash`（`P\...\local.ts:192-201`）；Rust 的 `user_file_to_trash` 在非 desktop 直接返回错误（`T\src-tauri\src\atomic.rs:397-416`，`:409-415`）。所以**当前插件在 iOS/Android 上无法传播远端删除**，`remove` 会抛错，sync 中止。
  - Android 的 SAF 文件夹是 `content://`，前端走 `scoped-folder.ts`（`T\src\platform\scoped-folder.ts:1-15`）；只有用户授予“所有文件访问”后 `beginAccess` 才返回普通路径（`T\src-tauri\plugins\textus-files\android\src\main\java\TextusFilesPlugin.kt:35-37`、`:257-316`）。Rust 内置用 `std::fs` 无法遍历 `content://`。
  - iOS 的 security-scoped 文件访问和 iCloud 协调在原生插件里：`NSFileCoordinator` 读写（`T\src-tauri\plugins\textus-files\ios\Sources\TextusFilesPlugin.swift:11`、`:194`、`:308`），启动时 `restoreFolderAccess` 才恢复书签（`T\src\platform\native-files.ts:163-176`）。Rust 直接用 `std::fs` 写，既可能没有 scope，也绕过了 iCloud 协调。
  - iOS app 容器路径会随每次安装/更新变化，仓库已有 `documents:` 相对路径机制（`T\src\platform\documents-path.ts:4-8`，`T\docs\dev\storage.md:98-101`）；内置若把绝对 root 存进 config，更新后配置失效。
- **后果**：插件多端 spike 会在“删除”这一最基本的同步语义上失败；内置移动端要么不能扫 SAF，要么绕过 iCloud 协调导致文件冲突/损坏；iOS 文件夹配置在更新后失灵。
- **建议**：移动端 `LocalFiles` 必须有原生后端：给 `textus-files` 暴露 Rust 可调的 `read/write/list/rename/delete/stat`（走 Swift/Kotlin 的 coordinated API），或让同步服务在移动端通过该插件执行 I/O；删除用 app 管理的回收站（`data/sync/trash/...`，不进 vault），不是系统 Trash；config 存稳定 folder handle（iOS bookmark URL / Android tree URI，或 `documents:<rel>`），启动时解析成当前路径再交给服务；Android 明确“要求所有文件访问”还是“实现 content:// 后端”。
- **验证**：iOS/Android 真机上完成“新建→修改→删除→重命名→冲突”五项；iOS 更新/重装后 folder 仍可解析；iCloud Drive 文件夹写入不产生额外冲突；Android 拒绝所有文件访问时给出清晰降级提示。

### [P0] 2.5 打开/脏文档安全：Rust 没有“哪些文件正开着”的信息

- **问题/证据**：插件在写本地前查 `api.layout.tabs()`，任何打开的文件都 `deferred`（`P\...\local.ts:53-57`、`:222-269`）；已有文本文件通过 `files.process` 的 tab revision/token 写（`T\src\plugins\host\broker-files.ts:80-90`）。Rust 侧 `WindowSession` 只有 paths/layout/folder，没有 dirty 状态（`T\src-tauri\src\commands\session.rs:15-21`），而且是 desktop-only。保存时前端会重读 mtime 并询问是否覆盖（`T\docs\dev\documents.md:85-90`）。
- **后果**：内置直接写打开中的干净文件，`useExternalChangeReload` 会重载，尚可；写打开中的脏文件，用户下一次保存会看到“文件已变，是否覆盖”，容易误覆盖同步下来的版本；最坏是用户在两个窗口间丢失编辑。
- **建议**：新增每个窗口的 open-docs 注册表（path + kind + revision，必要时 dirty），窗口变化时上报、销毁时清除；服务对任何 open path 一律 defer（照插件语义）；下载先写同目录临时文件 + fsync + 原子 rename，并在 rename 前再次校验本地 hash；保存路径发一个通用 `file-saved` 事件给服务。
- **验证**：built app 中打开干净/脏文件各一，触发远端更新：干净文件重载、脏文件 defer 且不覆盖、保存后下次 sync 产生冲突副本而不是静默覆盖；Rust 单测用 fake registry 覆盖同样分支。

### [P0] 2.6 服务生命周期、单例、移动前后台、远端锁

- **问题/证据**：插件是每窗口一份 `Controller`（`P\...\host.ts:453-483`），每个窗口一个 Pacer/定时器；`onStartupFinished` 在每个窗口都触发（`T\src\plugins\contributions\plugin-contributions.ts:258-260`，`T\src\plugins\manager.ts:113-167`）。移动端没有 background/schedule（`T\docs\dev\plugins\guide.md:400-451`、`:558-581`）；Tauri 有 `RunEvent::Resumed`，但没有 `Suspended`（Tauri 2.12 app.rs:220-252）。远端锁没有过期，崩溃/挂起后需要手动恢复（`P\...\engine.ts:121-129`，`P\...\connection.ts:38-73`）。
- **后果**：多窗口时 N 份扫描/N 个定时器，第二个窗口经常报 `locked` 错误；移动端切后台可能带着锁被挂起，下次恢复被自己的旧锁挡住；无窗口/后台模式下是否继续同步没有定义。
- **建议**：一个进程一个服务；按 folder/remote identity 串行；启动只在有配置时；移动端 `RunEvent::Resumed` + 前端 `visibilitychange` 做 catch-up/pause；退出时取消、保存 pending、尽力释放锁；持久化“本设备上次 lock id”，恢复时若远端 LOCK 是自己的，可安全地 remove→create 接管（其他设备的锁仍只允许人工确认）；明确桌面无窗口时是否继续（建议：进程活着就继续；Windows/Linux 只有 background mode 才活着；macOS 关窗后继续，需在设置页说明）。
- **验证**：三窗口同时开同一 folder：只有一个 sync 在跑，其他显示“另一窗口同步中”而非错误；移动端同步中切后台/杀进程/回前台：不丢 pending、能接管自己的锁；后台模式开关与最后窗口关闭的组合行为符合文档。

### [P1] 2.7 文件事件、文件树、保存触发：现在没有“外部变化”的宿主通道

- **问题/证据**：没有 OS 文件监听；只有当前显示的 tab 每 1.5 秒轮询 mtime（`T\src\document\useExternalChangeReload.ts:25`、`:75-147`），以及窗口 focus 时检查。文件树监听的是窗口内 DOM 事件 `FILE_WRITTEN_EVENT`（`T\src\utils\events.ts:89`，`T\src\files\useTreeData.ts:84-112`），跨窗口只同步 move/trash（`T\src\app\useEntriesFromOtherWindows.ts:20-48`）。保存只发插件事件 `didSave`，不发 DOM 事件（`T\src\app\useSaveWrites.ts:143-148`、`:181-186`）。
- **后果**：内置下载/删除后，文件树和其他窗口不会刷新；打开中的 tab 靠 1.5 秒轮询或 focus 才看到变化；保存后自动同步没有触发点，只能等 5 分钟 interval；外部编辑器改动延迟到下一次扫描。
- **建议**：服务写完后 `emit_to_all("sync-files-changed", paths)`（复用 `T\src-tauri\src\settings\app.rs:165-173` 的广播模式），前端一个桥接 hook 转成本窗口的 `FILE_WRITTEN_EVENT`/`ENTRY_TRASHED_EVENT`；新增通用 `file-saved` 事件（保存/自动保存两处），服务收到后 debounce；把“周期全量扫描”定为正确性来源，`notify` 只作 P2 桌面延迟优化；窗口 focus 也可触发一次 debounce 扫描。
- **验证**：两窗口同时开同一 folder，A 窗口触发同步下载：B 窗口树出现新文件、干净 tab 重载、脏 tab 不被覆盖；保存后 ≤5 秒触发一次 sync（按 saveGap）；外部改文件在 interval 内被扫描到。

### [P1] 2.8 传输、供应商、安全：HTTPS-only 与 WebDAV 原子性会直接卡住“WebDAV 为主”

- **问题/证据**：
  - 插件只接受 HTTPS endpoint（`P\...\config.ts:89-96`），插件 HTTP 也只允许 HTTPS 或 localhost（`T\src-tauri\src\plugins\access.rs:353-365`）。大量 NAS/自建 WebDAV 用 HTTP 或自签名证书；iOS ATS/Android cleartext 也会阻止 HTTP。
  - redirect 策略在 `network:*` 下会跟随任意 HTTPS 主机（`T\src-tauri\src\plugins\http.rs:76-83`），而 WebDAV 的 Basic Authorization 是请求头（`P\...\transport.ts:78-82`）；跨主机 redirect 有凭据泄露/SSRF 风险（取决于 reqwest 是否剥离敏感头，必须显式禁止或测试）。
  - WebDAV 的 `HEAD`/`HISTORY` 是直接 PUT（`P\...\transport.ts:156-159`，`P\...\publish.ts:94-96`）；并非所有 WebDAV 服务器保证 PUT 原子，崩溃可能留下半个 head，客户端会 `invalidManifest`。`create` 已经用 temp+MOVE（`transport.ts:160-187`），但提交点没有。
  - 供应商兼容性未验证：官方报告只到 0.3.0，且明确“Live WebDAV and Nutstore remain unverified”“not run in a native app”“no iOS”（`P\docs\cloud-sync\README.md:3-5`、`:126-131`）；当前代码已是 0.6.1（`P\plugins\catvinci.cloud-sync\textus-plugin.json:5`）。
  - iOS 没有 `NSLocalNetworkUsageDescription`（`T\src-tauri\Info.ios.plist` 全文件），连局域网 NAS 会触发本地网络权限；没有说明文案会被拒或无法访问。
  - 内置 E2E 加密会让 `ITSAppUsesNonExemptEncryption=false`（`T\src-tauri\Info.ios.plist:12-14`，注释写明“Only standard encryption (HTTPS)”）不再准确，涉及出口合规/App Store 声明。
- **后果**：最常见的 WebDAV 场景（NAS/自签名）直接不可用；redirect 可能泄露凭据；半个 head 可能让所有客户端停摆；iOS 审核/出口合规风险。
- **建议**：v1 继续 HTTPS-only，但启用系统根证书/自定义 CA（`reqwest` 的 native roots 或用户导入 CA），不支持明文 HTTP；redirect 默认同主机，S3 区域重定向以错误提示正确 region 而不是静默跟随；head/history/snapshot 在 WebDAV 上改为 temp+MOVE（S3 仍 PUT）；provider 差异做成表（S3/WebDAV/Nutstore 的 MKCOL/MOVE/HEAD/条件写）；补 iOS 本地网络说明；E2E 加密是否进内置 v1 需与出口合规一起决定。
- **验证**：Nextcloud、Synology、MinIO、R2、Nutstore 各跑一遍初始上传/双端/删除/冲突/历史；自签名 CA 可用；跨主机 redirect 不携带 Authorization；模拟 PUT 中断后 head 仍可读或能恢复；iOS 局域网首次请求出现系统权限提示。

### [P1] 2.9 CI 与互通验证：两套测试不在同一个仓库/同一个 pin

- **问题/证据**：云同步的单元/e2e 测试在 `textus-plugins` 仓库（`P\e2e\cloud-sync\flows.e2e.ts`），Textus CI 只把该仓库按 pin checkout 用于 e2e（`T\.github\workflows\ci.yml:191-194`、`:259-262`），并不运行 cloud-sync 的 175 个测试；e2e 的 HTTP 是页面内 fixture（`P\e2e\cloud-sync\flows.e2e.ts` 的 `Remote` 类），不碰真实服务器。`ci-config` 会拦 fork PR 改 CI（`T\scripts\guard-ci-config.mjs:9-13`）。本机 `textus-plugins` 是 shallow 的 `53b1f70`（cloud-sync 0.6.1），CI pin 是 `9dc102b`，两者不是同一提交。

### [P1] 2.10 依赖、体积、移动编译与 cfg 陷阱

- **问题/证据**：release 体积被明确当作约束（`T\src-tauri\Cargo.toml:13-34`，16.5 MB 级）；lock 里没有 rusqlite/notify/aws/diffy；`uuid` 只在 desktop 依赖（`:160-171`），核心 crate 在 mobile 会缺；`cfg(desktop)` 只由 tauri-build 给 app crate 设置（`T\docs\dev\ios-code-map.md:11-15`），在普通 crate 里会静默失效；`T\src-tauri\plugins\textus-files\src\lib.rs:41-53` 用 target_os 才是正确写法。`ring` 已在 lock（`T\src-tauri\Cargo.lock:3734`）且提供 PBKDF2/HKDF/HMAC/AEAD。
- **后果**：`cfg(desktop)` 写错会让桌面专属代码在移动端被静默排除，或反过来编译失败；`aws-sdk-s3`/bundled SQLite 可能让 iOS/Android 构建超时或体积超预算；`uuid` 在 mobile 缺失会直接编译失败。
- **建议**：核心 crate 用 target_os/feature；P1 不引入 rusqlite/notify/aws-sdk/diffy；加密直接用 ring；uuid 移到共享依赖；S3 手写 SigV4；P0 先做 iOS simulator/device 与 Android arm64 的 `cargo check/build`，量出体积/时间；体积增量写进 `Cargo.toml` 注释（照仓库现有风格）。
- **验证**：`cargo check`/`build` 四个目标（linux、macos、aarch64-apple-ios、aarch64-linux-android）通过；release/APK 体积增量在预算内；`cargo clippy --workspace --all-targets` 零警告；iOS/Android 构建时间不逼近 CI 60 分钟超时。

### [P1] 2.11 数据、迁移、崩溃：SQLite 是可选优化，不是起点

- **问题/证据**：仓库当前没有 SQLite；settings 的成熟模式是 `schemaVersion` + 损坏文件 move aside（`T\src-tauri\src\settings\store.rs:6-28`、`:60-100`；`T\src-tauri\src\json_file.rs:16-25`）。插件的 base/pending 是 JSON（`P\...\settings.ts:160-163`、`P\...\pending.ts:111-121`），且协议上限 20,000 文件（`P\...\model.ts:8`），所以本地状态天然有界。
- **后果**：一上来引入 SQLite 会新增 C 依赖、迁移、WAL/锁、损坏恢复、移动端构建五类问题；而收益（查询/并发）在 20k 文件上限下并不明显。另一个风险是 base 丢失被误判为“远端文件都新增”，产生大量下载/冲突副本；必须验证 base 丢失是安全的。
- **建议**：P1 用 JSON：`base.json`（与插件 Base 同形）、`cache.json`（path/size/mtime/hash/blocks）、`pending.json`、`status.json`；每个 folder 一个目录；原子写、损坏 move aside、丢失即重建；一个服务串行写。SQLite 只在实测（例如 >50k 文件、需要跨 folder 查询/历史缓存）后再评估。base 丢失的安全性要在测试里固定下来：空 base + 相同本地/远端只产生 equal/upload/download，不产生 delete。
- **验证**：删掉 base/cache/pending 各跑一次，远端不变、无数据丢失；写到一半 kill，重启后能 resume 或安全重扫；20k 文件 benchmark 的扫描/保存耗时；两个窗口同时改 config 不互相覆盖（服务串行）。

### [P1] 2.12 密钥、威胁模型与 Keychain

- **问题/证据**：现有密钥是 owner-only 文件（`T\src-tauri\src\plugins\files.rs:145-231`，`T\src-tauri\src\atomic.rs:107-111`），Unix 0600；Windows 依赖 `%APPDATA%` 的 ACL；没有任何 keychain 集成。插件为了自动同步把 sync password 也存进 `ctx.secrets`（`P\...\settings.ts:61-66`），即本地明文可读（owner-only）。
- **后果**：如果内置宣传“Keychain/Keystore 保护”，会与实现不符；备份（Time Machine/iCloud 设备备份）会带走 secrets；同用户恶意软件可读。
- **建议**：v1 明确 owner-only 文件 + 威胁模型（防其他用户/其他插件，不防同用户恶意软件/备份）；密码不进 DB/日志；Rust 用 `zeroize`；Keychain/Keystore 作为 P2，并单独评估“锁屏时后台能否读取”“重装后是否保留”“Android Keystore 需要 JNI/原生代码”。同步密码不可恢复的警告要在 UI 里说清楚。
- **验证**：新文件权限测试（Unix 0600）；日志/诊断/DB 扫描无 secret；备份包含 secrets 的行为写进文档；Keychain 方案有独立设计再评审。

### [P1] 2.13 启动、懒加载与预算

- **问题/证据**：预算实际是 1.00 MB（`T\vite.startup-budget.ts:7`），文档写 1.25 MB（`T\docs\dev\code-style.md:76`）；Settings 已经整体 lazy（`T\src\app\SettingsLayer.tsx:30`，`T\src\features\settings\lazy.ts:12-16`）；窗口栏插件状态也是 lazy（`T\src\app\frame\WindowBar.tsx:24-31`）。
- **后果**：如果把同步状态/IPC 放进 startup，容易突破预算或违反“Nothing new in the startup chunk”的评审规则；如果按 1.25 MB 估算会误判余量。
- **建议**：P1 只做 Settings 页 + 错误 notice；状态条 P2；`src/features/sync` 走 lazyModule；页面组件用 lazyComponent；同步 IPC 的 bindings 很小，但仍要测 entry；把文档的 1.25 改成 1.00（或说明实际值）。
- **验证**：`vite build` 过预算；`loadedModules()` 测试确认 startup 不含 sync-feature；打开 Settings › Sync 后模块才 loaded；bundle 分析显示 entry 无新增。

### [P1] 2.14 Fork 面与 rebase：文件数可控，但接入点清单不完整

- **问题/证据**：计划只列五个接入点（`T\docs\skein\discipline\薄fork魔改原则.md:29-31`；`T\docs\skein\specs\Textus-改造方案.md:810-816`），不包含 `Cargo.toml`、`lib.rs`、`invoke_handler.rs`、`bindings.rs`、Settings 页注册；而同步必然触碰这些。
- **后果**：下一次 rebase 按旧清单核对会漏掉冲突；`Cargo.lock` 每次都要重生成；`invoke_handler.rs` 是上游高频改动点。
- **建议**：把“后端服务注册”和“Settings 页注册”写进 patch 清单；核心全部放 crate；app 只在 `lib.rs` 加 `mod sync;` + `sync::init(app)`；命令用一个宏块；P1 不动 WindowBar/菜单/tray/`docs/dev/*`；每个 release 记录冲突文件数与耗时；通用宿主钩子尝试上游化。
- **验证**：把功能分支 dry-run rebase 到下一个上游 tag，统计冲突文件/人天；若连续两次 >3 人天，触发回退评估（计划 §12.7 的同一阈值）。

### [P1] 2.15 共存、迁移与退役：两个“官方同步”不能同时活着

- **问题/证据**：插件仍是官方插件、desktop-only（`P\plugins\catvinci.cloud-sync\textus-plugin.json:13`），README 已经提醒不要和社区插件同时开（`P\plugins\catvinci.cloud-sync\README.md:44-48`）；插件配置/凭据/base key 由 root+identity+account 派生（`P\...\settings.ts:44-66`、`:160-163`）；旧配置默认 `encrypt: true`（`P\...\settings.ts:40-43`）。内置若不做迁移，首次同步会重新 hash 全部文件；若不做共存检测，用户可能两个都开。
- **后果**：双重同步、锁冲突、冲突副本；迁移时误读旧加密配置会导致 `remoteEncrypted`/`legacyRemote`；用户重新输入连接信息的摩擦。
- **建议**：内置启动时检测 `plugins/state.json` 中 Cloud Sync 是否启用；若启用，设置页和 sync 启动都给出“先关闭插件”的阻断/警告。提供一次性“从 Cloud Sync 插件导入连接与 base”的显式流程（读取插件 config/secrets/base；旧配置按 `encrypt:true` 解释），或明确“不导入，首次同步可能产生冲突副本”。发布时决定插件的退役/冻结窗口；不要长期维护两套。
- **验证**：同时配置插件和内置时，内置拒绝运行并给出可操作提示；导入流程用真实插件数据 dry-run；关闭内置后插件能读写同一远端；旧 0.4/0.5/0.6 配置各有一个 fixture。

### [P2] 2.16 真实供应商、真机、加密审计与合规证据不足

- **问题/证据**：官方验证报告针对 0.3.0（`P\docs\cloud-sync\README.md:3-5`），当前是 0.6.1（`P\plugins\catvinci.cloud-sync\textus-plugin.json:5`）；报告明确说 live WebDAV/Nutstore 未验证、没在原生 app 跑、iOS 不支持、加密无独立审计（`P\docs\cloud-sync\README.md:126-131`）。
- **后果**：把“插件已多端验证”当成事实会误导阶段门；加密是核心功能但没有外部评审；App Store/出口合规没有准备。
- **建议**：spike 重新用 0.6.1 跑真实 WebDAV（Nextcloud/Synology）、MinIO、R2、Nutstore；iOS/Android 真机各一台；加密做一次独立评审或至少内部威胁建模；内置 E2E 前解决 `ITSAppUsesNonExemptEncryption`/出口分类；iOS 补 `NSLocalNetworkUsageDescription`。
- **验证**：每种供应商/平台留下日期、版本、步骤、结果；加密评审记录；App Store 上传预检通过。

### [P2] 2.17 规模与元数据成本

- **问题/证据**：每次 publish 写 head/history/snapshot 三份 JSON（`P\...\publish.ts:91-101`），上限 8 MB manifest/history（`P\...\model.ts:7-12`），20k 文件/2 MB 块（`:3-8`）；history 按小时/天抽稀（`P\...\history.ts:108-158`）。
- **后果**：大目录每次同步的元数据上传可能远大于实际文件变化；8 MB 上限可能先于 20k 文件触顶；没有增量 history。
- **建议**：用 5k/20k 文件做基准，量同步字节/耗时；文档写明上限；不要在 `/1` 上做增量改造；若未来需要 `/2`，先设计旧客户端只读迁移。
- **验证**：基准数据进 `test-results`/文档；接近 8 MB 的 fixture 通过/失败行为明确。

### [P2] 2.18 冲突/历史 UX、panic 与锁释放

- **问题/证据**：冲突是“本地保留 + 远端副本放 `Sync conflicts/`”（`P\...\planner.ts:82-87`），没有 merge；历史恢复在文件打开/有未同步编辑时写到旁边（`P\...\history-host.ts:49-68`）；JS 用 `finally` 保证释放锁（`P\...\engine.ts:416-428`），Rust panic 可能让任务直接死掉。
- **后果**：用户可能把冲突副本当垃圾删掉并同步删除；恢复历史时不知道写到了旁边；panic 留下远端锁。
- **建议**：UI 文案明确“两份都保留、不自动合并”；冲突中心提供打开两份/删除副本的明确动作；历史恢复提示“文件打开时写到旁边”；Rust 用 supervisor/`catch_unwind` 包裹 run，panic 后尝试释放锁并记录诊断。
- **验证**：打开/脏文件恢复历史的 e2e/手动；注入 panic 在每个阶段，重启后锁可恢复；冲突中心删除副本后其他设备按删除语义收敛。

## 5. 需要用户拍板的架构取舍

1. **是否正式推翻现有裁决**：内置同步与 `Textus-改造方案.md:772` 的“同步=深度分叉、不建议”、`:650` 的“不改同步”、`:742` 的“首版第三方，自建放最后”冲突。建议：先出 supersede 记录，明确“用户自有存储的内置客户端”不是“自建云/账号”，并接受“机制上是深分叉”；否则不做。
2. **协议所有权与插件退役**：内置发布后，插件是冻结为参考实现、还是长期双维护？建议：冻结 `/1`，内置成为所有者，插件只修安全；给出支持窗口。双维护会让成本翻倍。
3. **本地存储**：P1 是否接受“无 SQLite，JSON base/cache/pending”？建议接受（20k 上限、可导入插件 base、少一个 C 依赖）；SQLite 作为 P2 实测后的优化。
4. **加密是否进内置 v1**：进，才能加入已有加密远端；但会触发 iOS 出口合规/`ITSAppUsesNonExemptEncryption` 和加密评审。建议：进，但把合规作为 P1 发布门；否则内置只能读明文远端，等于不兼容现有用户。
5. **传输范围**：是否坚持 HTTPS-only？建议：是；支持系统根/用户自定义 CA，不做明文 HTTP；如必须支持局域网 HTTP，需要 iOS ATS/Android cleartext/网络安全配置的完整方案，不能只改一个 URL 校验。
6. **移动端范围**：iOS/Android 是否都做？建议：按计划 Android 先行、iOS 同代码但真机验证；v1 只承诺前台同步；后台同步（BGTaskScheduler/WorkManager）单独立项。Android 是要求“所有文件访问”还是实现 `content://` 后端，必须明确。
7. **移动端删除语义**：系统 Trash 在 iOS/Android 不可用。建议：app 管理回收站（app data，不进 vault），并提供“最近删除”；不要直接永久删除，也不要把回收站放进 vault 造成同步循环。
8. **打开/脏文档策略**：是否接受“任何打开的文件一律 defer”（插件语义）？建议：接受，简单且安全；不要尝试在 Rust 里猜 dirty。需要接受新增 open-docs 注册表这一宿主钩子。
9. **UI 面**：P1 是否只做 Settings 页 + 错误 notice？建议：是；窗口栏状态、菜单、tray 放 P2，减少 `WindowBar`/menu 的上游改动与 startup 预算风险。
10. **共存/迁移**：内置启动时是否阻断已启用的 Cloud Sync 插件？建议：阻断并提示；提供可选导入（config/secrets/base），不导入则明确可能产生冲突副本。不要让两个同步循环同时跑。
11. **无窗口生命周期**：桌面关掉最后一个窗口后是否继续同步？建议：进程活着就继续；Windows/Linux 由 background mode 决定进程是否活着；macOS 关窗后继续，但设置页要说明。移动端只在前台。
12. **依赖取舍**：是否接受“P1 零 rusqlite/notify/aws-sdk/diffy，crypto 用 ring，SigV4 手写”？建议：接受；如果后期 `notify` 的延迟成为真实痛点再加桌面-only 依赖，如果 SigV4 维护成本高再换 `aws-sigv4`（不是 sdk）。
13. **上游化**：open-docs 注册表、file-saved 事件、移动端文件/回收站 API 是否尝试提回上游？建议：拆成独立小 PR 按 `publishing-gate.md` 在新 clone 做；能上就减少 fork 面，不能上再本地维护。
14. **命名**：内置叫 “Sync” 还是 “Cloud Sync”？建议与插件区分，避免用户以为两个是同一功能；迁移提示要写清“原 Cloud Sync 插件的远端可直接使用”。

**一句话总结**：先让插件 spike 产出“移动端是否可行、协议是否可冻结、真实供应商是否可用”的证据；再用“规范 + 向量 + 无 Tauri 核心 crate + 薄 app 适配 + 懒加载 UI + JSON 本地状态”的内置方案做桌面 P1。不要把插件逐行翻译成 Rust，也不要在协议/移动端/合规证据不足时直接开写。
