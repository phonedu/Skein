# AI 协作纪律（下游增补）

> 来源：《通用-AI协作与工程管理规范》（`C:\Project\通用-AI协作与工程管理规范.md`，墨契蒸馏）2026-11-16 对账后**只抄本仓没有的四件**；状态源、ID、数值锚、门禁链、数据隔离、ADR 等机制 `AGENTS.md` / `CONTRIBUTING.md` / skein 各文档已覆盖，**不重复建**（通用规范 §C.1：一件事只在一处写全量）。AI 署名 trailer（通用规范 §B.5）经用户裁决**不采用**（2026-11-16）。生效 2026-11-16，只约束之后的协作，不补存量。冲突时按 skein README §六裁判：工程门禁按上游，流程纪律按本页。
>
> 上游的 AI 协作开发方式调研见 [research/上游AI协作开发方式.md](../research/上游AI协作开发方式.md)（参考，不是纪律；本页规则不受影响）。

## 一、任务六行（开工前写，写进汇报开头）

```text
问题：用户做了什么，当前发生了什么错误。
期望：用户希望看到什么结果，哪些数据不能改变。
标准：什么算对——可执行判据（能写成验收项/测试的那种）。
不做：明确排除项（这次不碰什么）。
范围：属于哪条工作线（D1 / 手机 / 同步 / 上游 / 主题 / 文档）；涉及哪些端。
证据：准备用哪条自动化命令、哪步人工操作证明。
```

「标准 / 不做」两行是硬门槛：写不出就先问清再动手（本仓成因：2026-11-16 混读事故——需求模糊时 AI 拿上游文档当规划）。

任务涉及**上游**（开 issue、改上游代码、开 PR、回 review）时，六行之外先按
[publishing-gate.md](publishing-gate.md) 的「上游工单」写清仓、基线 commit、
分支、issue/PR 关联和确切文件；「范围」一行写明这次是 fork 还是上游克隆，
**两边都要就分两步做，不在两边各写一版**。

## 二、完成四行（收尾时补）

```text
改动：代码、文档分别改了什么。
验证：命令与输出、人工步骤和结果。
未验证：仍缺什么环境/真机/视觉证据——没跑的写「未验证」，不写成通过。
状态：已实现 / 后续规划 / 阻塞。
```

## 三、多会话红线（违反 = 当次交付作废，不是「下次改」）

1. **路径限定提交**：`git commit -m "..." -- <自己的文件>`；禁 `git add -A` / `git add .` / 不带路径的裸 `git commit`；禁 `--amend`。提交前 `git diff --cached --name-only` 核对文件清单。
2. **单一写者**：一份文档同一时间只让一个会话改；接手先 `git status --short` 看工作区；看到别人的未提交改动不替对方提交。
3. **进程纪律**：只按自己记下的 PID 清理；禁按端口/镜像名批量杀。
4. 未执行的门禁不得写成「通过」；宁可写「未验证」。
5. **提交前重读**：`git status --short` 与 `git log --oneline -3`；看见别人刚
   提交、或同一文件正在被另一会话改，先停下来对齐，禁止拿自己的旧缓冲覆盖
   上去（2026-11-19 STATUS被旧缓冲回退过一版）。

## 四、报告四块分列

最终汇报按四块分开写：**门禁读数 / AI 审查 / 人工验收 / 未验证项**——不许合并成一句「都通过」。PR 模板的「Skein delivery evidence」同此四块。

## 五、一次改动该动哪些文档（防漏更新）

| 改动类型         | 必须更新                                                               | 需要时                         |
| ---------------- | ---------------------------------------------------------------------- | ------------------------------ |
| 新增裁决         | 新文件 `decisions/NNNN-*.md`；推翻旧裁决写 `supersedes`，不改旧文件    | 行为变了同步改 `specs/` 对应文 |
| 改方案           | `specs/` 对应文件；裁决不变就不新开裁决                                | 跨方案时补一条裁决             |
| 画板             | **已删除（2026-11-20，裁决 29）**：不新增/复活画板；界面以宿主现状为基 | —                              |
| 用户可感知的变化 | `docs/releases/next/` 新片段（英文）                                   | —                              |
| 任务进度         | `STATUS.md` 一行；完成项当日删除，里程碑才在 `archive/` 留证据         | —                              |
| 文档过期         | 移 `archive/`；跑 `npm run docs:index` 让索引跟上                      | —                              |
| 文档两处对不上   | 实现与可执行锚（测试断言）先行；定不了的挂 `STATUS.md` §5 待审/触发点  | 带触发点与默认值               |

不写版本号、修订记录和手写目录；`git log` 是历史，`INDEX.md` 与 `decisions/README.md` 由脚本生成。

## 六、偏差与缺口

偏差记在 `STATUS.md` §5 Waiting / Blocked（或 §6 待审），写清缺什么、触发点和默认值；不另立偏差册，也不写“暂无”占位。「为什么这么裁」由 `decisions/` 承接。

## 七、从上游借来的四条（2026-11-20 增补）

> 上游做法调研见 [research/上游AI协作开发方式.md](../research/上游AI协作开发方式.md)。只借下面四条；不借的也写在后面。

1. **仓库即提示词。** 同一段背景、同一套步骤，在对话里说过两次以上，就必须写进 skein 文档、[工程菜谱](工程菜谱.md)或 `.claude/skills/`；下一会话从文档读，不从聊天记忆读。文档是 agent 的输入，不是交付后顺手补的附件。
2. **规则要能执行。** 重复出现的 review 意见，要么变成检查脚本，要么变成《工程菜谱》里的“做到什么算对”，要么变成 PR / STATUS 的固定栏。只靠人反复提醒的规则，下一会话就会丢。新增检查单独提交并说明为什么；不改现有门禁来“让检查过”。`check:skein` 已于 2026-11-20 接进 `npm run check`，没有改任何现有检查。
3. **高频操作写成菜谱。** 加同步命令、加插件页/动作、加设置/菜单/字符串/测试、改界面小改/新裁决、跟上游 tag 并线——按《[工程菜谱](工程菜谱.md)》走。每步写清先读哪份文档、改哪些文件、跑什么验证、记录到哪里。
4. **交付证据固定四块。** 完成四行（改动/验证/未验证/状态）之外，再列：门禁读数、AI 审查、人工验收、未验证项；能复现的命令写命令。AI 产出必须有人读懂每一行；不写 `generated with` / `Co-authored-by` trailer。

**不借的四条**（调研文档有证据与理由）：15 个上游检查脚本原样搬；一个 release 一个 PR 的节奏；`docs/design/`、`docs/images/` 与 `design-language.md`；把 AI 当自动合并者。

## 八、验证闭环（2026-11-20 用户立规）

1. **不留待验证项。** 除特殊情况外，每个任务必须由 AI 自己验证到可复现证据（命令与输出、built app 步骤、引擎/夹具 round-trip），不得把“请用户验证”当作完成。只有 AI 能跑、能看的证据才算验证。
2. **特殊情况的边界。** 只有外部条件确实不具备时才算例外：没有真实凭据/账号、没有真机、第三方服务不可达、环境被其他进程或外部应用占用。发现时立即说明缺什么，并做能做的替代验证（单测、合成夹具、引擎级、本机服务）；剩余项写进 STATUS 的 Waiting / 待审，不写成“已验证”。
3. **验证后继续。** 一项验证通过后不等指令，按 STATUS 顺序继续同一工作线的下一项；只有遇到第 2 条的外部阻塞或需要用户裁决的产品选择才停下。
4. **完成四行的“未验证”只写特殊情况的外部缺口**，不写自己能跑却没有跑的项目。

## 九、任务边界（2026-11-21 用户立规）

1. **只做当次明确要求的事。** 让审文档就只审文档：不改代码、不跑构建、不做原生冒烟、不开 Android、不顺手重构。发现相邻问题，写进报告或STATUS，停在边界。
2. **任何扩大范围的动作，先经用户明确同意。** 包括但不限于：从文档审计切到代码验证、从静态检查切到 built app/真机、从单测切到全量测试、从当前分支切到别的分支、从修复切到重构。先说明“为什么要现在做、预计多久、不做的后果”，得到明确答复再动；没有答复视为不同意。
3. **验证也受边界约束。** 为完成当次改动所必需的测试可以跑；构建、真机、性能基准、长时间全量套件属于独立任务，先问。§八“验证后继续”只在用户当次批准的工作线内适用，不得用来跨线。
4. **违反即当次交付不合格。** 不辩解、不把跑偏算成“顺手验证”；在报告开头直接承认范围错误和实际耗时。

## 十、外部 AI 复核（2026-11-21 用户立规）

1. **触发**：插件 / D1 资产链实现完成（D1e）后、D0.5 小样本与 D1d 验收前。同步或宿主的大改也可临时套用；不是每次小改都跑。
2. **执行者**：`opencode run`，在独立 worktree 或干净 clone 中做，不碰主 checkout、不读 secrets、不改仓库。用 `opencode` 的只读审计/测试能力，不把它的修改直接合入。
3. **输入**：`AGENTS.md`、`docs/skein/README.md`、D1 规格与 STATUS、本次改动范围；要求它运行现有测试、读实现、找功能性缺陷/代码错误/测试缺口，按严重度列出并给文件行号与复现步骤。
4. **处理**：我们逐条复现；阻断项修复并补测试，非阻断项进 STATUS §5，opencode 的结论不等于验收，最终仍由我们的门禁、真机与用户验收。
5. **位置**：任务 `D1r`（D1e 后，D0.5/D1d 前）；D1 后插件若继续改，发布前再跑一次窄复核。
